# GitHub 이슈 작성

1. 대상 저장소·권한·요청 범위를 확인한다. 문안 작성과 게시를 구분한다. 연결되지 않은 계정이나 저장소를 추측해서 사용하지 않는다.
2. 실제 .github 이슈 템플릿과 중복 이슈를 읽는다. YAML 이슈 양식이면 필수 항목·선택지·검증 요건을 파악해 누락 없이 문안에 반영한다. Markdown 본문으로 변환할 때 필드의 label을 제목으로 쓰고 dropdown 선택값과 checkbox의 확인/미확인 상태를 보존한다. 존재하지 않는 label·milestone·담당자를 만들지 않는다.
3. 버그라면 환경, 재현 절차, 기대 결과, 실제 결과, 재현 빈도와 로그 근거를 정리한다. 개선이라면 문제·영향·목표·제외 범위·완료 기준을 쓴다. 추정 원인과 확인된 사실을 분리한다.
4. Unreal 관련 정보는 실제 엔진 버전·빌드 설정·플랫폼·맵·네트워크 역할·관련 에셋에서 확인한다. 고정 프로젝트 로그 경로를 가정하지 않는다. 로그의 비밀정보와 개인정보를 제거하고 공유 가능한 증거만 포함한다.
5. 사용자가 게시를 승인한 경우 사용 가능한 GitHub 도구 또는 CLI로 생성한다. CLI의 여러 줄 본문은 body 파일을 사용한다. 담당자 지정·멘션·알림은 별도의 사용자 지시와 확인된 신원 범위 안에서만 수행한다.
6. 생성된 번호·URL·내용을 확인한다. 응답이 불확실하면 실제 이슈 목록을 조회하여 중복 생성 여부부터 판단한다. 실패를 성공으로 보고하지 않는다.

[요구사항 분석](../../../docs/ai/REQUIREMENTS_ANALYSIS.md), [검증](../../../docs/ai/VERIFICATION.md)을 참고한다. 외부 도구가 없으면 게시 가능한 초안과 필요한 연결만 남긴다.

## 프로젝트 작업 경계

실행 전에 [작업 경계 기준](../../../docs/ai/WORK_BOUNDARIES.md)과 프로젝트가 채운 경계표·CODEOWNERS·기존 변경/잠금을 확인한다. 리뷰 소유자와 AI 쓰기 허용 범위는 별도다. 경계 충돌 시 기존 승인을 확인하고, 미승인 경로로 범위를 넓혀 진행하지 않는다. 필요한 결정과 독립적으로 계속할 작업을 구분한다.
