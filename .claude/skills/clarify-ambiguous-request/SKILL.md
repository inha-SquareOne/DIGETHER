# 모호한 요청 구체화

1. 요청, 기존 승인, 현재 파일과 [프로젝트 프로필](../../../docs/templates/PROJECT_PROFILE_TEMPLATE.md)을 읽어 목적·대상·완료 기준을 추출한다. 검색으로 확인 가능한 사실을 사용자에게 다시 묻지 않는다.
2. 불명확한 항목을 구현 결과가 달라지는 결정과 사소한 구현 선택으로 나눈다. 사소한 선택은 기존 관례에 맞게 처리하고 가정을 기록한다.
3. 결정이 필요하면 질문 하나에 하나의 주제를 담는다. 실제 가능한 선택지 2–3개와 각각의 결과·비용을 간단히 제시한다. 질문 도구가 제공되면 사용하고, 없으면 대화로 묻는다. 특정 제품의 질문 도구 이름을 필수 조건으로 삼지 않는다.
4. 답을 기다리는 동안 의존하지 않는 조사·문서·검사를 계속한다. 승인이나 핵심 결정이 필요한 작업은 응답 전에 실행하지 않는다. 시간 경과나 무응답을 승인으로 해석하지 않는다.
5. 답을 [작업 브리프](../../../docs/ai/TASK_BRIEF.md)에 반영한다. 이미 받은 결정을 다시 질문하지 않고, 충돌하는 새 증거가 있을 때만 이유를 설명한다.

## 출력

확인된 목표, 실제 근거, 잠정 가정, 남은 선택, 검증 가능한 완료 조건을 짧게 정리한다. 프로젝트별 게임 규칙·네트워크 구조·엔진 버전은 사용자의 결정 없이 공통 표준으로 확정하지 않는다. [요구사항 분석](../../../docs/ai/REQUIREMENTS_ANALYSIS.md)을 함께 따른다.

## 프로젝트 작업 경계

실행 전에 [작업 경계 기준](../../../docs/ai/WORK_BOUNDARIES.md)과 프로젝트가 채운 경계표·CODEOWNERS·기존 변경/잠금을 확인한다. 리뷰 소유자와 AI 쓰기 허용 범위는 별도다. 경계 충돌 시 기존 승인을 확인하고, 미승인 경로로 범위를 넓혀 진행하지 않는다. 필요한 결정과 독립적으로 계속할 작업을 구분한다.
