# 설계 결정 기록

## 시작

프로젝트의 기존 결정 기록 위치·번호·상태·문서 지도를 읽는다. 이미 결정 기록이 있다면 갱신/후속 기록으로 연결하고 중복 문서 체계를 만들지 않는다. 이유를 묻는 요청은 먼저 실제 기록을 찾아 답한다. 기록이 없으면 확인되지 않은 과거 결정을 만들어 내지 않는다.

## 작성

1. 지금 결정할 문제, 엔진/플랫폼/네트워크/데이터 등의 제약과 확인한 근거를 정리한다.
2. 실제 검토한 대안과 선택/제외 이유, 장점·비용·위험·검증·재검토 조건을 적는다. [대안 비교](../present-alternatives/SKILL.md)의 비교 결과를 필요한 만큼 사용한다.
3. 결정 상태를 proposed·accepted·deprecated·superseded 등 프로젝트 관례로 명확히 한다. 사용자가 결정하지 않은 정책을 accepted로 쓰지 않는다. 승인된 결정의 기록을 요청받았다면 다시 허락을 반복해서 요구하지 않는다.
4. 기존 작업 범위에 기록 작성이 포함되면 해당 위치에 작성한다. 위치 또는 결정권 자체가 미결이면 초안을 구체화하고 필요한 결정만 확인한다. 문서화 행위가 코드 수정·설정 변경의 자동 승인은 아니다.
5. 기존 기록을 대체하면 대체한/대체된 문서를 연결하고 이력을 보존한다. 과거 결정을 사후 기록할 때 원래 결정 시점과 현재 작성 시점, 불확실한 근거를 구분한다. 번호 충돌과 링크·색인을 확인한다.

## 간단한 양식

- 식별자·제목·작성일·원래 결정일(해당 시):
- 상태·결정 근거·실제 결정 참여자:
- 문제와 제약·근거 경로:
- 결정 또는 제안:
- 검토한 대안과 선택/제외 이유:
- 영향·비용·위험·검증·복구:
- 재검토 조건·대체 기록 링크:

가벼운 변수명 선택까지 별도 ADR로 늘리지 않는다. [문서 유지](../../../docs/DOCUMENTATION_POLICY.md)와 [인계](../../../docs/ai/SESSION_HANDOFF.md)의 역할을 대신하는 작업 일지로 사용하지 않는다.

## 작업 경계와 근거

[작업 경계](../../../docs/ai/WORK_BOUNDARIES.md), 프로젝트 경계표·CODEOWNERS·기존 변경/잠금을 먼저 확인한다. 경계 충돌 시 미승인 경로로 범위를 넓히지 않는다. 읽기 조사와 파일 수정·외부 실행 권한을 구분한다.
