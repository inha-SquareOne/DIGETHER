# Git 커밋 준비와 실행

## 범위와 현황

- 사용자가 요청한 것이 커밋 실행인지, 메시지 초안 또는 변경 검토인지 구분한다. 이 스킬이 선택되었다는 이유만으로 커밋·푸시 권한이 생기지 않는다.
- 실제 저장소 루트·현재 브랜치·작업 트리·index·untracked 파일을 읽는다. 기존 staged 변경과 이번 변경을 분리한다. 파일 내용과 diff에 비밀정보가 포함되면 출력·커밋에 노출하지 않는다.
- [소유권 확인](../check-code-ownership/SKILL.md), 저장소 지침, 실제 최근 메시지와 커밋 템플릿을 확인한다. 기본 브랜치명·작업자명·메시지 형식을 추측하지 않는다.

## 준비

1. 관련 코드·에셋·문서 변경과 검증 결과를 검토한다. 실행하지 않은 테스트를 통과로 적지 않는다. 엔진 빌드가 불가능하면 가능한 정적 확인과 미검증 영역을 구분한다.
2. 승인된 파일의 정확한 경로만 stage한다. 전체 디렉터리 일괄 staging으로 다른 변경을 포함하지 않는다. 이미 index에 관련 없는 변경이 있으면 커밋 전에 범위를 해결한다. 다른 작업자의 변경을 자동으로 unstage하거나 수정하지 않는다.
3. staged diff와 파일 목록을 다시 읽어 이번 커밋의 전체 내용을 확인한다. 의도하지 않은 바이너리·생성물·자격증명·대용량 원본을 확인한다.
4. 실제 최종 변경을 설명하는 제목과 본문을 작성한다. 여러 줄 본문은 안전한 파일 인자로 전달하고 셸 치환에 노출하지 않는다. 트레일러는 적용되는 저장소 관례를 따른다.

## 실행과 보고

실행이 승인된 경우에만 커밋한다. 결과 커밋 ID·포함 파일·남은 변경을 확인한다. hook 실패 시 원인을 조사하고 우회 옵션을 임의로 사용하지 않는다. 결과가 불확실하면 Git 상태와 로그를 조회한 뒤 재시도한다. amend·rebase·강제 푸시·자동 푸시는 이 절차의 기본 단계가 아니다.

메시지 초안만 요청받았다면 실제 커밋 없이 초안과 검사 결과를 제공한다. [검증 기준](../../../docs/ai/VERIFICATION.md)을 따른다.

## 프로젝트 작업 경계

실행 전에 [작업 경계 기준](../../../docs/ai/WORK_BOUNDARIES.md)과 프로젝트가 채운 경계표·CODEOWNERS·기존 변경/잠금을 확인한다. 리뷰 소유자와 AI 쓰기 허용 범위는 별도다. 경계 충돌 시 기존 승인을 확인하고, 미승인 경로로 범위를 넓혀 진행하지 않는다. 필요한 결정과 독립적으로 계속할 작업을 구분한다.
