# 이슈 쉽게 쓰고 처리하기

**제목과 필수 질문 두 개부터 적으면 된다.** 모르는 정보는 비워 두거나 “잘 모르겠어요”라고 쓰고, 등록 후 댓글로 보완한다. 원인 분석이나 해결책까지 알아야 신고할 수 있는 것은 아니다.

## 어떤 양식을 고르나요?

| 양식 | 이럴 때 | 제목 예시 |
|---|---|---|
| 버그 | 예상과 다르게 동작하거나 게임이 멈췄다 | `[버그] 방에 다시 들어오면 친구 목소리가 안 들려요` |
| 작업·개선 요청 | 만들거나 고치거나 준비할 일이 있다 | `[작업] 설정 화면에 마이크 테스트 버튼이 필요해요` |
| 밸런스 변경 제안 | 난이도·가격·보상·시간 같은 규칙을 조정하고 싶다 | `[밸런스] 초반에 장비를 사기까지 너무 오래 걸려요` |
| 플레이테스트 피드백 | 해 보니 재미있거나 불편했던 점을 전하고 싶다 | `[피드백] 귀환 위치를 찾기 어려웠어요` |

구분이 어려우면 가장 가까운 양식으로 등록한다. 확인하는 사람이 분류를 보완한다. 한 글에는 한 문제나 한 작업을 적고, 같은 문제가 이미 있으면 기존 글에 내 경험·자료를 댓글로 추가한다.

## 작성은 이렇게 하면 됩니다

1. 저장소 **Issues → New issue**에서 양식을 고른다.
2. 제목에 무슨 일이 있었는지 한 줄로 적고, 별표가 붙은 질문 두 개에 답한다.
3. 사진·영상이나 알고 있는 환경이 있으면 선택 항목에 덧붙이고 제출한다. 사진·로그의 비밀번호·토큰·개인정보는 가린다.

아래 정도로 시작해도 된다. 예시는 상황을 설명하기 위한 것으로 실제 확인된 버그나 승인된 변경 요청을 뜻하지 않는다.

| 양식 | 짧은 작성 예 |
|---|---|
| 버그 | **일어난 일:** 친구 목소리가 안 들렸어요. **직전에 한 행동:** 방에서 나갔다가 다시 들어왔어요. |
| 작업·개선 요청 | **할 일:** 설정에서 마이크를 시험하고 싶어요. **완료 모습:** 말하면 입력 여부를 확인할 수 있어요. |
| 밸런스 변경 제안 | **대상:** 초반 장비 가격. **관찰·원하는 방향:** 세 번 탐사해도 못 샀어요. 초반 구매 부담이 줄면 좋겠어요. |
| 플레이테스트 피드백 | **해 본 상황:** 친구 둘과 첫 탐사를 했어요. **느낀 점:** 귀환 위치를 몰라 오래 헤맸어요. |

버그는 한 번만 발생했거나 직전 행동이 기억나지 않아도 등록할 수 있다. 기대한 동작을 모르면 비워 두고 실제로 본 내용을 적는다. 밸런스 제안도 정확한 수치를 정할 필요는 없다.

빌드 파일 이름·받은 날짜, 맵·장소, 몇 명이 했는지, 방장인지 참가자인지 알면 도움이 된다. Git 커밋·SVN 리비전·엔진 버전 같은 개발 정보는 알고 있을 때만 적는다. 자료를 모으기 위해 게임을 다시 설치하거나 저장 파일을 지울 필요는 없다.

## 등록 후 확인하는 사람의 일

신고자는 경험한 내용을 적고, 작업을 맡는 사람이 착수 전에 다음을 보완한다. 실제 담당은 [작업 경계](../project/PROJECT_BOUNDARIES.md)에서 확인하며 임의로 배정하지 않는다.

- **버그:** 발생 빌드(Git 커밋 + SVN 리비전), UE 버전·플랫폼, 맵, 에디터/패키지, 인원·호스트/클라이언트·Steam/LAN, 재현 여부·빈도, 기대 동작의 근거를 확인한다. 모르는 값은 추정해서 채우지 않는다.
- **작업:** 목적·포함/제외 범위, 담당·쓰기 경로·선행 작업, 완료 조건과 필요한 검증을 확인한다. 에셋·맵을 바꾸면 편집 예약/잠금도 확인한다.
- **밸런스:** 관찰 조건과 현재 규칙/수치가 확정값인지 시험값인지 확인하고, 변경 목표·영향·비교 방법을 정리한다.
- **피드백:** 관찰 사실과 느낌을 구분해 읽고, 실행할 변경이 정해지면 관련 버그·작업·밸런스 이슈에 연결한다. 같은 상세 내용을 여러 글에 복제하지 않는다.

게임 규칙·수치는 [Notion 승인 근거](../project/DOCUMENTATION.md)를 확인한 뒤 구현한다. 이슈 등록은 기획 승인이나 작업 착수 확정이 아니다. 기술·운영 결정은 관련 [ADR](../decisions/)에 연결한다. 상세 개발 절차는 [개발 흐름](../project/DEVELOPMENT_WORKFLOW.md)을 따른다.

## 상태와 분류는 적게 유지합니다

기본 흐름은 **접수 → 확인·재현 → 작업 대기 → 진행 → 검증 → 완료**다. 작업·제안은 확인 단계에서 목표와 승인 상태를 정리한다. 외부 결정이나 선행 작업을 기다리면 현재 상태를 유지하고 기다리는 이유·관련 글을 남긴다. 날짜와 담당자는 실제로 정해졌을 때만 적는다.

| 구분 | 기록 기준 |
|---|---|
| 종류 | 위 양식 4종. 잘못 골랐어도 다시 쓰게 하지 않고 분류를 보완한다. |
| 분야 | 게임플레이·네트워크·UI·아트·사운드·빌드/도구 중 관련 분야. 필요할 때만 추가한다. |
| 심각도 | 치명(실행/진행 불가·데이터 손실), 높음(핵심 기능 손상), 보통(우회 가능), 낮음(영향이 작은 문제). 시각·음성 문제도 실제 영향으로 판단한다. |
| 우선순위 | 긴급·높음·보통·낮음. 테스트/제작을 막는 정도와 선행 의존성을 보고 확인하는 사람이 정한다. 미정이면 미정으로 둔다. |

Projects 보드를 사용할 때는 상태·담당자·분야·우선순위부터 두고, 실제 목표가 정해지면 마일스톤을 연결한다. 진행 상태는 보드 한 곳에서 관리하고 Notion이나 이슈 본문에 같은 상태표를 수작업으로 복제하지 않는다. 보드가 없으면 이슈 댓글에 진행·대기 이유를 남겨 운영할 수 있다.

라벨·Projects 필드·자동화는 GitHub에서 별도로 설정해야 한다. 이 문서와 양식 파일을 추가한 것만으로 생성되지는 않는다. 기존 이름·권한을 확인하고 연결하며, 신고자에게 라벨 선택이나 보드 입력을 요구하지 않는다.

## 수정 확인과 종료

수정한 사람은 PR과 확인할 빌드를 연결하고, 확인한 사람은 아래 내용을 이슈 댓글에 남긴다. 재검증 전 PR에는 `관련 #번호`로 연결하고, 필요한 검증이 끝나면 이슈를 닫는다. 자동 종료 키워드나 보드 자동화가 재검증 전에 닫지 않도록 설정을 확인한다.

```text
확인 빌드: 배포 파일명 또는 Git 커밋 + SVN 리비전
확인한 사람 / 날짜:
확인한 상황: 맵·인원·방장/참가자 등
결과: 해결됨 / 다시 발생 / 확인 못 함
정상·경계·관련 기능 확인:
남은 문제·미검증 / 사진·영상·로그:
관련 PR:
```

확인 수준은 [검증 계획](../verification/VERIFICATION_PLAN.md)을 따른다. 네트워크·공유 상태는 L1~L3 및 M2, 플랫폼 세션·음성은 M3 확인이 기본이다. PR 병합과 필요한 게임 검증을 구분하고, 확인하지 못한 범위를 완료로 쓰지 않는다.

중복이면 원래 글을 연결해 닫고, 기획대로인 동작이면 기준과 이유를 설명한다. 재현하지 못했다면 확인한 빌드·조건과 추가로 필요한 정보를 남긴다. 단지 재현하지 못했다는 이유로 “수정 완료”로 닫지 않는다. 같은 문제가 다시 발생하면 기존 글을 다시 열거나 새 글에 이전 번호를 연결한다.
