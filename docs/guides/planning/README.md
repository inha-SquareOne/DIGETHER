# 기획반 안내

기획은 Notion에서 작성한다. GitHub에서는 개발 요청과 결과를 확인한다. 코드 편집이나 Git 설치 없이 참여할 수 있다.

## 처음 읽을 순서

1. [문서 운영](../../project/DOCUMENTATION.md): 기획 원본·개정·승인과 구현 수용의 차이.
2. [기획 이관 안내](../../planning/README.md): 실제 Notion 주소가 등록됐는지 확인. 아직 없다면 초기 이관 절차로 초안을 Notion에 가져와 검토한 뒤 Notion에서 작성한다. 이관 전 저장소 초안을 고쳐야 하면 전달 담당에게 요청한다. 두 곳을 동시에 편집하지 않는다.
3. [담당과 경계](../../project/PROJECT_BOUNDARIES.md): 승인자와 개발 전달 담당 확인.
4. [GitHub 초보 안내](../GITHUB_BEGINNER.md)의 웹 요청·리뷰 부분.

## 하루 작업과 전달

1. 맡은 Notion 요구사항의 현재 개정과 승인 상태를 읽는다. 변경 목적, 플레이어에게 보일 동작, 수치·예외, 완료 조건을 작성한다. 미정인 부분은 질문으로 남긴다.
2. 기존 요구 ID를 유지하고 개정 번호를 올린다. 승인자·승인일이 없으면 초안으로 표시한다. 편집 완료가 곧 승인 완료는 아니다.
3. 개발 작업이 필요하면 관련 GitHub Issue가 있는지 먼저 찾는다. 있으면 같은 Issue에 변경 링크와 영향을 남긴다. 없으면 아래 양식으로 새 요청을 작성한다. 계정 권한이 없으면 양식을 개발 전달 담당에게 보내고 생성된 Issue 링크를 받는다.
4. 구현 PR과 검사 결과를 읽는다. 결과 영상·빌드에서 완료 조건을 확인하고 성공/실패 조건을 댓글로 남긴다. Notion에는 구현 증거 링크와 기획 수용 결과를 기록한다.

```text
제목: [요구 ID] 플레이어에게 필요한 변화
Notion 원문 URL / 개정 / 승인 상태·승인자·승인일:
목적과 기대 동작:
변경 전 → 변경 후:
완료 조건(눈으로 확인하거나 반복할 수 있는 조건):
예외·미결 질문 / 이번에 하지 않을 범위:
관련 Issue·PR / 참고 이미지:
```

기획 승인과 개발 PR 병합은 다른 판단이다. 이미지가 좋아 보인다는 의견만으로 다인 동작·성능 검사를 통과했다고 쓰지 않는다. 개발 완료 상태는 GitHub 증거로 확인하고 Notion에 별도 진행표를 중복 관리하지 않는다.

## 잘못 적었거나 구현과 다를 때

기획을 바꾼 이유와 이전 개정을 남기고 담당에게 영향을 알린다. 구현 중인 규칙을 조용히 덮어쓰지 않는다. PR에 기대 동작·실제 동작·재현 순서·영상 시점을 적고, 원인이나 해결 방법이 확인되지 않았다면 추측으로 구분한다. 코드·에셋을 직접 되돌릴 필요는 없다.

Notion 접근 불가, 승인 기준 충돌, 신규 규칙의 영향 범위가 불명확하면 해당 결정만 담당자와 확인한다. 다른 독립적인 기획 작업은 계속할 수 있다.
