# 갱도 미로·폐교 탐사 프로토타입 계약

기준일: 2026-10-29. 상태: **사용자 지시에 따른 시험 구현·완주 검증 완료**. 기획 운영 원본은 Notion이며 이관 전 [게임 기획](../GAME_DESIGN.md)을 참조한다. Notion 원문 URL·승인 개정은 확인되지 않았다. 이 문서는 정식 기획이나 밸런스 확정이 아니다.

## 사용자 요청과 완료 기준

사용자는 돈을 직접 입력해 납부하고, 갱도 미로의 한 지점에서 포털로 학교 컨셉 공간에 진입해 탐사한 뒤 돌아와 정산·납부하는 큰 흐름을 요청했다. 기존 실제 굴착을 유지하며 이 흐름을 한 번 연속 플레이할 수 있어야 한다. 갱도·폐교 공간의 배치·길이·조명·시험 회수품과 수치는 플레이 검증용이며 정식 생성 알고리즘·경제값이 아니다.

완주 관찰은 거점 출발 → 갱도 미로를 실제로 이동해 포털 발견 → 폐교 진입 → 회수품 획득 → 포털로 갱도 복귀 → 기존 승강기 탑승·화물 회수 → 거점 귀환과 기존 정산 확인 → 납부대에서 금액 입력·제출 → 잔고와 목표 진행 확인이다. 다음 탐사 출발도 확인한다. 포털은 회수나 정산 자체를 처리하지 않으며 획득한 물품은 기존 소지·운반·승강기 규칙을 따른다. 긴급 탈출은 기존 개인 탈출 규칙을 따른다.

## 확인된 기준선

- `RequestStartRun`은 출발 참가자를 고정하고 RunId를 새로 발급해 `Expedition`으로 전환한다. 기존 탐사 제한 시간과 승강 운행 규칙을 유지한다.
- `FinishRun`은 한 번만 정산하고 Day를 한 번 올린다. 거점 이동이 막히면 `Returning`에서 재시도하고, `CompleteReturn`은 Base 또는 출발 당시 4일차 목표 미달이면 GameOver로 전환한 뒤 시험 저장한다. 일반 화물·생존자 지급은 기존 `DigetherPrototypeRules`를 따른다.
- `RequestDeposit(Caller, Amount, OutMessage)`는 서버 권위·Base·양수·잔고를 검사하고 목표 잔여분을 상한으로 납부한다. 목표 달성 시 출발 유지 동작을 취소하고 새 목표·1일차로 바꾼다. 현재 `RequestBeginDeposit`은 납부대를 점유한 채 주기적으로 1씩 내는 방식이다. 입력 제출 기능은 아직 이 API만으로 제공되지 않는다.
- 구현 전 월드 빌더는 승강기·납부대·굴착 지형과 매 탐사의 시험 회수품을 생성했으며 폐교는 복도 모양 외형만 있었다. 이번 작업에서 미로·양방향 포털·학교 회수품을 구현하고 BP 연결 및 패키지 실행을 검증했다. 최종05의 1인 완주13단계·굴착6단계와 같은 게임 코드인04의 로컬4인 완주13단계를 통과했다. 기존 실제 굴착의 한정 볼륨과 검증 범위는 [프로토타입](PROTOTYPE.md), [굴착 구현](../design/EXCAVATION_IMPLEMENTATION.md)을 따른다.

## 구현 경계

### 직접 입력 납부

납부대 조작은 로컬 입력 화면을 열고 금액을 명시해 제출한다. 기존 E 유지·주기별 1원 차감 경로는 입력 화면에서 호출하지 않는다. E 해제와 입력 포커스 전환은 숫자 입력 세션을 취소하지 않으며, 명시 취소·화면 종료·거리나 시야 이탈·사망·출발·연결 종료·불러오기는 세션을 닫는다. 서버가 발급한 세션 ID, 서버가 기억한 납부대, 목표 기간 세대가 일치하는 요청만 제출할 수 있다. 제출 성공 후 세션은 종료하고 같은 요청의 재사용은 거부한다.

소유 PlayerController의 신뢰성 있는 서버 RPC에서 요청 빈도·세션·납부대 종류·Pawn·거리·시야·행동 가능 상태·Base 단계·기간 세대를 다시 검사한 뒤 기존 `RequestDeposit`을 호출한다. `RequestDeposit` 자체는 납부대의 종류·거리·시야를 검사하지 않으므로 이 검사를 생략할 수 없다. 클라이언트는 잔고·목표를 직접 갱신하지 않는다. 입력창이 열린 동안 숫자 슬롯·드롭·저장/불러오기·이동·굴착 등 게임 입력을 차단하고, 창을 닫으면 원래 게임 입력과 커서를 복원한다.

취소·이동·죽음·출발·연결 종료 및 화면 종료에서 점유를 해제하고, 오래된 화면의 제출은 거부한다. 입력창 방치가 납부대를 영구 점유하지 않도록 시험용 세션 만료를 적용한다. 양수 정수 범위와 잔고 초과, 목표 잔여보다 큰 금액, 동시 제출 및 목표 달성 직후의 오래된 요청을 확인한다. 시험 동작은 기존 `RequestDeposit`을 유지한다. 요청액이 잔고보다 크면 거부하고, 잔고 이내인 요청은 목표 잔여분까지만 차감하며 이를 입력 화면에 안내한다. 인정률 100%, 목표·증가량 등은 기존 시험값이며 정식 일차별 인정률이나 이월 정책(D27)을 확정하지 않는다. 개인 금액과 입력 값은 소유자에게만 표시하고 공개 상태는 기존 목표 합계만 이용한다. 공개 합계의 증감으로 개인 납부액을 추정할 수 있는 기존 공개 정책의 한계는 유지하며, 별도 개인 금액 복제·공개 오류·로그를 추가하지 않는다.

### 갱도·학교 이동

시험 미로는 기존 출발 지점에서 직접 걸어 포털에 도달할 수 있고, 귀환 방향과 승강기까지의 경로가 이어져야 한다. 포털은 갱도와 폐교 양방향 한 쌍으로, 기존 `Expedition` 안에서 살아 있고 조작 가능한 플레이어가 서버에서 상호작용한 경우만 이동시킨다. 포털 사용 자체는 새 RunId·일차·화물 지급·탐사 종료를 만들지 않는다. 서버는 대상 종류, 거리·시야, 플레이어 생존·행동 상태, 목적지와 충돌 가능성을 검증한다. 이동 실패 시 원위치·기존 소지품을 보존하고 실패를 알린다. 왕복 목적지는 포털 충돌과 즉시 재진입을 피하도록 배치하며, 다인 동시 이용 시 안전한 대체 위치와 실패 처리를 확인한다.

폐교에 기존 `ADigetherPrototypePickup` 유형의 시험 회수품을 배치해 기존 단일 소유·소지·낙하·승강기 적재·정산 경로를 그대로 사용한다. 매 RunId에 한 번 생성·재설정하고 기존 정리 및 재접속과 충돌하지 않게 한다. 기존 갱도 및 다른 영역의 회수품과 소유권·가치 비공개 경계를 유지한다. 구역 이동을 위해 별도 GameMode, 경제 장부 또는 게임 Phase를 도입할 필요는 없다. 좌표와 구조는 충돌·시야·바닥·문폭·복귀 가능성을 실기 검사한 시험 배치로만 취급한다.

시체 운반도 기존 회수 경로를 유지한다. 포털은 운반자 캡슐과 부착 시체 위치·경로가 안전한 후보만 선택하고, 예약되었거나 부착 관계가 잘못된 시체는 이동시키지 않는다. 도착 방향을 출구 쪽으로 맞추며 기존 상호작용 빈도 제한을 적용한다. 자동 접촉 이동은 없으므로 버튼을 다시 눌러야 왕복한다. 월드 빌더는 항상 관련되도록 설정하고 각 클라이언트에 로컬 씬을 한 번만 생성한다. 학교 재접속과 왕복 후 충돌·가시성은 별도로 확인한다. 시험 빌더의 회전은 0, 스케일은 1이다.

## 검증 계획과 한계

아래는 검증 계약이다. 실제 통과 범위와 미검증은 [프로토타입](PROTOTYPE.md)에 구분한다. 코드와 상태 변경은 [검증 계획](../verification/VERIFICATION_PLAN.md)에 따라 L1~L3 및 M2를 적용한다.

1. UE 5.8.4 빌드와 관련 자동검사 후 실제 게임에서 1인 완주를 확인한다. 출발, 실제 굴착 유지, 포털 양방향 도달, 학교 회수품 획득과 승강기 적재, 정산 금액, 직접 납부와 다음 탐사까지 각 상태를 기록한다.
2. 납부의 0·음수·문자·정수 범위 초과·잔고 초과·목표 잔여 초과, 취소·거리 이탈·출발 경합과 동시 제출을 검사한다. 자기 잔고와 입력 금액이 다른 플레이어에게 공개되지 않는지 확인한다. 입력 중 이동·슬롯·드롭·굴착·저장 키 차단, 종료 후 이동·커서·포커스 복원도 관찰한다.
3. 포털을 멀리서 호출하거나 장애물 뒤에서 호출하는 요청, 사망·관전·운행 중 요청, 도착 위치 막힘·동시 이동·반복 왕복·탐사 시간 종료를 확인한다. 실패 시 위치·소지품·RunId가 보존되고 중복 지급되지 않아야 한다.
4. 동일 PC 별도 4개 프로세스의 호스트와 원격 3인에서 위치·소유권·상호작용·정산 일치를 관찰하고, 탐사 중 동일 ID 재접속을 확인한다. 다른 PC·실제 Steam 외부망은 별도 환경에서 확인하며 로컬 결과로 대체하지 않는다.
5. 씬의 경로를 직접 걸으며 포털 가시성·충돌·학교 출입·화물 운반·승강기 복귀를 확인한다. 생성·배치가 성공한 사실과 렌더 및 플레이 가능성은 별도로 판정한다. 빌더 회전 0·스케일 1 전제는 에디터 MCP와 실행 프로브의 실제 transform으로 확인한다.

자동 실행기는 `scripts/validation/Invoke-MazeSchoolValidation.ps1`와 개발용 프로브를 사용한다. 정상 납부는 제품의 로컬 입력창 함수를 거치고, 잘못된 서버 요청은 실제 RPC로 별도 검사한다. 요청 ACK와 경제 결과는 구분한다. 1인 렌더 완주 및 4인 이동·정산·납부를 각각 검사하며, 남은 탐사 시간을 기록해 실제 맵 시험값 600초 안에서 완료됐는지 확인한다. C++ 기본값 180초와 Blueprint 재정의를 구분하며, 2026-10-29 실행 프로브에서 출발 직후 600초를 관찰했다. 굴착 회귀는 별도 실행기로 수행한다. 작성된 검사와 실제 통과한 검사는 결과 기록에서 구분한다.

정식 절차 생성, 피라미드, 최종 학교 아트·경제 수치 및 플랫폼 실환경은 이 시험 흐름만으로 완료되는 범위가 아니다. 기존 네트워크·저장·정산의 상세 미완료 항목은 [프로토타입](PROTOTYPE.md#기획-대비-구현-한계)을 따른다.
