# 데이터 작업

DataAsset(구성·참조), DataTable(수치 표), DeveloperSettings(프로젝트 설정)는 대표적인 선택지다. 기존 구조·편집 주체·로드 시점·배포와 보안 요구에 따라 프로젝트가 선택하며, 특정 저장 방식을 일괄 강제하지 않는다.
밸런스 수치(소모·충전·속도·피해·시간·거리)를 코드 매직 넘버로 넣지 않는다.
플레이테스트에서 수치 조정이 필요하면 관찰 결과를 기획 변경안으로 제시한다. 운영값은 [Notion 기획 개정·승인 절차](../project/DOCUMENTATION.md)에 따라 확정된 개정을 반영하며 구현에서 조용히 바꾸지 않는다. 실험값은 승인된 실험 범위와 구분해 기록한다.

## 변경 절차

1. 근거가 되는 기획 문서 절과 현재 데이터 행·에셋을 확인한다.
2. 단위(%와 %p, 초/분, 엔진 거리 단위), 범위, 기본값, 참조를 확인한다.
3. 변경 전후 값과 이유를 기록한다.
4. 멀티플레이의 게임 결과는 서버에서 확정하고 필요한 상태만 복제한다. 싱글플레이는 해당 시스템의 상태 소유자가 판정한다. 같은 데이터 파일을 읽는다는 사실만으로 런타임 상태 동기화가 보장되지는 않는다.
5. 경계값·잘못된 데이터·공유 자원 경합을 검증한다. 경계값과 무결성은 자동 테스트로 고정한다.

## 무결성

- 같은 정보를 두 표에 두지 않는다. 한 표를 원본으로 정하고 나머지는 참조한다.
- 중복 ID, 범위 초과, 없는 참조, 그래프 불일치를 로드 시점이나 에디터 검사로 잡는다. 오류를 드러내고, 시작 차단·해당 기능 비활성화·명시된 기본값 중 프로젝트가 정한 복구 정책을 따른다. 조용히 성공한 것처럼 넘기지 않는다.
- CSV·JSON 등을 임포트한다면 편집 원본을 하나로 정하고 문자 인코딩·행 ID·스키마와 재임포트 후 값을 확인한다. 에셋을 다시 열어 참조와 대상 cook 포함 여부도 검사한다.
- 문서에 적힌 데이터 에셋 이름은 계획일 수 있다. 실제 파일이 있는지 따로 확인한다.

## 영구 저장

런 중 상태와 달리 디스크에 남는 데이터는 버전 간 호환을 관리한다.
스키마 버전, 구버전 읽기, 미래 버전 파일, 손상 파일, 저장 실패를 처리한다.
실제 사용자 세이브를 덮어쓰며 시험하지 않고 임시 경로를 쓴다.
저장 중 중단·용량 부족·권한 오류에서 마지막 정상 데이터를 보존하는 경로를 정하고 검증한다. 임시 파일 교체·백업 등 복구 방식은 대상 플랫폼의 저장 API에 맞춰 선택한다.
마이그레이션 전 원본을 보존하며, 미래 버전·손상 파일을 읽지 못했다고 기본 세이브로 덮어쓰지 않는다. 사용자에게 보일 오류와 재시도·복구 정책은 프로젝트가 정한다.
