# DIGETHER 커밋 규칙과 Gitflow

확정일: 2026-10-27. 사용자 요청으로 채택한 프로젝트 규칙이다. 커밋 메시지·브랜치 흐름은 이 문서를 단일 기준으로 삼는다. 작업 권한과 파일 안전은 [AGENTS.md](../AGENTS.md), 검증과 파일 분류는 [개발 흐름](project/DEVELOPMENT_WORKFLOW.md)을 따른다.

## 커밋 메시지

```text
<타입>: <변경 결과>

<변경 이유와 필요한 검증·제약>
```

- 제목과 본문은 한국어로 작성한다. 타입, 코드 식별자, 파일명은 원래 표기를 유지한다.
- 제목은 50자 안팎의 한 줄로 쓰며 끝에 마침표를 붙이지 않는다. `추가`, `수정`, `변경`, `제거`처럼 결과가 드러나게 쓴다.
- 본문은 이유나 제약 설명이 필요할 때 작성하고 제목과 빈 줄로 구분한다. 수행하지 않은 검증을 통과로 적지 않는다.
- 관련 이슈가 있으면 마지막에 실제 `#번호`를 적는다. 번호를 만들지 않으며 이슈 종료 연결은 PR 본문에서 한다.

| 타입 | 용도 |
|---|---|
| `feat` | 새로운 기능·동작 |
| `fix` | 결함 수정과 재발 방지 |
| `refactor` | 동작을 유지하는 구조 개선 |
| `docs` | 문서 변경 |
| `chore` | 빌드·도구·설정·외부 에셋 도입·의도한 밸런스 조정 |

타입은 소문자로 쓰고 스코프 괄호는 사용하지 않는다. 새 타입은 이 문서를 먼저 갱신한 뒤 사용한다. 기능과 관련 테스트·문서는 기능의 타입으로 함께 묶는다. 승인 기획과 다른 수치를 바로잡는 변경은 `fix`다.

```text
feat: 회수품을 엘리베이터에 적재하는 기능 추가
fix: 중복 납부 요청으로 잔액이 두 번 차감되는 문제 수정
docs: 한국어 커밋 규칙과 Gitflow 전략 명시
chore: Unreal 생성물 제외와 에셋 LFS 설정
```

## 커밋 단위와 작성자

- 하나의 목적을 이루는 변경만 묶고 관련 없는 작업은 분리한다. 다른 작업자의 변경을 함께 stage하지 않는다.
- Unreal 에셋·맵과 필요한 참조·설정 변경은 일관된 단위로 포함한다. `.uasset`·`.umap`은 LFS 대상이며 바이너리 병합을 전제하지 않는다. 생성물·개인 설정·비밀값은 제외한다.
- `Co-authored-by:` 트레일러는 대소문자와 관계없이 넣지 않는다. AI 도구가 자동 추가하는 공동 작성자나 생성 도구 서명도 넣지 않는다.
- 실제 Git 작성자 설정을 사용한다. 공동 작성자 제거를 위해 author를 다른 사람이나 AI로 바꾸지 않는다.
- 커밋 전 메시지와 staged diff를 확인하고, 커밋 후 `git log -1 --format=%B`로 한국어 메시지와 트레일러 부재를 확인한다.
- 기존 이력의 amend·rebase·강제 푸시는 이 규칙만으로 승인되지 않는다. 이미 공유된 메시지는 유지하고 이후 커밋부터 적용한다. 공유 전 이력 수정도 사용자 요청 범위를 확인한다.

## Gitflow 브랜치

| 브랜치 | 역할 | 분기 기준 | 반영 대상 |
|---|---|---|---|
| `main` | 출시 기준 이력 | 기존 기준 브랜치 | release·hotfix 병합만 수용 |
| `develop` | 다음 버전 개발 통합 | 최초 도입 시 현재 main | feature·release·hotfix 통합 |
| `feature/<사람 이름>` | 담당자별 기능·일반 수정·문서·도구 작업 | develop | develop |
| `release/<버전>` | 출시 후보 안정화·검증 | develop | main과 develop |
| `hotfix/<주제>` | 출시 버전의 긴급 수정 | main | main과 develop |

feature 브랜치는 사람 이름으로 만들며 정확한 이름은 사용자가 지정한다. 현재 지정된 브랜치는 `feature/minsung`이다. AI는 작업 주제·이슈 번호를 붙여 feature 브랜치를 임의 생성하거나 이름을 추정하지 않는다. 이슈와 작업 구분은 커밋·PR에 기록한다. 브랜치명과 코드 식별자는 지정된 원래 표기를 유지한다.

1. 현재 브랜치·변경 파일·기준 이력을 확인한다. 미커밋 작업을 자동 삭제하거나 다른 작업에 섞지 않는다.
2. develop에서 사용자가 지정한 사람 이름의 feature 브랜치를 만들거나 기존 담당자 브랜치를 사용한다. 새 브랜치 생성은 사용자 요청 범위를 확인하며 문서 작업도 같은 흐름을 따른다. main과 develop에 직접 작업 커밋하지 않는다.
3. 해당 변경을 검증하고 한국어 메시지로 커밋한다. 푸시·PR·병합은 사용자가 승인한 작업 범위에서 수행한다.
4. feature는 develop으로 PR을 보낸다. release는 안정화 후 main에 병합하고 같은 수정 사항을 develop에도 반영한다.
5. hotfix는 main에서 시작해 main과 develop 양쪽에 반영한다. 진행 중인 release가 있으면 그 브랜치에도 수정 사항을 반영해 누락을 막는다.
6. 출시 승인 후 main의 출시 커밋에 버전 태그를 붙인다. 실제 버전·출시 시점·승인 담당은 임의로 정하지 않는다.

PR 제목과 squash 메시지도 한국어 커밋 형식을 따른다. Git/GitHub가 자동 생성한 병합 메시지는 형식 검사 예외로 허용하되, 직접 작성하는 병합 설명은 한국어로 쓴다. 원격 보호 규칙·리뷰 승인 수·병합 방식은 별도 설정이며 문서 채택만으로 서버에서 강제되지 않는다.

## 도입 상태

2026-10-27 로컬 develop이 있으며, 사용자 지정에 따라 작업 브랜치를 `feature/minsung`으로 정정했다. 같은 날 사용자가 기존 커밋 전체의 한국어 메시지 수정을 명시 요청했다. 파일 내용은 보존하고 로컬 이력의 메시지를 수정하며, 원격 이력 갱신은 별도 요청 없이 수행하지 않는다. 기존 main의 커밋을 출시 검증 완료로 간주하지 않는다. 원격 develop 생성, 브랜치 보호, PR·병합·출시 태그는 미실행이다.

shinshi의 `docs/commit-convention.md`에서 메시지 형식·커밋 단위·AI 트레일러 제외 원칙을 참고했다. 사람별 feature 브랜치는 사용자 결정에 맞춰 적용하며 Unity 전용 규칙은 DIGETHER의 Unreal 운영에 맞췄다.
