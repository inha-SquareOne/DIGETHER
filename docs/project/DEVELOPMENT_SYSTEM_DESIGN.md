# DIGETHER 개발반 기능 구현 설계

작성일: 2026-10-25 · 상태: **구현 전 설계 제안** · 개발/통합/리뷰 담당: 미정.

이 문서는 개발반이 무엇을 만들고 어떤 경계로 연결할지 설명한다. 기준 기획은 2026-10-23의 [Notion 이관 전 게임 기획 초안](notion/GAME_DESIGN.md) DG-001~019다. 등록된 Notion 원본 URL과 승인 개정이 없으므로 최신 온라인 기획을 확인한 문서가 아니다. 구현 착수 시 승인된 요구 개정을 연결해야 한다. UE 5.8.2는 확정 기준이며 아래 클래스 배치·데이터 형식·진행 순서는 채택 검토를 위한 제안이다. 작성 당시 프로젝트가 없었다. 2026-10-27 현재 Third Person 템플릿 파일은 [프로필](PROJECT_PROFILE.md)에 기록하며, 아래 게임 시스템 구현·실행 검증과 구분한다.

Unreal이 제공하는 기반, 지원 근거, 개발반의 추가 구현과 최소 적용 절차는 [Unreal 기능 활용 범위](UNREAL_FEATURE_COVERAGE.md)를 함께 읽는다. 이 문서의 논리 서비스명과 계약명은 존재하는 엔진 API가 아니다. 전체 책임 개요는 [기술 구조 초안](ARCHITECTURE.md), 미결 게임 규칙은 [결정 대기](notion/DECISIONS.md)가 원본이다.

## 1. 개발반이 만드는 결과물

개발반은 입력·캐릭터·물리·복제·AI·UI 같은 엔진 기반에 DIGETHER의 굴착, 운반, 정산, 비공개 납부 및 4일 주기를 연결한다. 콘텐츠 제작자는 규격에 맞춘 맵·메시·재질·애니메이션·효과를 공급하고, 개발반은 해당 콘텐츠가 게임 상태와 연결되어 1~4인에서 동일하게 동작하도록 구현한다. 실제 사람별 업무 배정은 [작업 경계](PROJECT_BOUNDARIES.md)에서 합의한다.

| 구현 묶음 | 연결 요구 | 개발반 산출물 | 기획·아트에서 받을 것 | 검증 연결 |
|---|---|---|---|---|

| 생존·구출 | DG-005, DG-015 | 깔림/피해/사망 상태, 구출 작업, 시체 식별 | 피해·솔로·부활/전원 사망 규칙, 연출 | VT-03, VT-08, VT-11 |

## 2. 상태 소유와 Unreal 배치 제안

처음부터 기능별 플러그인 여러 개를 만드는 대신 하나의 게임 모듈 안에서 책임을 구분하는 방안을 우선 검토한다. 실제 모듈명·폴더·클래스명은 프로젝트 생성 시 결정한다. 월드 이동 방식이 정해지기 전에는 어떤 Actor가 맵 이동 뒤 살아남는다고 가정하지 않는다.

| 상태/책임 | 엔진 배치 후보 | 수명과 전달 범위 | 주의점 |
|---|---|---|---|
| 접속 UI·로컬 세션 요청 | GameInstance 계열 서비스 | 로컬 프로세스/게임 인스턴스 | 복제 원본으로 쓰지 않는다. 클라이언트 지갑 원본을 두지 않는다 |
| 런 시작·종료 판정 | GameMode 계열 | 서버 월드 | 클라이언트가 직접 접근하는 UI 데이터 저장소가 아니다 |
| 공개 진행 단계·일차 | GameState 계열 | 월드, 참여자에게 허용된 상태만 복제 | 공개 누적 납부액은 D-008 승인 전 추가하지 않는다 |
| 플레이어 식별·공개 생존 상태 | PlayerState 계열 | 접속 플레이어; 전환 시 보존은 별도 계약 | PlayerState에 넣었다고 비공개가 되지 않는다 |
| 입력·서버 상호작용 요청 | PlayerController 또는 소유 Character의 복제 컴포넌트 | 소유 연결/빙의 수명 | 공유 월드 액터로 직접 Server RPC를 보내는 구조를 전제하지 않는다 |
| 이동·깔림·구출 표현 | Character와 책임별 컴포넌트 | 현재 Pawn | Pawn 파괴로 지갑·정산 기록이 소실되지 않게 분리한다 |
| 개인 지갑·거래·은닉 원본 | 서버 전용 장부; 같은 월드 객체 또는 서버 GameInstanceSubsystem 후보 | 실행 중 주기에 필요한 상태는 런/일차 전환 너머 유지. 주기 종료·재접속·영구 보존은 D-003/004/008 | 소유자에게 필요한 뷰만 별도 전달한다. 서비스 자체가 복제를 제공하는 것은 아니다 |
| 지형·생성·아이템 레지스트리 | 월드 서비스와 필요한 복제 Actor | 현재 런/월드 | 월드 서비스의 내부 메모리는 자동 복제되지 않는다. 명시적 상태 전달 계층이 필요하다 |
| 회수품·보강물·트랩·몬스터 | Actor/컴포넌트 | 생성부터 제거까지, 관련 수신 대상 | 단순 시각 파편과 권위 있는 장애물을 구분한다 |
| 수치·콘텐츠 정의 | 데이터 자산/테이블 후보 | 콘텐츠 버전 | 런에서 변한 지갑/내구도를 정의 자산에 기록하지 않는다 |
| UI·음향·효과 | 로컬 Widget·표현 컴포넌트 | 화면/표현 객체 수명 | 서버 규칙 계산은 Widget·오디오의 존재에 의존하지 않는다 |

권위 로직, 거래 원자성, 요청 검증은 C++ 중심으로, 콘텐츠 조합·애니메이션·효과·UI는 Blueprint 중심으로 검토한다. 단순 콘텐츠 이벤트까지 일괄 C++화하지 않는다. `Gameplay Ability System` 등의 도입은 엔진 활용 문서의 후보 평가 후 정하며, 상태가 있다는 이유만으로 필수 의존성을 추가하지 않는다.

### 공통 요청과 결과 흐름

1. 클라이언트가 입력과 대상 후보를 만든다. 로컬 Trace 결과는 조작 보조이며 판정 근거가 아니다.
2. 소유 연결의 유효한 RPC 경로로 행위 의도·대상 ID·현재 런/버전·요청 ID를 보낸다.
3. 서버가 호출자 식별, 허용 단계, 거리/시야/도구, 대상 존재, 값 범위, 호출 빈도, 중복을 검사한다. 비용·가격·피해·소유자 결과는 서버 데이터에서 계산한다.
4. 서버가 관련 상태를 검증하고 한 번에 확정한다. 실패 시 일부 상태만 변경하지 않는다. 비동기 작업은 준비와 확정을 분리한다.
5. 요청자에게 성공 또는 안전한 실패 이유를 반환하고, 다른 참여자에게는 허용된 상태만 복제한다. 실패 응답으로 은닉 아이템이나 다른 사람의 잔액을 노출하지 않는다.
6. 클라이언트는 확정 상태와 버전을 적용한다. 지속 상태를 Multicast 이벤트만으로 구성하지 않는다. 늦게 생성된 UI와 리슨 호스트도 현재 상태를 적용할 수 있어야 한다.

논리 오류 코드 후보는 `InvalidPhase`, `InvalidTarget`, `OutOfRange`, `StaleRevision`, `Busy`, `InsufficientResource`, `AlreadyProcessed`다. 실제 네트워크 형식은 구현 시 정의한다. 서로 다른 Actor의 도착 순서에 의존하지 않도록 필요한 상태 버전과 준비 조건을 둔다.

### 복제 규모와 대역폭

회수품·잔해·보강물·트랩이 런마다 많이 생길 수 있으므로 모든 대상을 항상 복제하는 구조를 기본으로 두지 않는다. 대상별로 다음을 정한다.

| 대상 | 정할 것 | 엔진 후보(로컬 5.8.2 `Actor.h` 확인) |
|---|---|---|
| 정지한 회수품·보강물 | 변경이 없을 때 휴면, 상태 변경 직전 깨우기 | `SetNetDormancy`, `FlushNetDormancy` |
| 먼 지역의 대상 | 거리 기준 수신 범위; 지형으로 막힌 공간의 관련성 | `SetNetCullDistanceSquared`, `IsNetRelevantFor`(Legacy 복제 경로) |
| 갱신 빈도 | 이동 중/정지 대상의 갱신 주기 차등 | `SetNetUpdateFrequency` |
| 소유자 전용 대상 | 개인 뷰 전달 Actor 한정 | `bOnlyRelevantToOwner`, `bNetUseOwnerRelevancy` |
| 연출 파편 | 권위 상태와 분리해 복제하지 않거나 사건 ID로 로컬 재생 | 해당 없음 — 4절 붕괴 결과 구분 |

휴면·관련성으로 수신이 끊긴 클라이언트가 다시 범위에 들어올 때 최신 상태와 버전을 받는지 검사한다. 비공개 정보는 관련성 제외에 의존하지 않고 6~7절의 소유자 뷰로 보호한다. Iris를 채택하면 관련성·필터 구성이 Legacy와 달라지므로 [기능 경계 4절](UNREAL_FEATURE_COVERAGE.md#4-채택-전에-남길-증거)의 복제 시스템 기록과 함께 다시 확인한다. 실제 대상 수·대역폭 목표는 D-011, 측정은 VT-12에서 한다.

## 3. 접속·런·일차 흐름

연결 요구: DG-001, DG-014. 서버 방식·세션 제공자·후입·재접속·호스트 종료는 D-003/004 결정 대상이다.

세션 서비스는 검색/참가/종료와 연결 실패를 처리하고, 런 진행 서비스는 참가자가 게임 규칙상 어떤 행동을 할 수 있는지 처리한다. 플랫폼 계정 ID와 런 내부 플레이어 ID의 매핑을 명시하며 클라이언트가 보낸 ID로 다른 플레이어의 지갑을 선택하지 못하게 한다.

| 논리 단계 제안 | 진입 시 작업 | 전환 조건/정리 |
|---|---|---|
| 준비 | 승인된 장비 구매, 참가 준비 확인 | 시작 조건은 기획 확인. 월드/콘텐츠 준비 실패 시 탐사로 넘기지 않음 |
| 탐사 | 지형·아이템·몬스터 초기화, 런 ID 활성화 | 탈출 또는 종료 규칙 승인 후 전환. 전원 사망을 임의로 정상 탈출 처리하지 않음 |
| 탈출 확정 중 | 선택 적재 목록·관련 상태 버전 고정, 충돌하는 요청 차단 | 확정 전 실패는 예약 해제. 확정 뒤 정산 재호출은 같은 결과를 사용 |
| 정산 | 확정 목록으로 개인 귀속 계산, 처리 영수증 기록 | 모든 대상의 결과가 확정된 뒤 후속 단계 허용 |
| 상점·납부 | 구매·납부 거래 허용, 창구 점유 관리 | 마감 규칙에 따라 신규 거래를 닫고 진행 중 거래 정리 |
| 일차/주기 판정 | 현재 일차와 승인 효율·할당량 적용 | DG-014의 성공·실패 분기는 D-008 검토 후 활성화 |
| 게임 오버 | 승인된 초기화 범위 적용 | 재시작·종료 정책은 D-008 결정 전 구현 확정 금지 |

이는 논리 단계 제안이며 각 단계마다 별도 맵을 만들라는 의미가 아니다. 맵 전환을 채택하면 필요한 상태를 명시적으로 직렬화·이관하고 수신 월드의 준비가 끝난 뒤 플레이를 연다. `GameInstance`의 존재만으로 서버/클라이언트 사이 데이터 이관이 해결되지는 않는다.

이 표는 **1런=1일을 확정하지 않는다**. 런 종료·정산과 일차 마감은 서로 다른 사건으로 두고, 어떤 사건이 일차를 넘기는지는 D-008의 런/일차 경계 결정 뒤 연결한다. 실행 중 4일 주기의 지갑·일차·할당량·납부 원장·중복 방지 기록은 필요한 후속 단계까지 유지해야 한다. 이는 영구 저장 도입 여부와 별개이며 사망 손실 등 승인된 규칙에 따른 갱신을 막는다는 뜻이 아니다.

맵 이동을 하지 않으면 동일 서버 월드의 장부를 유지할 수 있다. 맵 이동을 하면 서버 GameInstanceSubsystem에 월드 Actor 포인터가 없는 데이터로 보관하고 새 월드에 명시적으로 연결하는 방안을 비교한다. 이 서브시스템은 클라이언트에도 존재하고 세션 종료 뒤에도 남을 수 있으므로, 서버 권한일 때만 장부를 활성화하고 세션·주기 ID에 따라 초기화·정리한다. 다른 후보는 seamless travel의 `bUseSeamlessTravel`/`GetSeamlessTravelActorList`와 PlayerState의 `CopyProperties`/`SeamlessTravelTo`를 사용한 필요한 상태 이관이다. 자동 보존 범위와 전환 목적지에서의 객체 생성을 확인해야 하며, non-seamless 이동에 같은 보존을 가정하지 않는다. 재접속을 허용하면 `AGameMode`의 `InactivePlayerArray`/`InactivePlayerStateLifeSpan`과 PlayerState 복사·복원 기능도 후보지만, 이는 GameModeBase 자체의 기능이 아니며 재인증·비공개 장부·영구 복구를 자동 해결하지 않는다. 관련 엔진 근거는 [엔진 기능 안내 E16](UNREAL_FEATURE_COVERAGE.md)에 둔다.

후입을 허용하면 현재 런·지형 스냅샷·아이템·일차의 기준 버전을 먼저 맞추고 이후 차이를 적용해야 한다. 허용하지 않으면 게임플레이 진입 전에 이유와 함께 거부한다. 재접속 시 소유권 복원·미결 거래·히든 슬롯 복원 범위도 정책이 필요하다. 호스트 승계·관전·런 제한시간은 현재 필수 기능으로 추가하지 않는다.

검사: VT-01/07/11. 1인 및 2~4인 접속, 연결 취소, 중복 시작/종료, 로딩 실패, 단계 전환 중 구매/납부, 정책상 후입 허용/거부를 검사한다.

## 4. 굴착·생성·붕괴·보강

연결 요구: DG-002~004, DG-006~008. 핵심 미결은 D-005이며 지형 표현을 확정하기 전에 동일한 짧은 갱도에서 후보를 비교한다.

| 방식 후보 | 적합한 요구 범위 | 개발반이 검증할 비용 |
|---|---|---|
| 미리 만든 파괴 구간/블록 | 정해진 단위로 벽·통로 제거 | 굴착 자유도 충족 여부, 많은 조각·Actor 비용, 연결/충돌 전환 |
| 셀/청크 기반 가변 지형 | 연속적 굴착과 국소 수정 | 메시/충돌 재생성, 청크 경계, 복제량, 내비게이션 갱신 |
| 외부 지형 플러그인 | 후보가 제공하는 지형 변형 | 실제 UE 5.8.2 호환, 런타임·서버·패키징·라이선스, 저장/동기화 지원 범위 |

Chaos 파괴 연출, PCG 배치, 메시 편집 기능이 각각 게임의 굴착 전체를 해결한다고 간주하지 않는다. 상세 지원 범위와 공식 근거는 엔진 활용 문서에서 확인한다.

### 지형 수정 계약

지형 서비스의 논리 데이터는 `RunId`, `RegionId`, `Revision`, 파괴 가능 구간/셀, 보강 참조, 붕괴 상태를 갖는다. 형태는 선택한 지형 방식에 맞춘다. 플레이어 요청에는 결과 메시 전체를 받지 않고 행위·위치·도구 정보를 받아 서버가 허용된 변경을 계산한다.

서버는 CT-DIG를 검증한 뒤 변경 준비 → 충돌 준비 → 권위 상태 확정 → 시각/경로 갱신을 조정한다. 비동기 충돌 생성 중인 구간은 통행 가능으로 먼저 발표하지 않는다. 충돌 생성 실패 시 기존 유효 상태를 유지하거나 해당 수정 요청을 실패 처리하는 기술 정책을 정한다. 결과 버전이 바뀐 작업의 늦은 완료가 최신 구간을 덮어쓰지 않게 한다.

클라이언트는 지역 버전 기준으로 차이를 적용한다. 버전 공백이면 해당 지역의 현재 상태를 다시 받는다. 동일 시드만 전달해 모든 기기에서 동일 메시·충돌·아이템 배치가 만들어진다고 가정하지 않는다. 필요하면 서버가 생성 결과나 검증 가능한 구조 데이터를 전달한다. 재동기화 방식의 패킷 크기와 처리 예산은 측정으로 정한다.

### 여진과 보강

여진 서비스는 굴착된 대상 지역과 승인된 진행 기준으로 다음 예고/붕괴 사건을 서버에서 예약한다. 사건 ID와 서버 시간 기준으로 표현하며 클라이언트 타이머가 붕괴 결과를 결정하지 않는다. “후반일수록 간격 감소”의 후반 기준과 수치는 D-005에서 받아 데이터로 둔다.

보강 설치는 위치·재료·중복·효력 범위를 검증한 뒤 자원 차감과 설치를 함께 확정한다. 보강 철거·파괴·내구도 규칙은 미결이며 임의 추가하지 않는다. 보강 설치와 붕괴가 같은 시점에 도착하면 서버가 직렬화한 현재 상태에 승인 규칙을 적용하고, 클라이언트 시간만으로 승패를 고르지 않는다.

붕괴 결과는 권위 있는 막힘/피해 영역과 연출 파편으로 구분한다. 물리 파편의 기기별 접촉 차이가 깔림 판정을 바꾸지 않게 서버에서 대상과 상태 전이를 확정한다. 실제 플레이어를 가두는 잔해는 서버 판정과 일치하는 충돌·구출 대상 ID를 가져야 한다.

### 생성과 던전 연결

생성기는 입구·귀환점·포탈·방 연결·파괴 가능 구간을 포함한 논리 구조를 먼저 만들고 유효성을 검사한 뒤 콘텐츠를 배치한다. 연결 불능 또는 허용 조건 위반 시 제한된 재시도/실패 보고를 사용하고 무한 생성 재시도는 피한다. 재시도 한도와 대체 맵 도입 여부는 기술 검증 후 정한다.

폐교와 피라미드는 동일한 진입/귀환 계약에 각각 콘텐츠 정의를 제공한다. 포탈은 대상 준비 → 이동 예약 → 목적지 유효성 확인 → 이동 확정 순서로 설계한다. 실패 시 원래 유효 위치를 유지하고 회수품·플레이어를 중복 생성하지 않는다. 같은 월드 이동인지 맵 이동인지는 아직 미결이다.

검사: VT-02/09/12/13. 동시 굴착, 청크 경계, 보강과 붕괴 경합, 충돌 실패, 생성 연결성, 포탈 중복 접촉, 지형 변경 후 AI 경로, 4인 동시 수정 비용을 관찰한다. 갇힘 복구 규칙은 D-006 승인 후 검사한다.

## 5. 깔림·구출·사망·시체

연결 요구: DG-005, DG-015. 서버 생존 상태 후보는 `활동 가능`, `깔림`, `사망`이다. 기절은 현재 요구에 없고 회복·부활은 D-006 미결이므로 현재 상태 모델에 확정하지 않는다. 체력 수치가 있는지, 몬스터·트랩·깔림 피해가 같은 체력에 누적되는지도 D-006 결정 대상이다. 구현은 피해 출처·사건 ID·적용량을 서버에서 한 경로로 처리하는 피해 적용 지점을 두어 체력 모델 유무와 관계없이 중복 피해를 막는다. Character의 이동 제한은 서버 상태에서 적용하고 클라이언트 입력 차단만으로 처리하지 않는다.

깔림은 원인 잔해 ID, 상태 버전, 피해 적용 기준을 기록한다. 지속 피해는 서버 시간 기준으로 적용하고 중복 타이머/붕괴 이벤트가 피해를 중복 시작하지 않게 한다. 수치는 D-006 승인 데이터에서 받는다.

구출 CT-RESCUE는 구조자·대상·잔해의 현재 상태와 거리·도구를 검사한다. 동료가 잔해를 파내는 진행은 서버의 유효 굴착 결과와 연결하며, 단순 클라이언트 완료 메시지로 해제하지 않는다. 구조자 이탈·도구 변경·대상 사망·잔해 제거에서 작업을 취소/종료하고 예약을 정리한다. 사망이 확정된 뒤 늦게 온 구출 완료가 대상을 되살리지 못하게 상태 버전을 검사한다.

사망 거래는 논리 `DeathId`로 한 번만 실행한다. 사망 직전 확정 지갑 스냅샷과 손실 기록을 서버에서 연결하고, 시체는 해당 사망 ID를 참조한다. 복구율·귀속 대상·조건·공개 범위는 D-008 승인 전 보류한다. 복구를 구현할 때는 동일 시체 재회수와 사망 이벤트 중복에도 한 번만 반영해야 한다. 클라이언트에 복구 원금이 꼭 필요한지 별도로 검토한다.

검사: VT-03/08/11. 구출 완료와 사망 경합, 구조자 이탈, 잔해 제거 후 중복 완료, 반복 시체 접촉, 사망과 구매/정산 경합. 1인 깔림·전원 깔림·전원 사망은 D-006 결정 전 최종 규칙과 통과 기준을 확정하지 않는다.

## 6. 회수품·운반·히든 슬롯·탈출

연결 요구: DG-009~011, DG-017. 아이템 정의는 안정적인 정의 ID와 무게·가치·표현 참조를 갖고, 런타임 인스턴스는 별도 고유 `ItemId`와 상태 버전을 갖는다. Actor 포인터를 영구 식별자로 사용하지 않는다.

소유 상태는 예를 들어 `월드`, `플레이어 운반`, `히든 슬롯`, `엘리베이터 적재`, `정산 완료`로 구분한다. 이 이름은 구현 모델 제안이며 실제 운반 방식과 은닉 규칙은 D-007에서 받는다. 한 ItemId는 한 순간에 하나의 유효 보관 위치만 가진다는 불변식을 지킨다.

CT-ITEM은 서버가 현 소유 위치·대상 상태·거리·용량을 확인한 뒤 이전 보관 위치에서 제거하고 다음 보관 위치에 넣는 작업을 함께 확정한다. 두 플레이어가 동시에 획득하면 하나만 성공한다. 시각 Actor가 늦게 제거되어도 아이템 상태 버전이 이미 바뀌었으면 재획득을 거부한다.

운반이 손 부착형이면 Attach/Detach와 충돌 전환을 연결하고, 물리 운반형이면 잡기 제약·서버 물리·원격 보정 비용을 검증한다. 어느 방식을 채택할지는 D-007 결정과 프로토타입 결과에 따른다. 아이템 무게 합산은 서버의 승인 데이터와 보관 목록으로 계산하고 클라이언트가 보낸 합계를 신뢰하지 않는다.

엘리베이터는 중량 산정 대상과 적재 목록의 기준 시점을 갖는다. 탈출 요청 시 목록/중량/조건을 함께 검증하고 정산용 명세를 고정한다. 고정 중 들어온 놓기·집기·이탈은 승인된 정산 귀속 규칙과 상태 잠금으로 처리한다. 물리 Overlap만을 유일한 소유권 장부로 사용하지 않는다. 한도 초과 시 결과는 D-007 결정 전 임의로 아이템 삭제나 강제 탈출로 정하지 않는다.

히든 슬롯 상세는 서버와 허용된 소유자에게만 전달하는 뷰를 설계한다. 월드 Actor 숨김만으로 이미 복제된 정보를 회수할 수 있다고 가정하지 않는다. 은닉 전환 시 관련 Actor·인벤토리·UI·로그의 정보 경로를 함께 검사한다. 중량 표시와 아이템 사라짐 자체로 추론 가능한 범위는 D-007에서 합의한다.

보유자 사망·이탈·일부 인원 미탑승 탈출에서 운반품/히든 슬롯을 드롭·소멸·시체 귀속·유지할지는 D-006/007/008에 추가한 질문으로 결정한다. 구현 모델에는 보유자 Pawn·연결·탑승 자격이 사라져도 ItemId와 비공개 장부가 남는 서버 내부의 `처리 대기` 전이를 준비한다. 이는 최종 게임 규칙이 아니라 중복 지급·자동 공개를 막는 기술 경계이며, 정책 미결 상태에서 해당 분기를 플레이 가능한 완성 기능으로 출시하지 않는다. Pawn 파괴와 장부 삭제를 결합하지 않고, 승인 규칙으로 한 번만 다음 보관 상태에 확정한다. VT-04/08/10에서 사망·이탈·미탑승 후 소유권과 은닉 노출을 검사한다.

검사: VT-04/05/10. 동시 획득, 운반자 이탈, 은닉과 탈출 경합, 적재 경계 진입/이탈, 정산된 아이템 재사용, 다른 클라이언트 데이터의 은닉 정보 노출을 확인한다.

## 7. 개인 경제·상점·비공개 납부

연결 요구: DG-011~015. 경제 서비스가 정산·구매·납부·사망 손실·시체 복구를 같은 플레이어 장부에서 직렬화한다. UI마다 지갑 값을 직접 수정하는 구조는 피한다.

금액의 저장 표현은 승인된 최소 화폐 단위가 정해진 뒤 정수형을 우선 검토한다. 일차별 납부 효율을 곱한 결과의 단위·반올림은 D-008 결정 대상이다. 중간 계산 범위와 오버플로 검증을 정의하고, 음수·0·잔액 초과·비정상 큰 입력의 허용 여부를 명확히 한다.

| 거래 | 입력/검증 | 한 번에 확정할 상태 | 중복·실패 경로 |
|---|---|---|---|
| CT-SETTLE 정산 | 서버가 고정한 런/탈출 명세, 귀속 규칙 | ItemId 소비 표시, 개인 지갑 증가, 영수증 | 같은 런/물건 재요청은 재지급하지 않음. 귀속 불명확하면 임의 분배하지 않음 |
| 구매 | 상품 ID, 수량, 허용 단계·재고/소지 조건 | 잔액 차감, 장비 인스턴스 ID 발급/소유 기록, 영수증 | 장비 생성/적재 준비 실패 시 차감만 남기지 않음 |
| CT-PAY 납부 | 창구 점유, 금액, 일차/단계 버전, 잔액 | 개인 차감, 비공개 납부 원장, 할당량 반영 | 구매와 동시 요청을 같은 장부에서 순서대로 처리 |
| 사망 손실 | DeathId, 현재 확정 잔액, 적용 자산 범위(납부 완료 재화·장비 포함 여부는 D-008) | 지갑 손실, 사망 스냅샷, 처리 기록 | 동일 사망 재전달로 재손실하지 않음. 납부 원장은 승인 전 손실 대상에서 임의로 차감하지 않음 |
| 시체 복구 | DeathId, 승인된 회수 조건·귀속 | 복구 지급, 시체 복구 완료 표시 | 시체 중복/동시 회수에서 한 번만 지급 |

구매 장비는 회수품과 같은 인스턴스 ID·단일 보관 위치 불변식을 따르되, 정산 대상인지 여부를 정의 데이터로 구분한다. 장비가 사망·일차 전환·게임 오버에서 유지·손실되는지, 다른 플레이어에게 넘길 수 있는지, 중량에 포함되는지는 D-007/008 결정 대상이다. 결정 전에는 장비 보존을 런 상태에 묶지 않고 플레이어 장부 쪽에서 참조할 수 있게 두어 어느 규칙이든 적용할 수 있게 한다. 시체 복구 시점(접촉 즉시/정산 시 등)도 D-008에서 받으며, 시점과 무관하게 같은 DeathId로 한 번만 지급한다.

요청 ID만 같으면 무조건 성공을 반환하지 않는다. 서버는 호출자·거래 종류·대상·내용과 연결된 처리 기록을 확인하고 동일 ID의 변조된 입력을 거부한다. 영수증 보존 수명은 런/주기/재접속 정책과 맞춘다. 메모리 내 중복 방지는 서버 재시작 후 복구를 보장하지 않는다. 영구 저장이 승인되면 장부 저장과 복구의 원자성도 별도 설계한다.

납부 창구는 “한 번에 한 명”을 물리적 장소로 표현하는 구현 후보이며 기획 확정이 아니다(D-008). 공통으로 서버 점유 토큰과 소유 연결을 사용하고 취소·연결 해제·일차 마감에서 점유를 해제한다. 물리 창구를 채택할 때만 거리 이탈 검사를 추가한다. 이전 토큰의 늦은 제출을 거부하고, 점유 만료 규칙과 제한시간은 별도 승인/기술 검토 후 정한다.

일차 마감 CT-DAY는 신규 거래를 닫고 처리 중인 거래를 확정/실패 처리한 다음 기준 장부로 판정한다. 중복 마감 호출은 같은 판정 결과를 사용한다. 4일차 100%와 다른 일차 효율, 성공 상향·실패 게임 오버·초기화 범위는 원본 요구와 D-008 상태를 따른다.

### 개인 정보 전달 경계

개인 납부액·기여도는 다른 클라이언트에 보내지 않는다. 지갑·시체 복구액·히든 슬롯의 세부 공개 수준은 D-007/008에서 결정한다. 공개 합계가 매 거래마다 정확히 바뀌면 개인 납부액을 역산할 수 있으므로 합계 공개 범위·표시 주기·정밀도를 기획과 함께 결정한다. UI에서 숫자를 감추는 것만으로 해결하지 않는다.

로그·디버그 HUD·채팅 메시지·오류 응답에도 개인 정보가 새지 않는지 확인한다. 리슨 서버를 채택하면 호스트 프로세스에 권위 장부가 존재하므로 악의적 호스트로부터의 비밀 보장 요구는 별도 결정이 필요하다.

검사: VT-05~08/11. 중복 요청, 동일 ID 다른 입력, 구매와 납부 경합, 납부 중 일차 종료, 정산 중 사망/이탈, 창구 점유자 이탈, 음수/초과/반올림 경계, 원격 클라이언트 정보 역산을 검사한다.

## 8. 몬스터·트랩·음성·표현

### 몬스터와 트랩

DG-018/DG-008에 대해 서버 AI가 감지 → 행동 선택 → 이동 → 공격/기믹 → 종료를 수행한다. Behavior Tree 또는 StateTree 등 선택은 행동 복잡도와 팀 작업 방식으로 정하고 같은 몬스터의 권위 상태를 두 실행기에 중복 저장하지 않는다. 몬스터별 감지 조건·추격 해제·피해·분리 기믹은 D-010 승인 데이터에서 받는다.

지형 변경은 내비게이션 갱신 요청과 기존 경로 무효화를 연결한다. 경로 재계산 중의 대기/실패 행동과 갇힘 처리 규칙은 D-006/010에서 확정한다. 애니메이션 이벤트만으로 클라이언트가 피해를 확정하지 않는다. 트랩은 대상·중복 발동·재발동 조건을 서버에서 검사하고 피해와 연출을 분리한다.

### 근거리 음성

DG-016은 음성 서비스 접속/채널 수명과 플레이어 위치·상태 정책을 연결하는 작업이다. 일반 게임 사운드의 거리 감쇠를 켜는 것만으로 원격 음성 제공자·채널·권한·재접속이 해결되지는 않는다. D-009에 따라 근거리 외 채널 여부, 사망/깔림 처리, 거리 규칙을 확정한 뒤 제공자를 선정한다.

서비스 사용자와 게임 플레이어 매핑, 참가/종료/연결 실패 정리, 위치 갱신, 입력 장치·음소거 UI를 설계한다. 로그에 인증값을 남기지 않는다. 실제 서비스·4PC 검증 전 로컬 테스트만으로 완료 처리하지 않는다.

엔진 VoIP/VOIPTalker와 제공자 Voice Chat 경로를 비교하고, 규칙 밖 음성 전달을 금지해야 한다면 서버 중계 또는 제공자 권한에서 차단한다. 클라이언트 볼륨만 낮추는 것은 수신 방지가 아니다. 구체 집행 위치·제공자 제약은 [엔진 기능 안내 3절 E](UNREAL_FEATURE_COVERAGE.md#e-온라인-세션근거리-음성)와 D-009에서 확인한다.

### UI와 카툰 표현

DG-019의 외곽선·해칭·낮은 채도는 승인 아트 샘플에 맞춘 재질/후처리 조합으로 검토한다. 개발반은 굴착면·잔해·캐릭터·몬스터와 원격 상태에서 표현이 일관되게 적용되도록 연결한다. 숨겨진 아이템이나 보이지 않아야 할 대상을 외곽선 패스로 노출하지 않는지도 검사한다.

UI는 서버가 전달한 공개/개인 뷰를 표시하고 입력 의도를 보낸다. 지갑·할당량을 화면에서 다시 계산해 규칙 원본으로 삼지 않는다. 로딩·요청 중·실패·연결 종료 상태도 준비한다. 성능 목표·해상도·허용 시각 차이는 D-011이 원본이다.

검사: VT-10/12/13. 굴착 뒤 몬스터 경로, 트랩 동시 접촉, 원격 피해, 음성 재참가·종료 잔류·거리/상태 정책, 은닉 대상 윤곽 노출, 카툰 표현 비용을 확인한다.

## 9. 공통 데이터 계약과 저장 경계

| 논리 데이터 | 필요한 최소 정보 제안 | 설계 목적 |
|---|---|---|
| 요청 문맥 | 런 ID, 서버 식별 호출자, 요청 ID, 대상 ID, 예상 버전 | 오래된 런·대상에 요청 재사용 방지 |
| 지형 결과 | 지역 ID, 기준/결과 버전, 승인된 수정 내용 | 차이 순서·누락 감지와 재동기화 |
| 아이템 상태 | 인스턴스 ID, 정의 ID, 보관 위치/소유 참조, 버전 | 단일 소유권과 중복 정산 방지 |
| 탈출 명세 | 런/탈출 ID, 확정 ItemId 집합, 귀속 계산 근거 | 움직이는 월드와 정산 대상 분리 |
| 거래 영수증 | 거래 ID, 플레이어, 종류, 입력 식별, 확정 결과 | 같은 요청 재전송 처리와 감사 |
| 개인 뷰 | 소유자에게 허용된 지갑/인벤토리/거래 결과, 버전 | 권위 원장 전체를 복제하지 않고 UI 구성 |
| 콘텐츠 정의 | 정의 ID, 기획 요구/개정, 값·단위, 콘텐츠 참조 | 기획 변경과 데이터 변경 추적 |

정의 데이터와 런 상태를 분리한다. 콘텐츠 변경으로 과거 저장 데이터의 정의 ID가 사라질 경우 처리는 영구 저장을 채택할 때 버전/마이그레이션 규칙으로 정한다. 현재 저장 정책은 미정이므로 자동 저장·클라우드 저장·백엔드·서버 재시작 복구를 구현 범위에 확정하지 않는다.

## 10. 착수 순서와 결정이 필요한 지점

아래 순서는 제작 일정이 아닌 구현 의존 순서다. 팀원 수·담당·완료일을 임의 배정하지 않는다. 제작 M1~M3와 네트워크 검증 M0~M3는 별도 분류다.

| 순서 | 개발반 작업 | 다음 단계로 넘어갈 근거 | 결정 대기 중 가능한 작업 |
|---|---|---|---|
| 1 | UE 5.8.2 환경·프로젝트·입력·1~4인 접속 기반 확인 | 실제 엔진/SDK/플러그인·실행 기록, VT-01 | 설치/소스·공식 지원 조사. 플랫폼/서버 채택은 D-003/004 필요 |
| 2 | 동일 실험 맵에서 지형 후보·충돌·AI·복제 비교 | VT-02/12/13 측정과 자유도 충족 결과 | 파괴/청크 후보별 기술 실험; 최종 지형 선택은 D-005와 연결 |
| 3 | 아이템 1종으로 굴착→운반→탈출→정산 연결 | 소유권·중복 정산 불변식, VT-04/05 | 가짜 규칙을 승인값으로 기록하지 않는 시험 데이터 사용 |
| 4 | 보강·붕괴·구출·사망 거래 통합 | VT-02/03/08, 동시 요청과 실패 정리 | 상태 전이·거래 중복 방지 검사; 솔로/복구 정책은 D-006/008 필요 |
| 5 | 구매·비공개 납부·4일 루프 | VT-05~08, 정보 전달 경계 확인 | 입력 검증·거래 원자성; 효율·상향·공개 규칙은 D-008 필요 |
| 6 | 절차 갱도·던전 2종·AI/트랩 콘텐츠 확장 | VT-09/13과 전체 루프 | 데이터 규격·샘플 연결; 실제 목록은 D-010 필요 |
| 7 | 음성·최종 UI/표현·4PC·패키징 | VT-10/12, M3 서비스 검증 | 제공자 평가·UI 프로토타입; D-009/011 확정 후 수용 |

음성과 지형처럼 위험이 큰 항목은 실제 통합 순서와 별개로 초기에 짧은 기술 검증을 할 수 있다. 시험용 수치는 테스트 픽스처임을 표시하며 게임 기본값으로 승격하지 않는다. 기획 미결과 무관한 불변식 검사는 먼저 진행하고, 미결 정책에 의존하는 수용 결과는 보류한다.

### 채택 시 ADR로 남길 기술 결정

이 문서의 제안은 기술 책임자 검토 전까지 채택이 아니다. 아래 결정은 근거 실험이 끝나면 [ADR](decisions/ADR-001-document-ownership.md)과 같은 형식으로 기록하고, 연결된 D 항목의 기술 하위 질문을 닫는다. 검토·승인 담당은 미정이다.

|---|---|---|---|
| 서버 토폴로지(리슨/전용)와 세션 경로 | D-003, D-004 | VT-01, 플랫폼·제공자 조건 | 순서 1 |
| 복제 시스템(Legacy/Iris)과 대역폭 정책 | D-004, D-011 | VT-12 측정, 프로젝트 설정 | 순서 1~2 |
| 지형 표현 방식 | D-005 | 순서 2 실험의 VT-02/12/13 결과 | 순서 2 |
| 런·일차 월드 구성과 장부 보존(같은 월드/서버 travel) | D-008 | VT-07/09, 3절 비교 | 순서 3~5 |
| 운반 방식(부착/물리) | D-007 | VT-04, 프로토타입 | 순서 3 |
| 음성 경로(엔진 VoIP/제공자) | D-009 | VT-10, M3 | 순서 7 이전 |
| 저장 도입 범위 | D-003 | 기획 승인 저장 정책 | 정책 결정 후 |

AI 실행기(Behavior Tree/StateTree)와 GAS 같은 선택은 팀 작업 방식과 요구가 생길 때 같은 방식으로 추가한다.

## 11. 작업 인계와 완료 판정

기능 작업에는 요구 ID/승인 개정, 수정할 코드·에셋 경로, 담당 상태, 입력/결과 계약, 미결 결정, 정상/경계/실패 검사와 증거를 함께 남긴다. 바이너리 패키지와 공유 맵은 동시 편집하지 않는다. 코드에서 에셋 경로를 임의 하드코딩하기 전에 로딩·데이터 참조 규격을 합의한다.

문서 완료는 구현 완료와 다르다. 이번 문서에는 설계 제안만 있으며 빌드·PIE·다인·패키징·성능 통과 기록이 없다. 실제 기능 완료는 [검증 계획](VERIFICATION_PLAN.md)의 검사 결과와 해당 기획 수용 근거를 연결해야 한다. 승인된 Notion 원본이 등록되면 본 문서의 요구 추적과 미결 조건부터 다시 대조한다.
