# 요구사항에서 구현 작업으로

기획·설계 문서를 실제 구현 범위로 바꾸거나 구현과의 차이를 조사할 때 사용한다. 분석만 요청받았다면 파일 수정으로 확대하지 않는다.

## 원문과 구현의 연결

목표, 행위자, 입력·출력, 조건·예외·단위, 상태 소유자, 성공·실패 기준을 추출한다. 원문 절, 현재 코드·에셋에서 확인한 사실, 추정을 별도로 적는다.

| 요구 ID | 원문·결정 근거 | 현재 구현·실행 근거 | 충족·미확인·갭 | 변경 범위 | 검증 |
|---|---|---|---|---|---|
| 작업별 ID | 실제 문서 절 | 파일·심볼·검사한 버전 | 관찰된 상태 | 담당 경계 | L/M 기준과 예상 결과 |

키워드 일치만으로 구현을 찾았다고 하지 않는다. 진입점 → 호출 관계 → 상태 소유 → 데이터·초기화 → 사용자에게 보이는 결과를 추적한다. 없는 것으로 단정하기 전 검색 범위를 남긴다.

## 결정과 단계

- 기존 사용자 결정과 프로젝트 계약을 먼저 적용한다. 읽기만으로 다른 담당자의 수정 승인이 필요한 것은 아니다.
- 공개 API, 모듈 의존, 서버 권위, 맵·에셋 소유, 저장 호환성에 미치는 영향을 판단한다.
- 미결 질문에는 확인한 사실, 막히는 작업, 선택별 영향과 권고를 함께 적는다. 승인된 구현 선택을 다시 묻지 않는다.
- 각 요구를 [작업 브리프](TASK_BRIEF.md)의 산출물·제외 범위·완료 기준·검증에 연결한다. 요구 누락과 중복을 확인한다.
- 선행 계약이 정해지지 않은 단계는 작업자로 병렬 배정하지 않는다. 독립적인 단계만 [분업 기준](WORK_ORCHESTRATION.md)에 따라 분리한다.
- 분석 완료, 구현 존재, 실행 검증 완료는 서로 다른 상태다. 실제 근거로 [검증 상태](VERIFICATION.md)를 정한다.
