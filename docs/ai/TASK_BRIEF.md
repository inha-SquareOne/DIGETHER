# 작업 브리프

결과와 제약을 적고 구현 절차는 실행자에게 맡긴다. 작은 작업은 필요한 항목만 쓴다.

## 템플릿

- 목표 / 배경:
- 근거: 기획 문서 절 / 아키텍처 결정 / 에픽:
- 산출물 / 이번에 제외할 것:
- 읽기 범위 / 수정 범위:
- 담당 모듈 / 레벨·에셋:
- 환경: 엔진·도구·플러그인 버전, 플랫폼·빌드 타깃, 실행 가능한 검증:
- 기준 상태: 커밋·미커밋 변경 또는 파일 해시, 보존할 변경:
- 서버 권위·복제·음성 영향:
- 데이터 에셋·테이블 / 저장 호환성 영향:
- 병행 작업과 충돌 가능성:
- 관찰 가능한 완료 기준:
- 먼저 쓸 테스트([TDD](TDD.md) 대상이면):
- 검증: [L1 / L2 / L3](VERIFICATION.md), [M0~M3](MULTIPLAYER_TEST.md):
- 멈추고 물을 조건:
- 실패·롤백 조건: 복구 대상·기준 사본·데이터 보존·남은 프로세스 정리:
- 증거 위치 / 인수인계 위치:
- 별도 승인이 필요한 삭제·외부 전송·배포와 현재 승인 범위:
- 미결 결정 / 후속 작업:

완료 기준은 "무엇을 관찰하면 끝인가"로 쓴다. 예: "서버 검증 후 상태가 바뀌고 호스트와 클라이언트 전원에 같은 값이 보이며, 권한 없는 요청은 거부된다."
분석 전용 요청에는 "읽기 전용 조사, 파일 수정 없음"을 명시한다.

## 기획 문서에서 브리프 만들기

1. 기획 문서에서 목표·행위자·입출력·규칙·수치·상태 소유권·검증 기준을 추출한다.
2. 최신 결정 기록으로 폐기·변경된 내용을 구분한다.
3. 현재 공개 API·호출 관계·데이터·초기화 순서를 확인한다. 못 찾았으면 검색 범위를 적는다.
4. 요구사항마다 구현 근거·갭·변경·권위·검증을 연결한다.
5. 선행 순서에 맞춰 독립 검증 가능한 단계로 나눈다.

| ID | 요구사항 | 현재 구현 근거 | 필요한 변경 | 권위 | 테스트·검증 |
|---|---|---|---|---|---|
| 예 | 배치 후 전원에게 같은 상태 | 파일 확인 후 기록 | 복제 상태·적용기 | 서버 | 단위 테스트 + L3/M2 |

원문이 충돌하는 항목은 프로젝트의 결정 대기 목록을 확인하고 임의로 확정하지 않는다. 각 항목을 확정·제안·미결로 구분하고 근거·결정자·영향받는 작업을 연결한다. 미결 항목에 의존하지 않는 작업은 계속한다.
분석 완료와 기능 구현 완료를 구분한다.
