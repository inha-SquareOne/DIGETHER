# 질문·답변과 결과 보고 방식

Claude·Codex 공통 기준이다. 한국어로 **결론부터** 답하고, 필요한 근거와 한계를 이어서 설명한다. 실행 권한은 [실행 정책](EXECUTION_POLICY.md), 검증 판정은 [검증 기준](VERIFICATION.md)을 따른다.

## 답변 순서

1. 질문의 직접적인 답 또는 작업 결과를 한두 문장으로 먼저 말한다. 무엇이 완료됐고 무엇이 안 됐는지 명확히 한다. 조사한 순서를 먼저 나열하지 않는다.
2. 사용자의 결정·입력이 있어야 진행할 수 있으면 결론 바로 뒤에 둔다. 필요한 결정이 없으면 생략한다.
3. 이유·근거, 주요 변경과 실제 검증 결과를 설명한다. 관련 파일은 찾을 수 있는 링크로 연결한다.
4. 미검증·남은 문제와 다음 행동이 있으면 짧게 적는다. 실패나 제한을 보고 끝에 숨기지 않는다.

이 순서는 정보의 우선순위이며 매번 같은 제목·표를 만들라는 뜻이 아니다. 단순 질문에는 직접적인 답과 필요한 근거만, 단순 작업에는 결과·핵심 변경·검증만 적는다. 복잡한 조사에는 결론 → 근거 → 대안과 선택 이유 순서로 설명한다. 진행 업데이트는 현재까지 확인한 사실과 다음 확인 대상을 짧게 알린다.

## 사실과 증거

- 확인된 사실, 제안·추정, 미확인을 구분한다. 기존 문서의 계획을 실제 구현으로 표현하지 않는다.
- 검증하지 않은 것을 “동작합니다”, 실패한 것을 “완료했습니다”라고 쓰지 않는다. 설정 파일 작성·도구 연결·실제 호출·게임 실행은 서로 다른 확인 단계다.
- 테스트는 실제 환경·범위·결과를 적고, 반복 수·통과 수가 확인됐다면 함께 쓴다. 숫자를 만들거나 모든 문서 확인에 수치를 억지로 붙이지 않는다.
- 찾지 못한 것은 확인한 경로·검색 범위와 한계를 밝힌다. 검색 실패를 부재나 미지원으로 단정하지 않는다.
- 이번 변경에서 발생한 결함과 범위 밖 기존 결함을 구분한다. 중요한 위험과 미검증은 해당 결과 가까이에 설명한다.

| 피할 표현 | 대신 설명할 것 |
|---|---|
| 완벽하게 구현했습니다 | 구현된 범위와 실제 검증·미검증 |
| 동작할 것입니다 | 아직 실행하지 않았다는 사실과 확인 방법 |
| 간단히 수정했습니다 | 어느 파일의 어떤 동작을 왜 수정했는지 |
| 문제없습니다 | 확인한 항목과 확인하지 못한 범위 |
| 테스트했습니다 | 수행한 검사·환경·관찰 결과 |

## 질문과 설명

- 사용자가 “뭐 해야 돼?”, “할 일이 뭐야?”, “다음에 무엇을 하지?”, “남은 작업은?”처럼 할 일·우선순위·재개 지점을 물으면 로컬 `.claude/docs/pointer.md`에서 관련 작업 기록과 `handover/` 인수인계서를 찾아 먼저 읽는다. 목록 요약만 보고 답하지 않는다.
- 인수인계의 미완료·필요한 결정·다음 첫 행동을 현재 Git 상태, 관련 Issue·PR과 기준 문서에 대조한다. 완료·취소·변경된 과거 작업을 다시 할 일로 제시하지 않는다. 사용자 담당이 확인된 일과 다른 담당자의 일을 구분하고 담당자를 추정하지 않는다.
- 답변은 지금 할 일과 우선순위를 먼저 제시하고, 관련 인수인계 링크·확인 시점·선행 조건을 필요한 만큼 덧붙인다. 로컬 기록이 없거나 접근할 수 없으면 그 사실을 밝히고 공유 현황과 현재 파일로 확인한 범위에서 답한다. 기록이 없다는 이유로 할 일이 없다고 단정하지 않는다. 할 일 조회 자체를 구현·커밋·외부 전송 승인으로 해석하지 않는다.
- 이미 확정된 결정이나 승인 범위를 다시 묻지 않는다. 핵심 미결 사항만 질문하고 독립적인 작업은 계속한다.
- 질문은 한 번에 이해할 수 있는 결정 단위로 제시한다. 여러 질문이 꼭 필요하면 관련된 것끼리 묶고, 실질적인 선택지가 있을 때 각 선택의 영향과 권장 이유를 짧게 설명한다.
- 아직 결정되지 않은 정책을 먼저 구현한 뒤 선택을 묻지 않는다. 이미 정해진 정책에 우려가 있으면 확인 질문 대신 우려와 근거를 보고한다.
- 확인이 필요하면 왜 필요한지와 적용 근거를 설명한다. 사용자 답변을 기다리는 것과 전체 작업을 중단하는 것을 구분한다.
- “이쪽”, “저쪽”, “그거”처럼 대상이 모호한 표현보다 파일·기능·브랜치 이름을 사용한다.
- 코드는 필요한 변경 부분만 제시하고 이유를 함께 설명한다. 파일 전체나 로그 전체를 답변에 덤프하지 않는다.
- 표는 비교할 항목이 있을 때, 목록은 순서·병렬 항목을 읽기 쉽게 할 때 사용한다. 답변을 작업보다 불필요하게 길게 만들지 않는다.

## 적용 예

“MCP 설정은 추가했고 실제 읽기 호출도 성공했습니다. Claude는 프로젝트 서버 승인이 남아 있습니다.”처럼 결과와 한계를 먼저 말한다. 이후 변경 파일과 검증 근거를 필요한 만큼 설명한다. 예문의 성공 여부를 다른 작업에 그대로 적용하지 않는다.
