# 프로젝트별 소유권과 작업 경계

CODEOWNERS는 리뷰 소유자를 연결한다. 로컬 파일 쓰기 권한, AI 수정 허가, 파일 잠금이나 보안 차단 장치 자체가 아니다. 프로젝트는 리뷰 소유자와 실제 작업 권한을 따로 기록한다. 이 패키지의 템플릿과 역할 계약만으로 저장소 보호 설정을 변경하지 않는다.

## 설정할 내용

[작업 경계 양식](../templates/PROJECT_BOUNDARIES_TEMPLATE.md)에 실제 경로·담당자·공유 경로 최종 책임자·검토 담당·AI 읽기/수정 범위·필요 조율·검증·인계 위치를 채운다. 사용하지 않는 영역은 해당 없음으로 표시한다. 사람이 없는 개인 프로젝트도 자신의 결정·검사 책임을 기록할 수 있으며 가상의 담당자를 만들지 않는다.

Source, Content, Config, Plugins, Build, 공통 문서, CI, 에이전트/스킬·권한 설정의 경계는 프로젝트 구조에 맞춰 선택한다. 플러그인은 소스·바이너리·콘텐츠가 함께 바뀔 수 있고, 기능 하나가 여러 영역에 걸칠 수 있으므로 디렉터리 이름만으로 영향 범위를 끝내지 않는다.

## 작업 시작과 경계 변경

1. 현재 사용자 요청·이미 승인된 범위·프로젝트 경계표·CODEOWNERS·하위 지침·기존 변경/잠금을 확인한다. 담당자 표가 없다는 이유로 전체 저장소 수정이 허용된 것으로 해석하지 않는다. 현재 요청에 필요한 범위는 기존 승인과 관례에 따라 판단한다.
2. 대상 경로와 실제 영향 경로를 나누어 확인한다. 공유 헤더·설정·에셋 참조·빌드·CI·도구 설정을 포함한다. 경계 충돌이 있으면 작업 범위를 임의로 넓히지 않는다.
3. 경계 밖 변경이 필요하면 양식에 경로, 변경 이유, 현재 권한, 대안, 영향, 검증과 복구, 필요한 결정을 적는다. 기존 승인이 이미 포함하는 사항은 다시 묻지 않는다. 미승인 의존 작업만 보류하고 독립 작업은 계속한다.
4. 담당자와 리뷰어는 실제 프로젝트 기록 또는 확인된 계정에서 찾는다. 표에 이름이 있다는 사실만으로 메시지·리뷰 요청·멘션을 보내지 않는다. 명시된 발신 권한이 있을 때만 실행한다.

## 동시 편집과 인계

같은 파일·패키지에는 활성 작성자를 하나 정한다. 텍스트 파일을 나눠 수정해도 공유 선언·생성 파일·설정의 충돌 가능성을 확인한다. 분리된 체크아웃도 통합 충돌을 없애지 않으므로 최종 책임자가 통합된 상태를 검증한다.

.uasset/.umap 및 외부 액터 패키지는 텍스트 병합을 전제로 나누지 않는다. 실제 소스 컨트롤 잠금/checkout을 쓰거나 패키지·맵·연관 파일과 작업자를 기록해 명시적으로 조율한다. 사용 중인 Editor의 미저장 상태와 참조 변경도 확인한다. 다른 작업자의 잠금을 강제로 풀거나 파일을 덮어쓰지 않는다.

인계에는 변경 경로, 완료/미완료, 잠금과 미저장 상태, 검사 증거, 남은 위험, 다음 작성자·리뷰 담당과 시작 조건을 남긴다. 이전 작성자의 저장·검사·인계 확인 후 다음 편집을 시작한다. [작업 분담](WORK_ORCHESTRATION.md), [에셋 안전](../unreal/ASSET_SAFETY.md)을 따른다.

## 긴급 수정

프로젝트가 정한 긴급 기준·승인권자·최소 변경 범위·검증·복구 기준을 사용한다. 긴급하다는 이유만으로 경계나 보호 규칙을 우회하지 않는다. 승인된 긴급 수정 후 변경·영향·실행 검사·잔여 위험을 기록하고 지정된 검토 담당에게 정해진 기한 내 사후 리뷰를 받는다. 알림·외부 요청은 기존 발신 권한에 따르며, 사후 리뷰 완료까지 미결 항목으로 관리한다. 정책이 없으면 양식의 해당 항목을 미결로 두고 필요한 판단만 요청한다.

## GitHub CODEOWNERS 적용

비활성 [CODEOWNERS 예시](../templates/CODEOWNERS.example)의 주석을 실제 경로와 확인된 소유자로 채워 프로젝트에서 검토한다. 이 패키지는 활성 CODEOWNERS를 만들지 않는다.

2026-10-10 공식 문서 확인: GitHub는 .github/, 루트, docs/ 순서로 처음 찾은 CODEOWNERS를 사용한다. 경로는 대소문자를 구별하며 /는 저장소 루트 기준이다. 마지막 일치 규칙이 우선하고 같은 패턴의 복수 소유자는 한 줄에 둔다. ! 부정, [] 문자 범위, 시작 # 이스케이프는 지원하지 않는다. @username 또는 @org/team-name을 사용하며 소유자는 쓰기 권한, 팀은 가시성과 명시적 쓰기 권한이 필요하다. 잘못된 구문·계정·권한은 배정 실패를 일으킬 수 있다. [GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

리뷰 요청은 PR의 base 브랜치 정의를 따른다. draft에서는 자동 요청하지 않고 ready 전환 시 요청한다. 같은 경로의 소유자가 여러 명이어도 필수 소유자 리뷰는 그중 한 명의 승인으로 충족할 수 있으므로 경계표의 최종 책임자와 다중 검토 절차를 대신하지 않는다. 적용 전 실제 파일별 매칭과 GitHub 구문 오류·계정 권한을 확인한다. [리뷰 적용 조건](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

필수 소유자 승인·필수 검사·관리자 예외는 브랜치 보호 또는 ruleset에서 별도로 정한다. 설정 변경에는 해당 권한과 사용자 승인이 필요하며 이 작업에서 자동 변경하지 않는다. 프로젝트의 저장소 유형·플랜·기존 보호 규칙을 확인한다. [보호 브랜치](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## 도입 확인

대표 파일마다 예상 리뷰 소유자, 마지막 일치 패턴, AI 수정 범위, 활성 작업자, 필요한 검사를 대조한다. 넓은 기본 패턴 뒤에 좁은 예외를 두고, 더 뒤의 규칙이 의도치 않게 덮지 않는지 본다. CODEOWNERS 자체와 CI·에이전트/스킬 설정도 검토 책임을 지정한다. GitHub 적용은 실제 저장소에서 확인해야 하며 로컬 템플릿 검사만으로 리뷰 강제를 보장하지 않는다.
