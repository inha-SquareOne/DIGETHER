# 멀티플레이 테스트

N은 프로젝트 프로필이 정한 플레이어 수다. 리슨 서버는 호스트가 플레이어 한 명이므로 호스트 + 클라이언트 N-1, 전용 서버는 서버 + 클라이언트 N으로 구성한다.

| 등급 | 구성 | 확인 범위 |
|---|---|---|
| M0 | 단일 호스트 | 로컬 로직만 |
| M1 | 리슨: 호스트 + 클라이언트 1 / 전용: 서버 + 클라이언트 1 | 기초 복제 경로. 전용 서버의 클라이언트 간 상호작용은 추가 클라이언트 필요 |
| M2 | 플레이어 N명(리슨: 호스트 + 클라 N-1 / 전용: 서버 + 클라 N), 같은 PC의 다중 프로세스 | 전원 공유 상태·동시 요청 |
| M3 | 플레이어 N명, 서로 다른 PC | 플랫폼 세션·음성·실제 네트워크·성능 |

이 공용 기준에서 네트워크 변경의 기본 최소는 M2다. 프로젝트가 다른 기준을 채택했다면 이유·보완 검증을 명시한다. 에디터 다중 PIE는 가능한 환경에서 예비 점검으로 쓰고, 별도 프로세스 실행 결과를 기록한다.
M0는 서버 권위·원격 복제의 증거가 아니다. M3라도 실제로 실행하지 않은 플랫폼 세션·음성·성능 항목까지 통과로 간주하지 않는다.
에디터·엔진·빌드가 없으면 실행한 것으로 기록하지 않는다.
플랫폼 세션과 음성은 필요한 별도 계정과 실제 서비스 구성을 확인하며 로컬 PIE로 검증을 대체하지 않는다.
전용 서버 구조에서는 아래의 "호스트"를 서버 프로세스로 읽되 인원은 위 구성을 따르고, 서버에 화면이 없다는 점을 관찰 계획에 반영한다.

## 준비

같은 커밋 또는 동일 변경분으로 빌드하고 버전·맵·호스트 PC·접속 방식·계정을 기록한다.
실제 프로젝트 파일과 빌드 타깃을 확인해 실행한다. 존재하지 않는 전용 스크립트나 메뉴를 가정하지 않는다.
성능 비교 시 호스트 사양·렌더링 설정·측정 구간을 고정한다.

## 공통 시나리오

프로젝트 층이 게임별 필수 시나리오를 더한다. 아래는 어느 프로젝트에나 해당한다.

1. 전원 접속, 소유 플레이어, 입력, 원격 이동.
2. 공유 대상에 대한 동시 요청과 범위 밖 요청을 서버가 검증하는지.
3. 공유 권위 상태가 호스트와 모든 클라이언트에서 같은 값인지, 각 클라이언트의 표현이 프로젝트 계약에 맞는지. 소유자 전용 UI·팀별 정보·비대칭 역할처럼 같은 상태를 다르게 보여 주는 것은 계약대로인지 본다.
4. 공유 자원의 중복 차감·음수·경합.
5. 후입·재접속 시 초기 상태가 맞는지. 기술적 동기화와 제품의 입장 허용 정책은 구분한다.
6. 호스트·클라이언트 이탈 시 프로젝트가 정한 흐름(종료 고지, 재시작, 승계 여부)대로 되는지.
7. 세션 종료 후 정리와 재시작. 음성 채널을 쓰면 채널 잔류도 본다.

미구현 기능은 미실행으로 표시한다. 정책이 미결인 상황은 결정 대기 목록을 먼저 확인한다. 해당 없음은 프로젝트 계약상 불필요한 경우에만 이유와 함께 쓴다.
후입·재접속을 금지한 프로젝트는 허용 흐름을 임의로 추가하지 않고 거부·정리 흐름을 검사한다. 비교할 상태의 공개 범위와 수렴 대기 시간을 정해 일시적인 전송 지연을 영구 불일치와 구분한다. 소유자·팀 전용 정보가 다른 클라이언트에 전달되지 않는지도 확인한다.

## 반복·측정

경합·타이밍 결함은 기본 최소 10회 반복하고 횟수·실패율을 남긴다. 이는 무결함이나 통계적 신뢰도를 보장하는 수치가 아니다. 순서·시드·재현 조건을 남기고 위험과 프로젝트 목표에 맞춰 반복 수를 늘린다.
지연·손실 주입은 설정값과 관측값을 기록한다.
프레임·대역폭·지연 목표는 설계 목표이며 실측 전 달성으로 보고하지 않는다.
검증 로그에 실행 환경, 단계, 예상/실제, 호스트/클라별 결과, 미검증을 남긴다.
자동 스모크가 준비용 이동이나 상태 주입을 쓴다면 그 사실을 기록하고 사람의 플레이와 구분한다.
