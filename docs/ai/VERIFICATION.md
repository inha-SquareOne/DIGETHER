# 검증

완료는 관찰된 상태로 판정한다. 실행 실패·생략·환경 부재를 성공으로 쓰지 않는다.

| 수준 | 적용 | 증거 |
|---|---|---|
| L1 문서 | 문서·운영 규칙 변경 | 내용·로컬 링크·경로·상충 규칙 확인 |
| L1 코드·에셋 | 코드·빌드 설정·Blueprint·에셋 변경 | 코드·빌드 설정은 해당 타깃 빌드, Blueprint·에셋은 컴파일·로드·참조 검사. 신규 오류·경고 구분 |
| L2 | 기능·데이터 변경 | 자동 테스트 또는 테스트 레벨에서 정상·실패 경로 관찰 |
| L3 | 맵·초기화·전환, 여러 시스템에 걸친 상태, 네트워크·공유 상태 | 실제 실행 흐름에서의 시스템 통합과 회귀 확인. 네트워크·공유 상태 변경은 여기에 더해 다인 통합([멀티플레이 테스트](MULTIPLAYER_TEST.md))에서 호스트·원격 클라이언트를 관찰 |

수준은 해당 변경에 적용되는 항목을 누적한다. L3 변경은 L1과 L2도 충족해야 하며, Blueprint·데이터만 있는 프로젝트에 존재하지 않는 C++ 타깃을 요구하지 않는다. 적용하지 않는 항목은 이유를 적는다.
싱글플레이 프로젝트의 L3는 시작부터 해당 흐름까지의 실제 실행, 맵 전환·재시작·저장 후 재진입의 회귀 확인이다.
문서 변경만으로 엔진 빌드를 요구하지 않는다. 문서 단계에서는 링크·결정 정합성을 확인한다.
코드가 있는 프로젝트에서는 컴파일이 깨진 채로 안정점이라 보고하지 않는다.
L2의 기본 수단은 자동 테스트다. 어떤 변경에 테스트를 먼저 쓰는지는 [TDD](TDD.md)를 따른다.
다인 검증을 기다리는 동안에는 테스트 체크리스트를 인수인계에 남기고, 로컬 확인을 통합 통과로 올리지 않는다.
외부 서비스(플랫폼 세션·음성)와 실제 지연은 실제 환경이 필요하다. 캡처나 실제 관찰 없이 시각적 결과를 검증 완료로 쓰지 않는다.
자동 검사가 준비용 이동·치트·상태 주입을 썼다면 사람의 플레이 검증과 구분해 적는다.

## 코드 정적 확인

권위 경계, RPC 호출자·소유권·거리 검증, 수치 외부화, 타이머·델리게이트 수명, Tick의 반복 탐색을 확인한다.
모듈 의존은 빌드 스크립트의 실제 상태로 확인한다. 리플렉션·GC 참조·스크립트 노출(Unreal이면 UHT·Blueprint)과 헤더의 숨은 의존을 확인한다.
에디터 전용·출시 빌드 가드 변경은 해당 구성에서 확인한다.
영구 저장 변경은 구버전 읽기·손상 파일·저장 실패와 기존 데이터 보존을 검증한다.

## 상태 어휘

- 완료(검증됨): 요청 범위와 필요한 검증 모두 충족.
- 구현됨(미검증): 산출물은 있으나 실행 검증 부족.
- 조건부 통과: 제한이나 비핵심 미검증 항목이 남음. 남은 항목·영향·후속 검증을 적으며 필수 검증 부족을 이 상태로 숨기지 않는다.
- 검증 대기: 필요한 환경·인원 부족.
- 진단 완료·미수정 / 실패 / 차단됨: 해당 사실과 원인을 명시.

## 기록

| 주장 | 수준 / M등급 | 환경·실행 방법 | 실제 결과·증거 | 상태 |
|---|---|---|---|---|
| 예: 공유 상태 동기화 | L3/M2 | 호스트+클라3, 10회 | 실행 후 기록 | 검증 대기 |

증거는 다시 찾을 수 있게 적는다: 실행 명령, 로그·보고서 경로, 실행 파일이나 커밋 식별자, 반복 횟수.
자동 테스트는 통과 수뿐 아니라 실패·경고·미실행 수와 프로세스 종료 코드를 함께 적는다.
실행마다 별도 결과 위치와 실행 시각을 기록해 이전 보고서를 새 결과로 읽지 않는다. 기대한 테스트가 0개 실행됨, 보고서 누락·파싱 실패, 크래시·타임아웃, 필수 항목 미실행은 통과가 아니다. 종료 코드 0만으로 성공을 판정하지 않는다.
엔진·플러그인·플랫폼·빌드 타깃과 구성, 테스트 대상 버전을 남긴다. 미커밋 변경이 있으면 커밋 해시만 쓰지 말고 diff나 파일 해시로 실제 검사한 상태를 식별한다. 도구가 제공하지 않는 계수는 0이 아닌 확인 불가로 적는다.

## 완료 판정

요청한 산출물·완료 기준, 적용되는 검증 수준, 관련 회귀 확인, 최종 변경 범위, 필요한 작업 기록·인수인계 갱신을 함께 확인한다. 스크립트 작성과 스크립트 실행, 빌드 성공과 패키지 실행, 문서 근거 확인과 실제 동작 확인을 각각 구분한다.

## 독립 검수

독립 검수는 읽기 전용으로 요구사항·변경분·규칙·검증 결과를 평가한다.
판정은 PASS / CONDITIONAL / REJECT이며 핵심 미검증·오류가 있으면 PASS를 쓰지 않는다.
범위 밖 기존 결함은 기존 결함으로 분리한다.
지적은 수용·기각으로 나누고 기각에는 이유를 적는다. 수용 항목은 원 작성자가 반영한다.
