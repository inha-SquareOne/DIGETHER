# TDD — 테스트를 먼저 쓰는 범위와 순서

테스트를 먼저 쓰는 이유는 두 가지다. 구현 전에 "무엇이 맞는 동작인가"를 관찰 가능한 형태로 고정하고, 나중의 변경이 그것을 깼을 때 바로 알기 위해서다.
게임에서는 모든 것을 테스트로 고정할 수 없으므로 대상과 예외를 나눈다.

## 테스트를 먼저 쓰는 대상

- 순수 규칙과 계산: 자원 정산, 판정 조건, 경계값, 단위 변환.
- 상태 전이: 상태머신의 허용·거부 전이, 중복·순서가 뒤바뀐 요청.
- 서버 판정: 소유권·거리·상태 검증, 동시 요청의 승자, 권한 없는 요청 거부.
- 결정론이 필요한 생성기: 같은 시드의 같은 결과, 여러 시드에서 불변식 유지.
- 영구 저장: 구버전 읽기, 손상 파일, 저장 실패 후 재시도, 기존 데이터 보존.
- 데이터 무결성: 중복 ID, 범위, 없는 참조.
- 자동화로 재현 가능한 동작 결함: 고치기 전에 재현 테스트를 먼저 쓴다. 아래 시각·에셋·문서·다인 통합 예외는 해당 관찰로 검증한다.

## 순서

1. **Red.** 원하는 동작 하나를 테스트로 쓰고 실행해 실패를 확인한다. 원하는 동작이 아직 충족되지 않아서 실패하는지 본다. 구현이 없는 경우뿐 아니라 기존 구현의 버그·잘못된 경계값·빠진 거부 조건도 여기에 해당한다. 컴파일 오류나 테스트 자체의 실수로 실패한 것은 Red가 아니다.
2. **Green.** 그 테스트를 통과시키는 최소 구현을 한다. 범위 밖 기능을 같이 넣지 않는다.
3. **Refactor.** 테스트가 통과하는 상태를 유지하며 구조를 정리한다. 동작을 바꾸는 정리는 새 테스트부터 다시 시작한다.

버그 수정은 재현 테스트가 수정 전 코드에서 실패하는지 확인하고, 가능한 경우 예상되는 불완전한 수정도 잡는지 본다. 이전 상태 재현을 위해 사용자의 작업 트리를 되돌리지 않는다. 안전한 분리 환경이 없거나 실행이 불가능하면 수정 전 실패 미확인으로 기록한다.

## 테스트할 수 있게 만들기

판정을 엔진 월드·액터·시간에 묶지 않는다. 규칙은 입력을 받아 결과를 돌려주는 함수나 구조체로 빼고, 액터·컴포넌트는 그것을 호출해 결과를 적용한다.
시간·난수·저장 경로는 주입한다. 전역 난수나 현재 시각을 직접 읽으면 테스트가 재현되지 않는다.
컨테이너 순회 순서에 결과가 의존하지 않게 한다.

## 좋은 테스트

- 테스트 하나는 동작 하나를 본다. 이름만 읽어도 무엇을 보장하는지 알 수 있게 한다.
- 정상 경로와 함께 경계값과 실패 경로를 넣는다.
- 구현 세부(비공개 함수, 호출 횟수)가 아니라 밖에서 보이는 결과를 검사한다.
- 다른 테스트의 실행 순서나 남긴 상태에 의존하지 않는다.
- 사용자의 실제 세이브·설정을 건드리지 않고 임시 경로를 쓴다.

## 먼저 쓰지 않아도 되는 것

- 시각·연출·레벨 배치·UI 배열처럼 사람이 봐야 판단되는 것. 캡처나 실제 관찰로 검증한다.
- 방향을 찾는 탐색적 프로토타입. 다만 방향이 정해져 코드를 남기기로 하면 위 대상에 해당하는 부분에 테스트를 붙인다.
- 엔진·서드파티의 동작 자체. 우리 코드가 그것을 쓰는 경계만 검사한다.
- 문구·링크 수정처럼 되돌리기 쉽고 동작 계약을 바꾸지 않는 변경. L1 문서 검사로 확인하며 문장을 그대로 복제한 테스트를 만들지 않는다.
- 다인 통합에서만 드러나는 것. [멀티플레이 테스트](MULTIPLAYER_TEST.md)의 시나리오로 검증하고, 원인이 규칙 결함이면 단위 테스트로 내려 고정한다.

## 하지 않는 것

- 실패하는 테스트를 지우거나, 기대값을 현재 결과에 맞추거나, 건너뛰기로 표시해 통과시키지 않는다. 테스트가 틀렸다면 무엇이 틀렸는지 보고에 적고 고친다.
- 테스트만을 위한 분기를 제품 코드에 넣지 않는다.
- 통과 수를 늘리려고 같은 것을 여러 번 검사하지 않는다. 수치 목표보다 위험한 영역을 덮는다.

## 요청과 보고

사용자가 테스트 없이 구현하라고 하면 따르고, 무엇을 생략했는지 적는다. 자동 테스트 작성만 생략했는지, 실행 검증까지 생략했는지를 구분한다.
최종 상태는 실제로 충족한 검증으로 정한다. 실행해 관찰한 것이 없으면 "구현됨(미검증)"이고, 수동 관찰이나 통합 검증을 했다면 그 범위를 적고 자동 테스트 부재를 남은 작업으로 둔다. 나중에 위 대상부터 테스트를 붙인다.
보고에는 추가한 테스트, 수정 전 실패와 수정 후 통과를 확인했는지, 전체 테스트의 통과·실패·미실행 수를 적는다([검증](VERIFICATION.md)).
Unreal에서 테스트를 쓰고 돌리는 방법은 [Unreal 테스트](../unreal/TESTING.md)에 있다.
