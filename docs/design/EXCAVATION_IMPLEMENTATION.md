# 시험 굴착 구현 설계

기준일: 2026-10-28. 초도 한정 볼륨은 prototype-excavation-03에서 빌드·패키지·1인 렌더·로컬 4인 경합/재접속 검증을 통과했다. 상세 결과는 [프로토타입](../prototype/PROTOTYPE.md)의 실제 굴착 검증 절에 있으며 아래 확장 목표 전체의 완료를 뜻하지 않는다. 사용자 최신 지시: 조준한 흙을 둥글게 깎아 구멍을 넓히고 아래로 팔 수 있는 경험. [전체 시스템 설계](../SYSTEM_DESIGN.md)도 갱도 굴착 범위를 허용된 3D 흙 볼륨으로 해석한다. 던전의 지정 파괴 벽은 별도 규칙이다. Notion 기획 원본 URL·승인 개정은 아직 등록되지 않았고 [로컬 초안](../GAME_DESIGN.md)은 승인본이 아니다. 사용자 제공 추가 이미지의 어두운 저폴리 갱도·따뜻한 작업등·목재 지지대·철제 승강기·1인칭 도구·간결한 HUD는 프로토타입 시각 참고이며 게임 규칙이나 최종 아트 승인이 아니다.

## 기존 구현과 목표

기존 `World/DigetherPrototypeWorld.cpp`의 `ADigetherPrototypeDigCell::ApplyAppearance()`는 큐브 크기·위치와 Pawn 충돌 응답을 바꿀 뿐이며 WorldBuilder의 큰 `Floor`가 아래 공간을 막는다. `Character::AttackOrDig`와 `PlayerController::ServerInteract`는 액터 단위 상호작용이다. `CheckTremor`는 독립 큐브의 보강/복구와 근처 매몰을 시험한다. `GameMode::RequestWorldBurialPawn`은 기존 매몰 규칙 진입점이고 `SaveFixture`는 탐사 중 저장을 거부한다. `UDigetherPrototypeSaveGame` v2는 공개 상태·개인 상태·회수 장비만 저장한다. 따라서 큐브 및 거대 바닥의 미관 변경만으로는 실제 구덩이나 충돌 구멍이 생기지 않는다.

첫 수용 목표: 제한된 흙 영역에서 호스트와 접속 클라이언트가 같은 둥근 구멍을 보고, 그 표면에 부딪히며, 연속된 입력으로 옆을 넓히고 충분히 아래를 제거해 캐릭터가 실제로 내려간다. 지상 진입·구덩이 밖 이동·승강기 접근은 유지한다. 반경·셀 크기·볼륨·굴착 속도·여진 값은 **시험값**이다. 플레이어가 빠져나올 수 있는 경사와 안전 바닥, 최소/최대 공간 크기는 조작 시험으로 조정하며 제품 밸런스로 확정하지 않는다.

## 초도 구현 범위와 검증 상태

초도 `World/DigetherExcavationField.{h,cpp}`와 `DigetherExcavationTerrain.{h,cpp}`는 **단일 한정 볼륨**을 사용한다. XY 8m × 8m, 보호된 최하층을 제외하면 지표 아래 최대 약 2.15m까지 파기 가능한 시험 범위이며 표면 위 샘플을 포함한 격자는 16×16×6칸, 17×17×7개(2,023개) 꼭짓점, 간격 50cm다. 흙의 밀도는 128을 0으로 하는 2cm 단위 `uint8`이고 브러시 반경 125cm는 시험값이다. 보호 경계와 실제 파기 가능 깊이·조작감은 실행 검증이 필요하다. 무한 지형, 여러 지형 청크 또는 최종 크기를 뜻하지 않는다.

시험 배치에서 벽 지형은 WorldBuilder 원점 기준 `(5300, 0, 200)`, 회전 `Pitch +90°`로 생성되며 흙은 X 5300~5550 범위에 놓인다. 측면·뒤·윗면은 별도의 고정 암벽으로 막는 코드가 있다. 바닥 구덩이의 서쪽에는 X 중심 4010~4325cm, Y 중심 300cm, 폭 180cm의 고정 작업 계단을 두고 흙을 걷어내면 드러나도록 한다. 8개 발판은 최고 발판을 Z=-2cm로 두며 이후 높이는 -30~-210cm다(단차 약 28~30cm, 7단). 이 좌표와 치수는 시험값이며 03 패키지의 1인 렌더·충돌·계단 복귀 시나리오를 통과했다.

`GameMode`의 시험 안전 내려놓기는 충돌 sweep·바닥·흙 내부·시야를 확인하고 유효한 위치가 없으면 거부하도록 작성됐다. 구조 위치 후보는 수평 지형 영역에서 원래 지표 아래인 위치를 제외하고 흙 내부·캡슐 충돌을 확인한다. 이 두 경로는 실행 검증 전이며 지형을 파낸 뒤 이미 배치된 물품이 떨어지는 물리 동작을 보장하지 않는다.

Unreal MCP로 열린 `L_Prototype`의 최신 WorldBuilder 인스턴스 `BP_PrototypeWorldBuilder_C_1`은 위치·회전 0, 스케일 1로 확인됐다. 이 확인은 다른 맵이나 패키지 실기 검증을 대신하지 않는다.

서버 소유 지형 액터는 스키마·revision·밀도 배열을 하나의 `UPROPERTY` 스냅샷으로 복제하고 각 측에서 메시에 반영하는 초도 구현이다. 지지대 상태는 별도 복제 속성이다. 두 메시 컴포넌트 중 비활성 쪽에서 동기 충돌을 준비하고 body setup 상태를 확인해 교체하도록 구현했다. 03 패키지에서 굴착 후 실제 충돌 표본·캐릭터 이동 및 4인 복제 hash 일치를 확인했다. 프레임 단위 성능 측정과 실패 주입 검사는 별도다. 초기 접속/재접속 시 클라이언트의 충돌 준비 완료를 서버에 알리는 readiness 게이트, 누락·오류 복구, 다중 청크·부분 스냅샷 재조립은 **아직 구현되지 않은 후속 과제**다. 안정적인 다인 입장·재접속 보장을 뜻하지 않는다.

아래는 첫 구현의 설계 근거와 **확장 목표**다. 청크·조각 복제·저장 확장·다인 readiness 등은 구현 완료를 주장하지 않는다. 기존 큐브 `DigCell`은 별도 레거시 코드이며 새 지형과 맵 연결 및 제거 여부는 실제 통합 결과를 기준으로 한다.

## 한정 밀도 격자와 메시

- 고정 원점·셀 간격·정수 좌표·유한한 X/Y/Z 범위를 가진 런별 지형을 둔다. 각 **격자 꼭짓점**의 signed density는 양수 흙, 0 표면, 음수 빈 공간이며 일관된 정수 단위와 포화 범위로 저장한다. 초기는 지정 구간을 흙으로 채우고 표면 위와 안전 경계는 빈 공간이다. 경계 밖을 굴착 불가 바닥/벽으로 닫는 것이 목표이며 시험 배치의 실제 연속 충돌은 실행으로 검증한다. 구역·시드·격자 버전은 런 ID와 함께 정의한다. 고정 평면을 흙 구간과 겹치지 않게 분리하고 경계에 틈이 없도록 한다.
- 성공한 타격은 서버에서 추적한 표면점 근처에 구형 제거 연산 `new = min(old, distance(sample, center) - radius)`을 적용한다. 거리 및 중심/반경을 명시된 고정 정밀도로 양자화하고 정수 overflow·범위·0면 타이를 처리한다. 연산은 샘플링된 근사 구면이다. 초기 시험에서는 구멍이 큐브 토글처럼 보이지 않도록 해상도와 반경의 비율을 실화면에서 확인한다. 내부적으로 양자화된 격자를 쓰더라도 화면은 삼각 곡면이며 충분한 분해능이 필수다.
- 육면체 각 격자칸을 일관된 tetrahedra로 분할하고 부호 변화 변에서 0 위치를 보간해 삼각형을 만든다. 공통면의 대각선과 부호 0 규칙은 전역 좌표에서 양쪽 청크가 동일하게 계산한다. 삼각 winding·법선은 흙에서 빈 공간 쪽으로 향하게 하며 0 면적 삼각형은 제외한다. 이 알고리즘은 직접 구현 대상으로, 엔진에 marching tetrahedra 기능이 있다고 가정하지 않는다. 정수 샘플이 네트워크의 원본이며 메시 삼각 배열을 원본으로 복제하지 않는다.
- **확장 시** 청크는 격자칸 단위로 나누되 경계 꼭짓점은 **전역 좌표로 단일 소유**한다. 각 청크 재생성은 인접 청크의 꼭짓점까지 읽는다. 한 표본의 변경으로 영향을 받는 모든 청크를 같은 revision 거래에 넣고 빈/전부 흙/볼륨 경계 및 청크 모서리까지 검사한다. 색·재질과 UV는 저폴리 시험 표현이며 플레이 판정과 분리한다.

### 메시 정점 순서와 실제 충돌 조사

UE 5.8.2 `UKismetProceduralMeshLibrary::GenerateBoxMesh`의 윗면은 공기 방향 법선이 +Z여도 원래 인덱스의 `Cross(B-A, C-A)`가 -Z인 winding을 사용한다. `UProceduralMeshComponent::GetPhysicsTriMeshData`는 `bFlipNormals=true`로 두고 Chaos cook에서 첫 두 인덱스를 바꾸며, Chaos는 cook 후 정점 순서의 외적으로 충돌 면 법선을 구한다. 따라서 렌더링에 제공한 공기 방향 법선과 cook 후 물리 면 법선이 같으려면, 원래 메시의 외적은 공기 방향의 반대여야 한다.

패키지 `prototype-excavation-02` 실기 중 구덩이 바닥 충돌의 법선 Z가 약 -0.998로 관측되고 캐릭터 이동이 막혔다. 기존 코드가 외적을 공기 방향으로 정렬한 채 정점 A,B,C를 내보내 UE 순서와 반대였던 점이 원인이다. `DigetherExcavationField.cpp`는 공기 방향 shading normal을 유지하며 A,C,B 순으로 내보내도록 수정했다. `DigetherExcavationTerrainTest.cpp`는 원래 외적과 shading normal이 반대인지, cook의 인덱스 교환을 반영한 평면 바닥 +Z 및 Pitch +90° 벽 -X 법선이 기대값과 일치하는지 검사하도록 추가됐다. 이는 순수 생성 회귀 검사이며 **03 패키지의 실제 충돌·시각·이동 시나리오도 통과**했다.

### UE API와 선택 근거

설치된 UE 5.8.2 `Engine/Plugins/Runtime/ProceduralMeshComponent` descriptor에서 `ProceduralMeshComponent` Runtime 모듈을, 공개 `ProceduralMeshComponent.h`에서 `UProceduralMeshComponent::CreateMeshSection`의 충돌 생성 인자, `bUseComplexAsSimpleCollision`, `bUseAsyncCooking`을 확인했다. 이 컴포넌트는 노출 삼각형으로 렌더와 정적 복잡 충돌을 만들 후보이다. 런타임 모듈 의존성을 `DIGETHER.Build.cs`에 추가하고 프로젝트 플러그인 활성 상태와 패키징을 검증해야 한다. `UpdateMeshSection`은 위상 변경에 쓸 수 없으므로 구멍 변화에는 `CreateMeshSection`이 필요하다. 현재 소스 확인은 컴파일·cook·게임 충돌 성공 증거가 아니다. 이 컴포넌트의 복잡 충돌은 실제 캐릭터 캡슐·trace·동적 물품으로 검증해야 하며 메시 자체를 복제한다고 가정하지 않는다.

초도는 `bUseAsyncCooking=false`로 한정 단일 볼륨을 동기 재생성해 오래된 비동기 충돌이 새 상태를 덮는 경로를 피한다. 다른 방법(GeometryProcessing의 등치면, GPU/Voxel 플러그인)은 해당 API·패키징·복제와 지원 상태를 별도 검증하기 전까지 채택하지 않는다. 이 선택은 재생성 비용을 지불하므로 프레임·서버 시간·메모리와 네트워크 예산을 실제 측정하고 실패하면 격자 크기/빈도 또는 전용 충돌 경로를 재설계한다.

## 권위·입력·원자적 적용

`Character`의 좌클릭은 기존 공격과 구분하되 서버가 첫 유효 충돌을 재결정한다. 소유 `PlayerController`의 새 Server RPC에는 굴착 입력 의도만 보내고, 흙 액터·좌표·반경·변경 결과는 클라이언트가 결정하지 않는다. 호스트는 서버 Pawn에 속한 카메라 컴포넌트 위치와 서버가 받은 컨트롤 회전으로 거리 제한 trace를 실시하고 최초 차단 대상, 같은 월드, 탐사 상태, 생존/매몰, 장비, 양손 화물/시체 운반, 요청 빈도와 유효 표면·영역을 검증한다. 표면이 가려졌거나 다른 Pawn이 먼저 맞으면 흙을 뚫어 변경하지 않으며 기존 공격 판정을 이용한다. `CanInteract`의 액터 중심 거리 검사만으로 넓은 지형 전체를 판정하지 않는다. 서버 시점 갱신과 패킷 지연에 따른 조준 차이는 실제 네트워크 시험으로 확인한다.

한 서버 게임 스레드에서 동일 위치 동시 요청은 순서대로 직렬화하고 각각 최신 충돌 및 밀도를 재검사한다. 변화가 없는 타격은 성공으로 지급/카운트하지 않는다. 요청 식별자 중복 제거는 [2026-10-29 보정](../SYSTEM_DESIGN.md#2026-10-29-보정-steam-판매-기준과-요청-처리-단순화)에 따라 두지 않으며, 반복 타격은 최신 밀도 재검사와 요청 빈도 제한으로 처리한다. 경계/범위가 잘못된 입력은 변경하지 않는다.

초도 코드는 변경 후보 샘플로 준비용 비활성 컴포넌트에 메시와 충돌을 만들고 body setup의 생성/실패 상태를 확인한 다음 같은 게임 스레드에서 기존 충돌/표시를 교체하고 revision을 확정한다. 대표 위치의 trace를 통한 통합 검증은 후속 검사다. `CreateMeshSection`은 성공 반환값이 없으므로 함수 복귀만을 cook 성공의 증거로 삼지 않는다. 여러 청크의 전환 시 물리 쿼리가 부분 상태를 관찰하지 않는지 검증해야 하며, 준비/검사가 실패하거나 구현이 원자 교체를 보장하지 못하면 변경을 보류하고 이전 유효 상태를 유지한다. 비동기 전환은 이 보장과 별도 버전 취소·완료 통지 계약 검증 후에만 검토한다. 클라이언트 준비 중 지형은 이전 버전을 유지하고, 서버 판정이 최종 권위다.

## 복제·재접속·저장

**확장 목표:** 서버는 `RunId`, 지형 스키마/설정, 전역 거래 revision, 청크 좌표별 최신 밀도와 revision을 보유한다. 지형을 항상 관련성 있게 제공하거나 명시적 스트리밍을 구현한다. 초도는 위 단일 밀도 스냅샷을 전송한다. 이 스냅샷의 밀도 배열(2,023개)은 UE 5.8.2 네트워크 설정 `MaxRepArraySize`의 기본값 2,048개(`NetworkSettings.h`의 `DefaultMaxRepArraySize`. 5.8.4 헤더에서도 같은 값임을 2026-11-10에 확인)에 거의 닿아 있다. 따라서 격자를 한 층이라도 늘리기 전에 아래 조각 복제를 먼저 구현하며, 한도 설정을 올리는 것으로 대신하지 않는다. 복제는 서버 소유 지형 액터의 bounded 최신 스냅샷을 사용하는 `FFastArraySerializer` 등 엔진 지원 상태 복제 후보로 구현한다. 항목은 청크 좌표·generation/revision·부분 번호/총수·정수 샘플 payload·검증값을 담은 **작은 고정 상한 조각**으로 쪼갠다. 정확한 한도는 실제 NetDriver 패킷/복제 검사에서 정하며 거대한 단일 배열/RPC 또는 무한 연산 로그를 가정하지 않는다.

**후속 구현:** 수신기는 런·generation별 조각을 모아 개수·좌표·길이·해시를 검증하고 완성된 청크 세트만 적용한다. 여러 청크가 한 거래에 걸리면 거래의 영향 목록과 각 revision을 함께 수신한 후 동시 전환한다. 이전 generation/중복은 버리고 누락·불일치·타임아웃은 소유 Controller 경유의 제한된 스냅샷 재요청으로 복구한다. 새 세대가 진행 중 이전 조각이 늦게 도착해도 되돌리지 않는다. 데이터 크기와 복구 요청 빈도를 제한하고 초기 수신 완료 전 해당 영역으로 입장·조작하지 않도록 안전 위치/입력 제한을 둔다. `OnRep` 순서, late relevance, 신뢰 채널 포화, 서버와 클라 충돌 준비 지연을 따로 시험한다. 실제 정책은 탐사 중 신규 참가 금지, 동일 ID 재접속 허용이다(같은 계정이 다시 들어오면 이전 접속을 끊고 새 접속을 받는다, 사용자 결정 2026-11-05). 일반 늦은 입장은 허용으로 바꾸지 않으며 재접속/관련성 복귀에서 동일 상태 복구한다.

현 프로토타입은 탐사 중 저장을 허용하지 않고 새 런에서 지형을 초기화한다. 따라서 첫 slice에서 기존 v2의 거점 저장/복원은 유지하며 탐사 지형을 영구 보존했다고 주장하지 않는다. 수동 저장은 없고 탐사 중 상태는 저장하지 않는다(시스템 작업리스트 1.1.0, D29 닫힘). 탐사 도중 지형 저장은 작업리스트의 나중 검토 후보이며, 그 범위가 확정될 경우 새 저장 스키마 버전으로 런 ID·생성 설정·완전한 청크 밀도·보강/여진 상태를 하나의 일관된 스냅샷으로 기록하고, 전부 검증한 뒤 설치한다. v2는 기존 필드로 정상 이관하거나 명시적으로 안전 거절하며 원본 저장을 덮지 않는다. 저장 원자성/손상 복구는 현재 별도 미구현 범위다.

## 보강·여진·붕괴·구조

이 절은 기획 기준과 프로토타입의 현재 구현이 다르다. 아래 첫 문단은 기획 기준, 둘째 문단은 프로토타입 현 구현, 그 뒤 두 문단은 설계 방향이다.

**기획 기준(시스템 작업리스트 1.1.0. 천장 판정과 예고 지연은 2026-11-10 기준 두 계열 모두 코드가 없다):** 보강과 붕괴는 **천장에서만** 일어난다. 천장은 레벨이 지정한 붕괴 가능 영역에서 굴착한 면이 아래를 향하는 곳이며 기준 각도는 시험 값(`CEILING_ANGLE_THRESHOLD`)이다. 벽·바닥 굴착면과 원래 자연 지형은 보강·붕괴 대상이 아니다. 손상됐지만 부서지지 않은 보강은 E로 무료 수리하고, 완전히 부서진 보강은 목재가 제거되어 수리할 수 없으며 다시 보강한다. 여진이 오면 무너질 천장 구간을 확정하고 먼지·작은 돌·갈라지는 소리로 국소 예고를 시작한 뒤 3~10초 무작위 시간(`COLLAPSE_WARNING_DELAY`) 후 잔해를 떨어뜨린다. 그사이 여진이 멎어도 예정대로 무너지며, **예고가 시작된 뒤의 보강·수리로 붕괴를 취소하지 않는다.** 굴착 주체(플레이어·몬스터)는 구분하지 않지만, 보강은 '플레이어가 직접 판 천장'으로 적혀 있어 몬스터가 판 천장의 보강·붕괴 처리는 확인 대상이다(PQ-28). 전역 숫자 카운트다운은 없다. 던전에는 갱도 굴착 규칙을 적용하지 않고, 던전 지정 벽 파괴는 검토 단계(D41)라 결정 전 구현 범위가 아니다(PQ-18). 타격당 진행량 `DIG_HIT_PROGRESS`와 실제 흙 제거 방식의 관계는 PQ-29, 보강 설치 시간 `SUP_INSTALL_TIME`(유지 입력)과 '미리 보기 후 확정' 처리의 관계는 PQ-30이다.

**프로토타입 현 구현(위 기획 기준과 다름, 2026-11-10 코드 확인):** `Prototype/World/DigetherExcavationTerrain.cpp`의 `CheckTremor`는 1초마다 여진 간격(남은 시간과 상승 여부로 계산)을 확인한다. 간격이 차면 **마지막 굴착 지점 한 곳**을 기준으로, 250cm 안에 강도가 남은 지지대가 있으면 강도만 1 줄이고, 없으면 반경 175cm를 `ServerRestoreAt`으로 **즉시** 원래 밀도로 되돌린다. Pawn·회수품·시체가 차지한 범위는 복원에서 뺀다. 굴착면이 천장인지 보는 각도 판정, 붕괴 가능 영역 지정, 국소 예고와 3~10초 지연, 예고 뒤 취소 불가 규칙은 구현돼 있지 않다. 다인 계열 계산 코어에는 밀도를 되돌리는 연산이 없다.

굴착 후 빈 공간의 서버가 검증한 표면/좌표에 보강 앵커를 배치한다. 신규 설치는 `RequestUseWood` 성공과 배치 확정을 한 거래로 처리하고 실패 시 소비하지 않는다. 기존 지지대 무료 보수, 여진에 따른 강도 감소는 유지하되 범위·수치·표시 방식은 시험값이다. 보강과 영역의 연결, 제거·붕괴·런 종료는 서버가 정리하고 상태를 복제한다. 예시 구현은 별도의 복제 지지대 액터와 좌표 기반 영향 반경이며, 지지대 위치를 클라이언트가 확정하지 않는다.

여진은 기존 호스트 제한 시간과 상승에 따른 일정 경로를 재사용한다. 영향을 받는 **이미 굴착된** 영역에서 서버가 붕괴량을 정해 밀도를 추가하고 같은 청크 변경 절차로 시각·충돌을 갱신한다. 플레이어 캡슐/회수품 내부에 충돌을 생성해 끼우지 않는다. 충돌이 들어갈 수 없는 점유 공간을 비워두고 논리적 붕괴 영역에 있는 유효 Pawn을 `RequestWorldBurialPawn`으로 매몰시킨다. 이 공간 제외와 보강 효과는 판정 순서가 명시된 시험 규칙이지 실제 흙 물리 시뮬레이션이 아니다. 매몰은 잔해가 덮치는 순간에만 판정하고(이미 떨어진 잔해에 들어가면 매몰 아님), 더 높은 단계의 추가 붕괴만 단계를 갱신하며 구조 게이지를 0으로 한다. 1·2단계는 느려진 이동(`BUR_MOVE_SLOW_RATIO`)으로 매몰 영역을 벗어나 해제하고 자력 탈출 키·게이지는 없다. 3단계는 동료 구조(대상당 1명 단독 점유)이며, 3단계 즉사는 실제 출발 인원이 1명인 탐사에서만 적용한다(방 인원·활동 인원 아님). 붕괴 영역의 흙은 동일한 구형 굴착으로 재제거할 수 있어야 한다. 여러 Pawn·이탈 Pawn·중복 여진·구조와 사망 경합, 아이템 내부 충돌과 빈 공간이 남는 경우를 실제 게임에서 검증한다. AI 경로 사용 시 충돌 확정 후 내비게이션 갱신/완료를 별도 검증하며, 초도에 경로가 준비됐다고 주장하지 않는다.

## 검증 항목과 한계

1. L1 순수 알고리즘: 구면 연산·전부 흙/빈 공간·표면 0 처리·중복/범위·여러 청크 모서리와 동일 공유면·정수 포화·정상/퇴화 삼각형, 역순 generation 및 중복 조각을 검사한다.
2. L2 실 에디터/패키지: 한 타격이 구형 흔적을 내고 연속 타격으로 옆과 아래 공간이 실제 확장되는지 카메라에서 확인한다. 바닥 trace와 캡슐 이동·낙하·벽의 전면 및 측/뒤/상단·굴착 후 계단을 통한 탈출·구조 후 지표 복귀·안전 내려놓기·지형 밖/승강기 통로, 흙과 분리된 기본 바닥, 충돌 cook 실패를 확인한다. 시각 변화만으로 통과시키지 않는다.
3. L3/M2: 호스트+클라에서 같은 지점, 청크 경계, 동시 타격·가림·속도/거리 위반, 붕괴/구조, 패킷 지연·순서 변경·재접속 시 density hash와 trace/이동 결과를 비교한다. 실제 탐사 중 신규 참가 거절을 유지한다. 이전 자동 런은 큐브 기준이므로 새 지형의 통과 증거가 아니다.
4. 저장: v2 기존 슬롯 불러오기·거점 저장/복원과 새 런 초기화 확인. 탐사 저장은 정책 확정 전 미지원임을 확인한다. 부하: 최대 시험 청크 수·연속 굴착·4인에서 프레임/서버 tick·cook 시간·네트워크/메모리를 기록한다. 프로파일 전에 성능 목표 달성을 주장하지 않는다.

제품 플레이에 필요한 정확한 지지 반경, 여진 확률, 깊이 제한, 수치 및 정식 저장 허용 상태는 아직 미정이다. 이 문서는 시험 값을 허용하며 이를 기획 승인으로 취급하지 않는다. 엔진 API는 로컬 헤더를 확인했을 뿐이고, 메시 알고리즘·충돌 전환·복제·BP·패키징·실 플레이의 성공 여부는 후속 검증이 필요하다. Claude Opus 5.5 `xhigh` 읽기 전용 교차 검증과 수용·후속 항목은 로컬 작업 기록에 남기며, 수정 후 재검증은 별도 결과를 확인한다.
