## 4. 최소 통합 구조

```text
플레이어/도구 입력 담당
  → 소유 Controller 또는 승인된 소유 컴포넌트의 서버 요청
  → 서버가 현재 도구·상태·거리·빈도를 검사하고 첫 유효 타격 결정
      ├ 플레이어/몬스터: 기존 공격 처리
      ├ 일반 암벽/허용되지 않은 대상: 지형 변화 없음
      └ 지정 흙: 굴착 영역 소유자에 요청
          → 후보 밀도 → 표면/충돌 준비 → 성공 시 상태 확정
          → 최신 지형 상태 복제 → 각 클라이언트가 같은 적용 경로 수행
          → 확정된 변경 영역을 AI/후속 갱도 시스템에 알림
```

클라이언트가 흙 Actor에 직접 Server RPC를 호출하게 하지 않는다. 그 액터는 보통 클라이언트 소유가 아니다. 클라이언트의 좌표·반경·결과도 신뢰하지 않는다. 현재 카메라 trace는 시험 입력이며 최종 삽/곡괭이 타격 판정 시점·sweep 모양은 플레이어 담당자와 정한다. 애니메이션 Notify나 클라 충돌만으로 지형 변경을 확정하지 않는다.

### 제안하는 최소 계약 — 아직 팀 공용 API가 아님

| 경계 | 입력 | 결과·책임 |
|---|---|---|
| 입력 → 서버 타격 담당 | 도구 사용 의도, 필요하면 서버 검증 가능한 조준 정보 | 서버가 장착 장비·허용 상태·타격을 결정. 클라 지정 제거량 금지 |
| 서버 타격 → 굴착 | 서버가 확인한 흙 대상/표면 위치, 서버 도구 설정의 반경, 필요한 행위 주체 | Changed / NoChange / Rejected / ApplyFailed, 적용 revision과 변경 영역 |
| 굴착 → 표현 | 확정 결과와 표면 위치 | 소리·파편·손맛. 효과 실패가 지형 판정을 되돌리지 않음 |
| 굴착 → AI·갱도 상태 | 흙 식별, 적용 revision, 변경된 공간 범위 | AI 경로 갱신과 굴착면 분류. 알림만으로 경로 준비 완료라 하지 않음 |
| 런 관리 → 지형 | 현재 런 식별, 초기 생성/종료 | 새로운 런 초기화, 종료된 런의 늦은 요청 무시 |

요청 ID·별도 이벤트 버스·범용 지형 프레임워크를 먼저 만들지 않는다. 작은 C++ 결과 구조와 일반 함수/델리게이트로 시작한다. 도구 수치는 기존 아이템 정의와 별도 굴착 설정 DataAsset 중 팀 소유권에 맞는 위치를 합의한다. 기존 ItemDefinition에 필드를 임의 추가하지 않는다.

## 5. 네트워크·후속 MUST 연결

서버만 밀도와 revision을 확정한다. 동일 흙 동시 타격은 최신 상태 기준으로 순서대로 처리하며, 변화 없는 요청은 새 성공이나 보상을 만들지 않는다. 서버 apply 성공 후 확정 상태를 복제하고 클라이언트는 준비 성공 후 applied revision을 바꾼다. 실패 시 이전 유효 상태 유지 + 준비 제한/복구가 필요하다.

처음 제품 수직 구현은 크기가 제한된 단일 흙 볼륨으로 검증하되, 그 상태로 전체 갱도 지원을 주장하지 않는다. 기존 2,023개 배열은 문서상 복제 배열 기본 한도에 가까우므로 현재 엔진/NetDriver 한도와 실제 직렬화 크기를 검증하기 전 격자를 늘리지 않는다. 한도 확대 설정으로 해결하지 않는다. 규모 확대 시에만 bounded 조각/청크 전송을 채택하며, generation·revision·완료된 조각 세트 검증·오래된 상태 거절을 설계한다. 구체 wire format은 이번에 확정하지 않는다.

2026-11-10 정정: [표면 개선](DAIN_EXCAVATION_SMOOTHING.md)에서 개인 맵의 격자가 1,254샘플에서 7,200샘플로 늘었다. 복제가 없는 1인 시험용 변경이며 네트워크 허용 크기를 정한 것이 아니다. 다만 7,200샘플은 단일 배열 복제의 기본 한도(2,048)를 넘으므로, 프로토타입처럼 밀도 배열을 통째로 복제하는 방식은 이 격자에 그대로 쓸 수 없다. E4를 시작하기 전에 조각·청크 전송을 포함한 동기화 방식과, 클라이언트가 초기 지형을 만드는 경로(현재 초기화는 서버 권한에서만 동작)를 먼저 정해야 한다. 어느 방식으로 할지는 결정 대기다.

기존 ID 재접속과 relevance 복귀에는 최신 밀도뿐 아니라 클라이언트 충돌 준비가 필요하다. 승인된 연결 완료 계약으로 준비 확인 전 조작/진입을 제한한다. 새 탐사 참가 금지와 호스트 이탈 종료는 기존 정책 유지. 탐사 지형 영구 저장과 새 세션 시스템은 구현하지 않는다.

| 후속 기능 | 굴착에서 지금 준비할 정보 | 지금 구현하지 않을 것 |
|---|---|---|
| 갱도 맵 선택·로드 S05 | 선택한 사전 제작 맵의 지정 흙 볼륨 배치·유효 설정, 보호 통로/던전 구분 | 갱도 형태 생성기·시드 관리 중복 구현 |
| 여진·붕괴 S09 | 초기/현재 밀도 비교, 변경 영역, 레벨 지정 붕괴 구역과의 교차, 천장 표면 분류 가능성 | 변경 박스 전체를 붕괴 가능 천장으로 처리, 임의 손상 공식 |
| 보강 S08 | 실제 굴착 천장과 표면 유효성 조회 | 몬스터가 판 천장 보강 여부 확정(PQ-28) |
| 매몰·구조 S10 | 붕괴 충돌 확정 시점·영역 전달 경계 | 흙 Actor가 체력·이동·구조 점유까지 소유 |
| AI | 충돌 확정 이후 변경 범위 통지 | NavMesh 존재만으로 몬스터 통과 완료 판정 |

초기/현재 밀도만으로 행위 주체·변경 역사를 모두 복원할 수는 없다. 후속 기획에서 주체 구분이 필요한 영역에는 최소한의 provenance가 필요하며 무한 타격 로그를 저장하지 않는다. 천장 판정은 표면 방향과 지정 붕괴 구역을 함께 사용한다. 붕괴 예고 3~10초·시작 후 취소 불가, 실제 출발 1인/3단계 즉사, 1·2단계 감속 탈출, 3단계 대상당 단독 구조는 최신 기획 기준을 따른다.

## 6. 혼자 진행할 것과 협의할 것

개인 경계 안에서 지금 진행 가능: 밀도/표면 알고리즘 검증, 닫힌 유한 볼륨, 빈 상태/회전/스케일 거절 처리, 충돌 실패 보존, 순수 데이터 테스트, 변경 범위 계산. 네트워크와 공용 캐릭터 계약을 임의로 확정할 필요가 없다.

| 협의 상대(실명/리뷰 계정 미확정) | 최소 질문 | 답이 필요한 작업 |
|---|---|---|
| 플레이어·공격 담당 | 공용 Pawn/도구 타격 함수는 무엇이고, 서버에서 첫 타격을 누가 확정하는가? | 실제 도구 연결·공격/굴착 분기 |
| 장비·인벤토리 담당 | 현재 장착 도구/양손 운반 상태를 서버에서 어떻게 조회하며 반경·간격 정의는 누가 소유하는가? | 도구 검증·장비별 차이 |
| 런·네트워크 담당 | 소유 요청 경로와 런 식별, 재접속 시 지형 준비 완료를 어디에 연결하는가? | RPC·재접속·런 초기화 |
| 레벨·AI 담당 | 허용 흙/보호 경계/붕괴 구역 배치 규칙, 지형 변경 후 AI 갱신 담당은? | 배치·내비게이션·천장 판정 |
| 개발 책임자 | 개인 소스의 최종 통합 경로와 공용 파일 리뷰 담당은? | 공용 API 변경·팀 맵 연결·PR |

기획 담당에게는 PQ-29의 진행량 추가 의미와 PQ-28 보강 범위만 필요할 때 묻는다. 현재 명시된 타격당 범위 제거 작업 전체를 이 질문 때문에 중단하지 않는다. 문의는 초안이며 팀에 자동 발송하지 않았다.

## 7. 실제 개발 순서와 완료 기준

| 순서 | 산출물 | 통과 조건 |
|---|---|---|
| E1 지형 코어 | 개인 Source 아래 제품용 순수 밀도/표면 계산과 테스트 | 닫힌 경계, 보호 영역 불변, 빈 지형, 회전, 무변화 타격, 잘못된 입력. Prototype/DainLab 원본 보존 |
| E2 지형 Actor | 유한 볼륨 설정·초기화·상태 적용·충돌 교체 | 벽/바닥/천장 반복 굴착 후 실제 Pawn 통과·낙하·복귀, 실패 이전 상태 보존 |
| E3 팀 도구 연결 | 합의한 실제 서버 타격 계약 연결 | 공용 캐릭터의 삽/곡괭이·공격 공존, 가림/거리/운반/생존·매몰 제한. 시험 입력 성공과 구분 |
| E4 네트워크 통합 | 최신 상태 복제·준비 상태·복구 | 2인 이후 4인 동시 타격, 지연/손실, 동일 ID 재접속, relevance 복귀. hash와 실제 충돌/이동 모두 일치 |
| E5 출시 검증 | 목표 규모 계측·패키지·후속 연결 | 5.8.4 패키지, 목표 동시 볼륨·4인 부하, AI 경로 갱신, 런 초기화. 목표 FPS/최소 사양/대역폭 예산은 팀 합의 후 판정 |

E1~E5는 출시 기능의 단계다. E1/E2 완료가 S07 전체 완료는 아니다. 다중 청크가 필요하면 E4/E5 사이 별도 규모 확장 작업으로 쪼갠다. 무작정 전체 월드를 한 메시/배열로 키우지 않는다. 현재 계산 코어는 격자 바깥 한 겹을 항상 빈 공간으로 두는 닫힌 볼륨이어서(`DigetherSoilField.cpp`의 경계 검사), 볼륨 두 개를 맞붙여도 사이가 관통되지 않는다. 이어진 지형으로 넓히려면 경계 계약부터 바꿔야 하며, 갱도 흙을 구획으로 둘지 연속으로 둘지는 결정 대기다.

### 다음 실행 작업 하나: E1

2026-11-10 현재: E1과 E2는 끝났다(아래 진행 갱신). 다음은 E3이며 실제 서버 도구 타격 계약을 확인한 뒤 연결한다. 아래 문단은 초기 작성 당시의 E1 범위다.

기존 `DigetherDainField`의 인덱스·구형 제거·표면 추출을 개인 `Game/Excavation/Dain/` 아래 제품용 계산 코드로 분리하는 변경안을 만든다. 첫 변경은 Character·Controller·Config·맵·플러그인을 건드리지 않는다. 입력은 유한 격자 설정/밀도/굴착 위치·반경, 출력은 변경 여부·변경 범위/표면이다. 도구 소유권·RPC는 계산 코드 밖에 둔다.

우선 검사는 열린 옆면 재현, 완전 제거 시 빈 표면 정상 처리, 허용/보호 경계, NaN·잘못된 배열 거절, 동일 요청의 무변화, triangle winding이다. 기존 Prototype 테스트를 검토해 가져올 수 있는 검사만 재사용하고 새 독립 지형의 결과를 별도 확인한다. Actor 설정/청크 API까지 한 번에 확정하지 않는다.
