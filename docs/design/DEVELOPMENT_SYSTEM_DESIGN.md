# DIGETHER 개발반 기능 구현 설계

후속 시험 구현과 실제 검증 범위는 [그레이박스 프로토타입](../prototype/PROTOTYPE.md)에 정리한다. 아래 논리 계약 전체를 프로토타입이 완성했다는 의미는 아니다.

기준일: 2026-10-28 · **구현 전 기술 제안**. [전체 시스템 설계](../SYSTEM_DESIGN.md)가 최신 작업 목록의 책임·게임 흐름과 데이터 계약을 관리한다. 이 문서는 구현 시 지켜야 할 기술 경계와 검증 방법이다. UE 5.8.2의 기존 기반과 지원 조사·근거는 [엔진 기능 활용 범위](UNREAL_FEATURE_COVERAGE.md)를 따른다. 아래 논리 이름은 구현된 API가 아니며 새로운 엔진 기능의 지원·프로젝트 적용을 주장하지 않는다.

## 상태 소유와 요청 경로

호스트가 규칙과 거래를 판정하고 클라이언트는 입력 의도를 보낸다. 접속 UI·개인 설정은 로컬 수명, 런과 지형·아이템 개체는 탐사 수명, 세션·게임 ID·일차·경제 장부·거래 완료 기록은 필요한 게임 수명을 갖도록 구분한다. Pawn 파괴는 지갑·사망 기록·아이템 장부 삭제를 뜻하지 않는다. 맵 이동 시 객체 자동 생존을 가정하지 않고 전환 대상과 인계를 명시한다.

GameMode 계열은 호스트의 월드 규칙, GameState 계열은 허용된 공개 뷰, PlayerState 계열은 허용된 플레이어 공개 정보, 소유 Controller/Character는 입력 요청 경로의 배치 후보다. 서버 원장과 월드 서비스는 자동 복제되지 않으며 별도 전달 경계가 필요하다. PlayerState에 넣는 것만으로 비공개가 되지 않는다. 표현 Widget·오디오·애니메이션은 권위 판정에 필요하지 않게 한다. 이 배치는 후보이며 실제 클래스와 맵 전환 방식은 기술 검증 후 채택한다.

요청은 소유 Controller/Character의 Server RPC로 받고 호출자는 연결로 확인한다. 호스트는 단계·거리·시야·대상 상태·소유·비용·빈도를 현재 상태로 확인하고, 통과하면 같은 서버 함수 안에서 차감·지급·이동을 함께 반영한다. 한 번만 성립하는 대상의 반복 요청은 현재 상태 검사로 거절한다. 반복이 정상인 구매는 요청 한 건을 한 건으로 처리하고, 실수 연타는 UI 처리 중 표시와 서버 빈도 제한으로 막는다. 기간·런 경계를 넘을 수 있는 요청은 `PeriodId`/`RunId`를 담아 현재 값과 대조한다. 거절 사유는 소유 클라이언트에 돌려준다. 클라이언트 요청 ID·예상 버전·준비/확정 영수증은 두지 않는다([2026-10-29 보정](../SYSTEM_DESIGN.md#2026-10-29-보정-steam-판매-기준과-요청-처리-단순화)). 시스템 작업리스트 1.1.0 공통 요청 처리는 구매·획득·납부·사망·탈출·정산 요청에 고유 번호를 붙이라고 적어 이 보정과 다르며, 기획 확인 대상이다([PQ-35](../planning/DECISIONS.md)). 확인 전에는 어느 쪽도 확정하지 않는다. 장기간 유효한 상태는 일회성 이벤트만으로 복구하지 않고 복제된 현재 상태로 제공한다.

개인 잔고·납부·히든 상세는 허용된 소유자의 뷰로만 전달한다. 숨기는 동작은 다른 플레이어에게 보이며 내용·가치의 상세는 소유자만 받는다. 중량으로 느려지거나 장비 구성이 달라지고 엘리베이터 무게 단계가 바뀌어 짐작할 여지는 기획 의도다. 정확한 내용·가치, 상세 Actor 정보·로그·시체 복구액의 비허용 전달은 차단한다. 호스트는 권위 데이터를 보유하므로 호스트에 대한 비밀 보장은 별도 요구다. 비활성·관련성 재진입 때도 현재 버전과 허용 정보를 복구한다.

## 도메인별 처리

- 지형: 갱도의 허용 3D 흙 볼륨(밀도 지형)과 던전 지정 파괴 벽을 별도 판정한다. 지형 수정의 기준 버전, 결과와 충돌·AI 경로 준비를 연결한다. 늦은 비동기 결과가 새 버전을 덮지 못하게 한다. 생성 결과는 연결·귀환 가능성을 확인하고 실패를 정상 시작으로 표시하지 않는다.
- 아이템: 정의 ID와 고유 인스턴스 ID를 분리하고 월드·소지·회수 건의 유효 위치를 한 곳으로 제한한다. 한 아이템의 중량은 한 번만 더한다. 양손 회수품·시체·장비의 슬롯과 보존 규칙은 다르다.
- 생존·구조: 사망/탈출은 호스트에서 먼저 확정된 하나만 인정한다. 대상별 구조 점유는 한 명이며 중단·사망·이탈·연결 해제 시 진행과 점유를 정리한다. 사망 ID와 시체 복구 완료 기록을 분리해 중복 이벤트를 방지한다.
- 엘리베이터: 동결 명세와 실제 운행 성공을 분리하고 편별 회수 건 ID를 유지한다. 동결 시점의 기획 기준은 문이 완전히 닫힌 순간이며 문 닫힘 중 무게 초과(문 재개방·게이지 0)·시간 종료(갱도 대기 처리, 문 닫힘 완료가 같은 시점이면 문 닫힘 우선) 처리가 따로 있다(시스템 작업리스트 1.1.0, [전체 설계](../SYSTEM_DESIGN.md#출발운행종료-장벽)). 문은 게이지 완료 시 자동으로 닫히고(임시 3초) 닫히는 동안 탑승할 수 있으며 문턱 밀어내기는 폐기했다(사용자 결정 2026-11-05). 문 닫힘 단계와 문 닫힌 순간 목록 고정은 구현(실행 검증 일부)이다. 출발·상승 문 닫힘 시간 분리(`HubDoorCloseSeconds`·`MineDoorCloseSeconds`, 각 3초 임시), 레버 한 번 완료로 자동 닫힘, 닫히는 중 탑승, 문 닫힘 중 무게 초과 재개방, 문 닫힘 완료 우선 판정, 거점 사슬 소집(MVP 순간이동, 클라이언트 암전은 BP 이벤트 `OnChainSummoned` 연결 필요), 갱도 상승 레버 안·밖 2개(먼저 잡은 레버만)는 구현(자동 테스트 통과, M2·연출 미검증)이다. 일반 상승은 최대 2회로 확정이며 코드도 2로 고정했다. 중량 초과·시간 종료·운행 중 종료를 상태별로 처리한다. 이전 성공 건을 뒤늦은 편의 취소로 지우지 않는다.
- 경제: 일반 정산·히든 지급·사망 손실·시체 복구·구매·납부·해금을 같은 개인 장부에서 직렬화한다. 출발 인원과 생존 자격은 고정된 런 결과에서 계산한다. 목표 달성 및 마감 경합은 호스트 처리 순서로 단일 결과를 얻는다.
- 저장: 수동 저장 없이 탐사 정상 완료 후·할당량 달성·호스트 정상 거점 종료·5일차 실패 귀환에 자동 저장하고, 탐사 중·정산 중간 상태는 저장하지 않는다. 공통 출발 로딩 실패는 확정된 준비·4일차 마감을 유지한 채 같은 일차 거점으로 돌아가며 일차 시작 저장으로 되돌리지 않는다. 저장 실패는 알리고 재시도하며 출발을 막지 않는다(시스템 작업리스트 1.1.0 S30). 탐사 정상 완료 후·할당량 달성·호스트 거점 종료 저장, 10초 재시도(임시), 메모리 기준점 로딩 실패 복귀(호출 경로는 실제 로딩 계층이 없어 아직 없음), wire v5·슬롯 3개(임시)는 구현(자동 테스트 통과, M2 미검증)이다. 버전, 쓰기 실패, 구버전·손상 데이터, 복구 중 중복 지급을 검증한다.
- AI·음성: 종별 행동은 아직 미설계며 지형 변화 후 경로를 재평가한다. 살아 있는 플레이어와 관전자의 음성 허용 경로를 분리한다. 제공자, 인증·재접속 및 실제 전달 차단은 채택 후 검증한다.
- 외형·배치: 외형 값은 판정에서 분리한다. 거점 배치는 호스트에서 점유·겹침·동선을 검증하고 유효 상태를 전달한다. 잘못된 저장 배치는 전체 기본 배치 복구로 처리한다.

## 구현 단계와 검증

기능 구현 순서(①~⑦)와 우선순위 표기(P2 등)는 [전체 시스템 설계](../SYSTEM_DESIGN.md)의 개발 순서를 따른다. 기존 코드의 구조 이전 단계는 [코드 구조 계획](CODE_STRUCTURE_PLAN.md)의 P0~P7이며 기능 우선순위 P2와 다른 구분이다. 콘텐츠별 값과 도입이 미정인 기능은 승인 데이터나 시험용 픽스처로 구분한다. Editor 도구는 게임 권위 상태를 소유하지 않는다. 공통 상태라는 이유로 미채택 기능을 선구현하지 않는다.

문서 L1은 출처·링크·상충 검사를 뜻한다. 구현 후 네트워크·공유 상태는 L1~L3 및 M2, 실제 음성·플랫폼 서비스는 M3를 수행한다. 1인과 M2(호스트+원격 3, 별도 프로세스 4인)를 각각 확인한다. 그 전에 PIE 리슨 서버+클라이언트 2의 3인으로 서버→클라, 클라→서버, 클라↔클라 경로를 예비 검사한다. 검사에는 동시 요청·반복 입력·지연·연결 이탈·저장 실패를 포함한다. 상세 수용은 [검증 계획](../verification/VERIFICATION_PLAN.md)과 자료의 T 시나리오를 따른다. 빌드·실행·수용은 이 문서 작성으로 완료되지 않았다.

## 구현 규칙

2026-10-29 채택한 프로젝트 구현 규칙이다. 일반 원칙은 [네트워크 권위](../unreal/NETWORK_AUTHORITY.md)·[개발 패턴](../unreal/ENGINEERING_PATTERNS.md)을 따르고 여기서는 DIGETHER의 구체 선택만 적는다. 기존 프로토타입 코드는 2026-11-04부터 수정하지 않고, 이 규칙은 `Game/`의 새 코드에 적용한다([코드 구조 계획](CODE_STRUCTURE_PLAN.md)).

### 프레임워크 역할

- UE 기본 프레임워크의 역할을 지킨다. GameMode는 서버에만 있고 규칙을 판정한다. GameState는 모두에게 보일 공통 상태, PlayerState는 플레이어별 공개 상태(개인 값은 `COND_OwnerOnly`), Pawn/Character는 이동·표현, HUD/Widget은 표시만 맡는다. 관전 전환(S17·S22)은 SpectatorPawn 계열을 우선 후보로 검토한다.
- PlayerController는 서버에 전원 몫이 있고 클라이언트에는 자기 것 하나만 있다. 클라이언트 코드는 다른 플레이어의 Controller 값(시점 회전 등)을 읽지 않는다.
- `GetPlayerController(0)`·`GetPlayerCharacter(0)`처럼 인덱스로 고르는 접근은 실행 머신마다 결과가 달라 게임 로직에 쓰지 않는다. 위젯은 소유 플레이어(`GetOwningPlayer`), 서버 로직은 RPC가 들어온 Controller를 쓴다.

### 복제와 RPC

- 지속 상태는 `Replicated` 또는 `ReplicatedUsing=OnRep_이름` 프로퍼티로 전파한다. 신규 참가는 출발 게이지 완료~결과 크레딧 동안 금지하며(시스템 작업리스트 1.1.0 S01. 문 닫힘 중 참가 잠금은 구현(실행 검증 일부), 게임 오버 중 잠금·관전 합류는 구현(자동 테스트 통과, M2 미검증)), 그 밖의 허용된 입장, 동일 ID 재접속(이전 접속을 끊고 새 접속 수락, 사용자 결정 2026-11-05)·관련성 복귀 때 현재 값을 복원한다. 클라이언트→서버 입력은 Server RPC로 보내고, 서버→클라이언트 RPC(Client·Multicast)는 거절 사유 통지나 놓쳐도 되는 연출 같은 일회성 사건에만 쓴다.
- RPC 함수 이름은 `Server_`·`Client_`·`Multicast_` 접두사로 실행 위치를 드러낸다. 구현은 `_Implementation`에 둔다.
- 상태를 바꾸는 Server RPC는 `Reliable`, 이펙트·사운드 같은 연출 Client/Multicast RPC는 `Unreliable`을 기본으로 한다. 매 프레임 입력을 Reliable로 보내지 않는다.
- Server RPC는 클라이언트가 소유한 PlayerController 또는 빙의한 Character에서만 보낸다. 월드 물체와의 상호작용은 Controller/Character의 Server RPC가 대상 액터를 인자로 넘기고 서버가 거리·상태를 검증한다. 여러 명이 함께 쓰는 물체의 소유권을 클라이언트로 옮기는 방식은 쓰지 않는다.
- 상호작용 대상(아이템·레버·엘리베이터·보강 지점 등)은 공통 상호작용 인터페이스(`UInterface`)를 구현한다. 호출 쪽은 대상의 구체 클래스를 몰라도 된다.
- 맵에 고정된 정적 물체는 `Net Load on Client`로 각자 로드하고 복제하지 않는다. 움직이거나 상태가 바뀌는 공유 물체만 복제하고, 컴포넌트 단위 변화는 해당 컴포넌트 복제를 켠다.
- 액터별 `NetUpdateFrequency`를 조정한다. 정지 대상은 낮추거나 휴면시키고, 변경될 때만 깨운다.
- 권위 판정은 UI·머티리얼·Niagara·사운드 생성에 의존하지 않는다. 현재 네트워크는 리슨 서버이며 전용 서버 출시 구조를 채택한 것은 아니다. 헤드리스·전용 서버 모드로 자동 검사할 때는 표현을 생략하되 리슨 서버의 호스트 화면에는 원격 캐릭터의 월드 표현도 적용한다. 개인 UI는 로컬 소유자에게만 적용하며, 월드 표현까지 `IsLocallyControlled()`로 제한하지 않는다.

### 장비 상태와 행동 표현

2026-11-04 문서 반영. 아래는 후속 구현 지침이며 장비 교체·원격 애니메이션의 구현 완료를 뜻하지 않는다. 세부 클래스·전송 필드·에셋은 구현 범위에 맞춰 확정한다.

- 장비 교체·획득·버리기는 소유 Controller/Character로 요청하고 서버가 현재 소지·생존·양손 운반 제한·대상·거리·빈도를 검증한 뒤 확정한다. 이후 장비 사용 판정도 서버가 확정한 장착 상태를 참조한다. UI의 선택 슬롯을 서버 장착 완료로 간주하지 않는다.
- 현재 장착·부착 상태는 지속 상태로 복제한다. 동료에게는 허용된 장비 외형·운반 표현에 필요한 최소 정보만 제공하며, 인벤토리 전체·히든 내용·가치 상세를 함께 공개하지 않는다. 재접속·관련성 복귀 때 과거 교체 RPC를 재생하지 않고 현재 상태에서 복원한다.
- 장비 UI와 월드 외형 갱신은 [네트워크 권위의 표현 규칙](../unreal/NETWORK_AUTHORITY.md#규칙)을 따른다. C++ 서버 변경 경로와 클라이언트 OnRep가 공통 표현 함수를 사용하고, UI·메시·참조 에셋이 늦게 준비되면 최신 상태를 다시 적용한다. 비동기 로드의 오래된 완료가 새 장비를 덮지 않게 한다.
- 굴착·장비 공격은 서버가 도구·대상·거리·간격과 결과를 판정한다. 지형·피해·아이템 변경은 지속 상태로 전달하고 휘두르기·타격음·파편은 일회성 표현으로 분리한다. 연출 누락으로 판정이 취소되거나, 연출 수신으로 피해가 재적용되지 않아야 한다. 로컬 예측 연출을 채택하면 서버 확인과 중복 재생·거절 정리를 별도로 설계한다.
- 동료에게 보여야 할 일회성 효과에 Multicast를 쓸 경우 서버에서 관련 클라이언트에 복제되는 Character/Actor를 경유한다. PlayerController의 Multicast가 모든 플레이어에게 도착한다고 가정하지 않는다. 장비 Actor를 쓰는 경우 생성·장착·해제는 서버가 확정하고, `SetOwner`를 서버 authority 이전이나 게임상 귀속 소유권으로 해석하지 않는다.
- 획득은 기존 조준 상호작용을 유지한다. Overlap 자동 획득·재습득 대기처럼 기획에 없는 획득 규칙을 임의로 추가하지 않는다. 타이머가 필요한 구현은 해제·재장착·파괴 때 취소와 유효성을 확인해 오래된 콜백이 장착 장비의 충돌을 다시 켜지 않게 한다.

현재 C++ 확인(2026-11-04): 프로토타입은 `ServerDig` → 서버 지형 판정 → `ClientDigConfirmed`로 조작자에게만 휘두르기를 재생하며 도구 메시도 소유자 전용이다. 인벤토리 `PrivateState`는 `COND_OwnerOnly`, 헤드랜턴은 `OnRep_Headlamp`와 서버 공통 표현 경로를 사용한다. 동료용 장비 외형·굴착 모션은 후속 구현 대상이며 Blueprint 내부와 실행 결과는 이번 확인 범위에 포함하지 않는다.

### 전송 좌표의 정밀도

좌표를 실제로 전송하는 RPC·복제 필드에 한해 `FVector_NetQuantize` 계열을 검토한다. 서버에서 자체 계산하는 굴착 판정점에 새 좌표 RPC를 추가할 이유로 쓰지 않는다. UE 5.8.4 `Engine/NetSerialization.h`와 [공식 API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FVector_NetQuantize) 기준으로 `FVector_NetQuantize`는 소수점 0자리, `FVector_NetQuantize10`은 1자리, `FVector_NetQuantize100`은 2자리다. 판정과 표현의 허용 오차·좌표 범위·전송 빈도에 맞춰 선택하며, 굴착 경계·장거리 좌표에서 결과 일치와 대역폭을 측정한 후 적용한다. 일괄 치환이나 성능 개선 완료를 뜻하지 않는다.

### 캐릭터와 애니메이션

- 정식 스켈레탈 캐릭터에 AimOffset을 도입할 때 조준 방향은 `GetBaseAimRotation()`을 사용하고 Pitch를 `FRotator::NormalizeAxis`로 정규화한 뒤 애니메이션 입력 범위에 맞춘다. 원격 플레이어의 Controller를 직접 읽거나 조준 각도를 별도 RPC로 매 프레임 중계하지 않는다. 현재 프로토타입은 숨긴 SkeletalMesh 대신 정적 실린더 몸체를 쓰며, 헤드랜턴은 이미 `GetBaseAimRotation()`을 사용한다. 기존 Pitch 결함이 재현됐다는 의미는 아니다.
- 회전은 판정 기준과 화면에 보이는 기준을 구분한다. 표현용 Yaw를 계산할 때 액터 회전과 보간된 메시 회전 중 실제 렌더 경로에 맞는 값을 선택하고 메시의 기본 축 보정을 반영한다. `HasAuthority()`만으로 호스트가 보는 원격 캐릭터까지 항상 액터 회전을 쓰도록 고정하지 않는다. 로컬 조작자·호스트의 원격 캐릭터·클라이언트의 Simulated Proxy를 각각 검사한다.
- 조준·제자리 회전 값은 AnimInstance에 전달되는 일관된 프레임의 데이터로 계산한다. 게임 스레드에서 필요한 값을 수집하거나 지원되는 thread-safe/property access 경로를 사용하며, 워커 스레드의 애니메이션 업데이트에서 Controller·Actor·Component를 임의로 접근하지 않는다. 계산 위치 이동만으로 떨림이 해결됐다고 판정하지 않는다.
- 제자리 회전과 장비별 Linked Anim Layer는 정식 스켈레톤·모션 준비 후 조건부로 적용한다. 시작/종료 각도·회전 속도는 모션에 맞춰 정하고, 이동·낙하·사망·장비 변경 시 중단/초기화와 방향 반전·±180도 경계를 검증한다. 외부 예시의 모션·각도 수치를 프로젝트 값으로 고정하지 않는다. 캡슐 회전·메시 오프셋·루트 모션 중 처리 방식은 기존 이동 복제와 비교한 후 선택한다.
- AnimInstance C++ 변수 이름은 연결된 애니메이션 블루프린트 변수와 맞춘다. 상태 머신 전이 규칙은 State Alias·Conduit로 정리한다.

### 코드 구조

- 캐릭터 기능은 ActorComponent로 나눈다(이동·상호작용·인벤토리·굴착 도구). 분리 후 기존 동작을 회귀 검사한다.
- 시스템 간 알림은 타입 있는 델리게이트로 한다. C++ 내부는 `DECLARE_MULTICAST_DELEGATE`, Blueprint 노출이 필요하면 `DECLARE_DYNAMIC_MULTICAST_DELEGATE`, BP에서 부를 함수는 `UFUNCTION(BlueprintCallable)`로 연다.
- 세션·저장·플랫폼 연동 같은 전역 서비스는 Subsystem(GameInstance·World)으로 둔다. 같은 기능에 C++용·BP용 요청 함수를 따로 만들지 않는다. 함수 하나를 두고, BP 비동기 노드가 필요하면 그 함수를 감싼다.
- RPC `WithValidation` 실패는 연결을 끊으므로 정상 클라이언트가 만들 수 없는 값에만 쓴다. 길이 초과·잔고 부족 같은 일반 오류는 실패 응답으로 돌려준다.

### 작업 방식

- RPC·`UPROPERTY`·`UFUNCTION` 선언을 바꾸는 빌드는 에디터를 닫고 한다. 에디터를 켠 채 빌드하면 Blueprint 재인스턴싱으로 기본값이 깨질 수 있다.
- 멀티플레이 기능은 먼저 PIE `Play As Listen Server` 3인(호스트+클라이언트 2)으로 서버→클라, 클라→서버, 클라↔클라를 예비 확인한 뒤 M2(호스트+원격 3, 별도 프로세스 4인)로 검증한다.
- AI에게 구현을 맡길 때는 계획 문서를 먼저 받아 검토·수정한 뒤 구현을 요청한다.

- **수치 표**: 곡선·단계표는 CurveTable/DataTable을 보조로 쓰되 같은 값을 두 곳에 두지 않는다([데이터 작업](../unreal/DATA_WORKFLOW.md)). 런 시작 시 고정할 값(R01·T65)은 정의 자산에서 읽어 런 스냅샷에 복사한다.

C++에서 쓰는 태그는 네이티브 태그 매크로로 선언하고 `GameplayTags` 모듈 의존을 추가한다. 동시에 참일 수 없는 상태(생존/매몰/사망/관전)는 enum 상태머신을 원본으로 두고 태그는 조회 보조로만 쓴다.
- **범위 밖**: Gameplay Ability System 도입은 별도 결정이다. 프로토타입 상수를 정의 자산으로 옮기는 작업은 사용자 범위 확인 후 진행한다.

### 복제 규모와 월드 인계

회수품·잔해·보강·몬스터의 수가 늘면 모든 개체를 항상 전송하는 방식을 기본으로 두지 않는다. 정지 대상의 휴면과 변경 시 깨우기, 거리·관련성, 갱신 빈도, 소유자 전용 뷰, 비권위 연출 분리를 대상별로 결정한다. 기존 UE 5.8.2 소스 조사에서 확인한 Actor의 휴면·관련성·빈도 API는 [엔진 기능 안내](UNREAL_FEATURE_COVERAGE.md)를 따른다. 재진입 때 최신 상태·버전을 받고 은닉 정보가 전달되지 않는지 측정한다. Iris/Legacy 등 구체 방식과 예산은 미결이다.

월드 전환 없이 유지하는 장부와, 서버 GameInstanceSubsystem에 월드 객체 포인터 없이 데이터로 인계하는 후보를 비교한다. Seamless travel과 PlayerState 복사 경로도 비교하되 자동 보존 범위와 재생성 순서를 직접 확인한다. 비활성 PlayerState는 요구 전체를 해결하지 않으며 현재 GameModeBase와 동일시하지 않는다. 저장소·월드 파괴·세션 종료의 각 정리 조건을 구현 브리프에 명시한다.

### 정보·음성·튜닝

관전 UI는 대상의 허용된 공개 뷰만 사용하고 잔고·히든 슬롯을 받지 않는다. 엘리베이터의 정확한 중량은 호스트 판정에 사용하고 다른 화면에는 승인된 단계만 전달한다. 히든 줍기의 숨기는 동작은 모두에게 보이되 손 표시·월드 Actor·복제·로그에 내용이나 가치의 상세가 노출되지 않도록 하며 시체 복구액을 운반자에게 전달하지 않는다. 시각적으로 감추는 것과 데이터 수신을 차단하는 것을 구분한다.

몬스터 음성 감지는 호스트가 참가자의 음성 활동을 신뢰 가능한 방식으로 받을 수 있는지에 의존한다. 제공자에 따라 오디오 경로가 호스트를 통과하지 않을 수 있고 클라이언트 단독 보고는 위조될 수 있다. 서비스의 활동 신호·서버 접근·개인정보 및 지연을 비교하는 ADR/검증이 필요하며 지원을 가정하지 않는다. 전체 R01~R14와 테스트 빌드 동기화 계약은 [전체 시스템 설계](../SYSTEM_DESIGN.md)를 따른다.

### 착수 근거와 완료 조건

현재 게임 프로젝트는 Third Person 및 변형 템플릿과 두 Editor 워크벤치가 존재한다. 템플릿 전투, 의존 선언, 에디터 도구는 DIGETHER의 S 기능이 구현됐다는 증거가 아니다. 실제 확인과 검사 범위는 [프로필](../project/PROJECT_PROFILE.md), [개발 도구 안내](../tools/DEVELOPER_TOOLS.md)를 따른다.

각 구현 브리프에 S ID·승인 개정·입출력·소유 경계·수명·미결 항목·작업 경로와 정상/실패/경합 검사·담당 상태를 남긴다. 공유 맵·에셋의 담당과 잠금을 확인한다. 후보 ADR은 호스트 세션·ID/재접속, 복제 방식과 예산, 지형·충돌, 월드/장부 인계, 음성 및 몬스터 음성 감지, 저장 기준점·복구, 데이터/튜닝 원본이다. 구현 전 실험·의사결정 근거와 영향을 기록하며 이름만으로 채택으로 취급하지 않는다. 문서 완료와 L1~L3/M2·M3 실행 완료를 구분한다.
