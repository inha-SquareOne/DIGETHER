# DIGETHER 개발반 기능 구현 설계

후속 시험 구현과 실제 검증 범위는 [그레이박스 프로토타입](../prototype/PROTOTYPE.md)에 정리한다. 아래 논리 계약 전체를 프로토타입이 완성했다는 의미는 아니다.

기준일: 2026-10-28 · **구현 전 기술 제안**. [전체 시스템 설계](../SYSTEM_DESIGN.md)가 최신 작업 목록의 책임·게임 흐름과 데이터 계약을 관리한다. 이 문서는 구현 시 지켜야 할 기술 경계와 검증 방법이다. UE 5.8.2의 기존 기반과 지원 조사·근거는 [엔진 기능 활용 범위](UNREAL_FEATURE_COVERAGE.md)를 따른다. 아래 논리 이름은 구현된 API가 아니며 새로운 엔진 기능의 지원·프로젝트 적용을 주장하지 않는다.

## 상태 소유와 요청 경로

호스트가 규칙과 거래를 판정하고 클라이언트는 입력 의도를 보낸다. 접속 UI·개인 설정은 로컬 수명, 런과 지형·아이템 개체는 탐사 수명, 세션·게임 ID·일차·경제 장부·거래 완료 기록은 필요한 게임 수명을 갖도록 구분한다. Pawn 파괴는 지갑·사망 기록·아이템 장부 삭제를 뜻하지 않는다. 맵 이동 시 객체 자동 생존을 가정하지 않고 전환 대상과 인계를 명시한다.

GameMode 계열은 호스트의 월드 규칙, GameState 계열은 허용된 공개 뷰, PlayerState 계열은 허용된 플레이어 공개 정보, 소유 Controller/Character는 입력 요청 경로의 배치 후보다. 서버 원장과 월드 서비스는 자동 복제되지 않으며 별도 전달 경계가 필요하다. PlayerState에 넣는 것만으로 비공개가 되지 않는다. 표현 Widget·오디오·애니메이션은 권위 판정에 필요하지 않게 한다. 이 배치는 후보이며 실제 클래스와 맵 전환 방식은 기술 검증 후 채택한다.

요청은 소유 Controller/Character의 Server RPC로 받고 호출자는 연결로 확인한다. 호스트는 단계·거리·시야·대상 상태·소유·비용·빈도를 현재 상태로 확인하고, 통과하면 같은 서버 함수 안에서 차감·지급·이동을 함께 반영한다. 한 번만 성립하는 대상의 반복 요청은 현재 상태 검사로 거절한다. 반복이 정상인 구매는 요청 한 건을 한 건으로 처리하고, 실수 연타는 UI 처리 중 표시와 서버 빈도 제한으로 막는다. 기간·런 경계를 넘을 수 있는 요청은 `PeriodId`/`RunId`를 담아 현재 값과 대조한다. 거절 사유는 소유 클라이언트에 돌려준다. 클라이언트 요청 ID·예상 버전·준비/확정 영수증은 두지 않는다([2026-10-29 보정](../SYSTEM_DESIGN.md#2026-10-29-보정-steam-판매-기준과-요청-처리-단순화)). 장기간 유효한 상태는 일회성 이벤트만으로 복구하지 않고 복제된 현재 상태로 제공한다.

개인 잔고·납부·히든 상세는 허용된 소유자의 뷰로만 전달한다. 숨기는 동작은 다른 플레이어에게 보이며 내용·가치의 상세는 소유자만 받는다. 중량으로 느려지거나 장비 구성이 달라지고 엘리베이터 무게 단계가 바뀌어 짐작할 여지는 기획 의도다. 정확한 내용·가치, 상세 Actor 정보·로그·시체 복구액의 비허용 전달은 차단한다. 호스트는 권위 데이터를 보유하므로 호스트에 대한 비밀 보장은 별도 요구다. 비활성·관련성 재진입 때도 현재 버전과 허용 정보를 복구한다.

## 도메인별 처리

- 지형: 갱도 굴착 가능 오브젝트와 던전 지정 파괴 벽을 별도 판정한다. 지형 수정의 기준 버전, 결과와 충돌·AI 경로 준비를 연결한다. 늦은 비동기 결과가 새 버전을 덮지 못하게 한다. 생성 결과는 연결·귀환 가능성을 확인하고 실패를 정상 시작으로 표시하지 않는다.
- 아이템: 정의 ID와 고유 인스턴스 ID를 분리하고 월드·소지·회수 건의 유효 위치를 한 곳으로 제한한다. 한 아이템의 중량은 한 번만 더한다. 양손 회수품·시체·장비의 슬롯과 보존 규칙은 다르다.
- 생존·구조: 사망/탈출은 호스트에서 먼저 확정된 하나만 인정한다. 대상별 구조 점유는 한 명이며 중단·사망·이탈·연결 해제 시 진행과 점유를 정리한다. 사망 ID와 시체 복구 완료 기록을 분리해 중복 이벤트를 방지한다.
- 엘리베이터: 게이지 완료의 동결 명세와 실제 운행 성공을 분리하고 편별 회수 건 ID를 유지한다. 중량 초과·시간 종료·운행 중 종료를 상태별로 처리한다. 이전 성공 건을 뒤늦은 편의 취소로 지우지 않는다.
- 경제: 일반 정산·히든 지급·사망 손실·시체 복구·구매·납부·해금을 같은 개인 장부에서 직렬화한다. 출발 인원과 생존 자격은 고정된 런 결과에서 계산한다. 목표 달성 및 마감 경합은 호스트 처리 순서로 단일 결과를 얻는다.
- 저장: 완료된 정산·복구·귀환 및 전환 결과를 저장한다. 로딩 오류 복원은 일차 시작 자동 저장을 기준으로 개인과 팀 상태를 함께 되돌린다. 버전, 쓰기 실패, 구버전·손상 데이터, 복구 중 중복 지급을 검증한다.
- AI·음성: 종별 행동은 아직 미설계며 지형 변화 후 경로를 재평가한다. 살아 있는 플레이어와 관전자의 음성 허용 경로를 분리한다. 제공자, 인증·재접속 및 실제 전달 차단은 채택 후 검증한다.
- 외형·배치: 외형 값은 판정에서 분리한다. 거점 배치는 호스트에서 점유·겹침·동선을 검증하고 유효 상태를 전달한다. 잘못된 저장 배치는 전체 기본 배치 복구로 처리한다.

## 구현 단계와 검증

구현 순서와 P0/P1/P2는 [전체 시스템 설계](../SYSTEM_DESIGN.md)의 개발 순서를 따른다. 콘텐츠별 값과 도입이 미정인 기능은 승인 데이터나 시험용 픽스처로 구분한다. Editor 도구는 게임 권위 상태를 소유하지 않는다. 공통 상태라는 이유로 미채택 기능을 선구현하지 않는다.

문서 L1은 출처·링크·상충 검사를 뜻한다. 구현 후 네트워크·공유 상태는 L1~L3 및 M2, 실제 음성·플랫폼 서비스는 M3를 수행한다. 1인과 M2(호스트+원격 3, 별도 프로세스 4인)를 각각 확인한다. 그 전에 PIE 리슨 서버+클라이언트 2의 3인으로 서버→클라, 클라→서버, 클라↔클라 경로를 예비 검사한다. 검사에는 동시 요청·반복 입력·지연·연결 이탈·저장 실패를 포함한다. 상세 수용은 [검증 계획](../verification/VERIFICATION_PLAN.md)과 자료의 T 시나리오를 따른다. 빌드·실행·수용은 이 문서 작성으로 완료되지 않았다.

## 구현 규칙

2026-10-29 채택한 프로젝트 구현 규칙이다. 일반 원칙은 [네트워크 권위](../unreal/NETWORK_AUTHORITY.md)·[개발 패턴](../unreal/ENGINEERING_PATTERNS.md)을 따르고 여기서는 DIGETHER의 구체 선택만 적는다. 기존 프로토타입 코드의 일괄 수정은 별도 작업으로 범위를 확인한 뒤 진행한다.

### 프레임워크 역할

- UE 기본 프레임워크의 역할을 지킨다. GameMode는 서버에만 있고 규칙을 판정한다. GameState는 모두에게 보일 공통 상태, PlayerState는 플레이어별 공개 상태(개인 값은 `COND_OwnerOnly`), Pawn/Character는 이동·표현, HUD/Widget은 표시만 맡는다. 관전 전환(S17·S22)은 SpectatorPawn 계열을 우선 후보로 검토한다.
- PlayerController는 서버에 전원 몫이 있고 클라이언트에는 자기 것 하나만 있다. 클라이언트 코드는 다른 플레이어의 Controller 값(시점 회전 등)을 읽지 않는다.
- `GetPlayerController(0)`·`GetPlayerCharacter(0)`처럼 인덱스로 고르는 접근은 실행 머신마다 결과가 달라 게임 로직에 쓰지 않는다. 위젯은 소유 플레이어(`GetOwningPlayer`), 서버 로직은 RPC가 들어온 Controller를 쓴다.

### 복제와 RPC

- 지속 상태는 `Replicated` 또는 `ReplicatedUsing=OnRep_이름` 프로퍼티로 전파한다. 늦은 참가자·재접속자도 같은 경로로 현재 값을 받는다. 클라이언트→서버 입력은 Server RPC로 보내고, 서버→클라이언트 RPC(Client·Multicast)는 거절 사유 통지나 놓쳐도 되는 연출 같은 일회성 사건에만 쓴다.
- RPC 함수 이름은 `Server_`·`Client_`·`Multicast_` 접두사로 실행 위치를 드러낸다. 구현은 `_Implementation`에 둔다.
- 상태를 바꾸는 Server RPC는 `Reliable`, 이펙트·사운드 같은 연출 Client/Multicast RPC는 `Unreliable`을 기본으로 한다. 매 프레임 입력을 Reliable로 보내지 않는다.
- Server RPC는 클라이언트가 소유한 PlayerController 또는 빙의한 Character에서만 보낸다. 월드 물체와의 상호작용은 Controller/Character의 Server RPC가 대상 액터를 인자로 넘기고 서버가 거리·상태를 검증한다. 여러 명이 함께 쓰는 물체의 소유권을 클라이언트로 옮기는 방식은 쓰지 않는다.
- 상호작용 대상(아이템·레버·엘리베이터·보강 지점 등)은 공통 상호작용 인터페이스(`UInterface`)를 구현한다. 호출 쪽은 대상의 구체 클래스를 몰라도 된다.
- 맵에 고정된 정적 물체는 `Net Load on Client`로 각자 로드하고 복제하지 않는다. 움직이거나 상태가 바뀌는 공유 물체만 복제하고, 컴포넌트 단위 변화는 해당 컴포넌트 복제를 켠다.
- 액터별 `NetUpdateFrequency`를 조정한다. 정지 대상은 낮추거나 휴면시키고, 변경될 때만 깨운다.
- 서버 실행 경로에서 UI·머티리얼 인스턴스·Niagara·사운드를 만들지 않도록 로컬 조종 여부·넷 모드로 감싼다. 지금은 리슨 서버지만 헤드리스 자동 검사와 이후 구조 변경에 대비한다.

### 캐릭터와 애니메이션

- 다른 플레이어의 조준 pitch는 `GetBaseAimRotation()` 값을 `FRotator::NormalizeAxis`로 다시 정규화한다. 네트워크 압축 뒤 음수 각도가 큰 양수로 복원되는 문제를 막는다.
- 회전 기준은 역할별로 고른다. 로컬 조종 캐릭터와 서버는 액터 회전, 다른 클라이언트에서 보이는 Simulated Proxy는 보간된 메시 회전을 쓴다. 조준·제자리 회전 값은 AnimInstance 업데이트에서 계산해 게임 스레드와의 갱신 차이로 생기는 떨림을 줄인다.
- AnimInstance C++ 변수 이름은 연결된 애니메이션 블루프린트 변수와 맞춘다. 상태 머신 전이 규칙은 State Alias·Conduit로 정리한다.

### 코드 구조

- 캐릭터 기능은 ActorComponent로 나눈다(이동·상호작용·인벤토리·굴착 도구). 분리 후 기존 동작을 회귀 검사한다.
- 시스템 간 알림은 타입 있는 델리게이트로 한다. C++ 내부는 `DECLARE_MULTICAST_DELEGATE`, Blueprint 노출이 필요하면 `DECLARE_DYNAMIC_MULTICAST_DELEGATE`, BP에서 부를 함수는 `UFUNCTION(BlueprintCallable)`로 연다.
- 세션·저장·플랫폼 연동 같은 전역 서비스는 Subsystem(GameInstance·World)으로 둔다. 같은 기능에 C++용·BP용 요청 함수를 따로 만들지 않는다. 함수 하나를 두고, BP 비동기 노드가 필요하면 그 함수를 감싼다.
- RPC `WithValidation` 실패는 연결을 끊으므로 정상 클라이언트가 만들 수 없는 값에만 쓴다. 길이 초과·잔고 부족 같은 일반 오류는 실패 응답으로 돌려준다.

### 작업 방식

- RPC·`UPROPERTY`·`UFUNCTION` 선언을 바꾸는 빌드는 에디터를 닫고 한다. 에디터를 켠 채 빌드하면 Blueprint 재인스턴싱으로 기본값이 깨질 수 있다.
- 멀티플레이 기능은 먼저 PIE `Play As Listen Server` 3인(호스트+클라이언트 2)으로 서버→클라, 클라→서버, 클라↔클라를 예비 확인한 뒤 M2(호스트+원격 3, 별도 프로세스 4인)로 검증한다.
- AI에게 구현을 맡길 때는 계획 문서를 먼저 받아 검토·수정한 뒤 구현을 요청한다.

현재 상태(2026-10-29 저장소 확인): GameplayTag는 쓰지 않는다(`DIGETHER.Build.cs` 의존·태그 설정 파일 없음). Asset Manager에는 엔진 기본 `GameFeatureData` 스캔 규칙만 있다(`DefaultGame.ini`, 미커밋 변경). 프로토타입 수치는 `ADigetherPrototypeGameMode`의 `EditDefaultsOnly` 속성(제한 시간·상호작용 거리·엘리베이터 용량·운행 횟수 등, Blueprint 기본값에서 편집 가능)과 `Prototype/DigetherPrototypeRules.h`의 고정 산식(일반 분배·시체 복구 50%)으로 나뉜다. 코드 재빌드 없이 일부 값은 바꿀 수 있지만, 정의 데이터 분리(R02)·호스트 기준 런타임 변경과 버전 동기화(R04)·레지스트리(R09~R10)는 충족하지 않으며 시체 복구 비율(D25)은 코드에 고정돼 있다.

공통 사용 규칙은 [표준 엔진 기능](../unreal/STANDARD_FEATURES.md), 코드 배치와 단계별 적용은 [코드 구조 계획](CODE_STRUCTURE_PLAN.md)을 따른다. DIGETHER 적용 현황(2026-10-29 저장소 확인)은 다음과 같다.

| 기능 | 현재 | 다음 조치(범위 확인 후) |
|---|---|---|
| GameplayTag | 미사용 | 태그 계층·네이티브 태그 선언, `GameplayTags` 의존 추가 |
| Primary Data Asset + Asset Manager | 정의 자산 없음. `GameFeatureData` 기본 규칙만 | 아이템·장비·몬스터·튜닝 정의 타입 등록 |
| 소프트 레퍼런스 | 미사용 | 정의 자산의 메시·사운드 참조부터 적용 |
| Enhanced Input | 모듈·기본 입력 클래스는 설정됨. 프로토타입 캐릭터는 `BindKey`·`BindAxisKey` 사용 | Input Action·Mapping Context로 이전 |
| Subsystem | 프로토타입은 `UGameInstance` 하위 클래스로 세션 처리 | 세션·저장을 GameInstance Subsystem으로 분리 검토 |
| 로그 카테고리 | 기능별 카테고리 사용, 일부 `LogTemp` 남음 | `LogTemp` 정리 |
| Data Validation·CommonUI·StateTree | 플러그인 활성 | 정의 자산 `IsDataValid`, 화면 스택 적용 |

아래는 **제안**이며 클래스 이름은 후보다. GameplayTags·Asset Manager·Primary Data Asset은 UE 엔진 기본 기능이지만 이 프로젝트의 적용·빌드·cook은 검증하지 않았다.

- **정의 자산**: 아이템·장비·몬스터 종·런 튜닝 프로필을 `UPrimaryDataAsset` 하위 클래스로 만든다(예: 아이템 정의에 무게·가치·슬롯 태그·히든 가능 여부). 런타임 인스턴스(아이템 인스턴스 ID·위치·소지자)는 정의와 분리한다.
- **Asset Manager 등록**: 각 정의 타입의 스캔 타입·경로를 `PrimaryAssetTypesToScan`에 등록하고, cook 규칙(기본값 `Unknown`)을 `AlwaysCook` 등으로 명시한다. 등록·규칙 설정과 별도로 패키지 빌드에서 `FPrimaryAssetId` 로드가 되는지 검증한다. 기존 `GameFeatureData` 규칙은 유지한다.
- **수치 표**: 곡선·단계표는 CurveTable/DataTable을 보조로 쓰되 같은 값을 두 곳에 두지 않는다([데이터 작업](../unreal/DATA_WORKFLOW.md)). 런 시작 시 고정할 값(R01·T65)은 정의 자산에서 읽어 런 스냅샷에 복사한다.
- **GameplayTag**: 분류·조회용으로 쓴다. 후보 계층은 `Item.Type.*`, `Item.Slot.*`, `Interact.*`, `Terrain.*`, `Player.State.*`. C++에서 쓰는 태그는 네이티브 태그 매크로로 선언하고 `GameplayTags` 모듈 의존을 추가한다. 동시에 참일 수 없는 상태(생존/매몰/사망/관전)는 enum 상태머신을 원본으로 두고 태그는 조회 보조로만 쓴다.
- **범위 밖**: Gameplay Ability System 도입은 별도 결정이다. 프로토타입 상수를 정의 자산으로 옮기는 작업은 사용자 범위 확인 후 진행한다.

## 구현 착수용 기술 계약

아래 계약은 구현 후보이며 실제 코드의 존재를 의미하지 않는다. UE API·공식 근거는 [엔진 기능 안내](UNREAL_FEATURE_COVERAGE.md)를 따른다.

| 논리 계약 | 검증과 확정 | 실패·경합 |
|---|---|---|
| CT-DIG / S07~09 | 도구·대상·거리·영역·버전을 확인한 뒤 변경 준비 → 충돌 준비 → 권위 상태 확정 → 시각·경로 갱신 | 준비 실패는 이전 유효 상태 유지. 오래된 비동기 작업의 완료는 최신 버전을 덮지 못한다. 수신 버전 공백은 해당 지역 스냅샷으로 복구 |
| CT-RESCUE / S10 | 구조 자격·대상 생존·거리 확인, 한 명 점유와 진행 | 중단·거리 이탈·연결 해제·사망은 진행 0 및 점유 해제. 대상 사망 후 늦은 완료를 거부 |

### 복제 규모와 월드 인계

회수품·잔해·보강·몬스터의 수가 늘면 모든 개체를 항상 전송하는 방식을 기본으로 두지 않는다. 정지 대상의 휴면과 변경 시 깨우기, 거리·관련성, 갱신 빈도, 소유자 전용 뷰, 비권위 연출 분리를 대상별로 결정한다. 기존 UE 5.8.2 소스 조사에서 확인한 Actor의 휴면·관련성·빈도 API는 [엔진 기능 안내](UNREAL_FEATURE_COVERAGE.md)를 따른다. 재진입 때 최신 상태·버전을 받고 은닉 정보가 전달되지 않는지 측정한다. Iris/Legacy 등 구체 방식과 예산은 미결이다.

월드 전환 없이 유지하는 장부와, 서버 GameInstanceSubsystem에 월드 객체 포인터 없이 데이터로 인계하는 후보를 비교한다. Seamless travel과 PlayerState 복사 경로도 비교하되 자동 보존 범위와 재생성 순서를 직접 확인한다. 비활성 PlayerState는 요구 전체를 해결하지 않으며 현재 GameModeBase와 동일시하지 않는다. 저장소·월드 파괴·세션 종료의 각 정리 조건을 구현 브리프에 명시한다.

### 정보·음성·튜닝

관전 UI는 대상의 허용된 공개 뷰만 사용하고 잔고·히든 슬롯을 받지 않는다. 엘리베이터의 정확한 중량은 호스트 판정에 사용하고 다른 화면에는 승인된 단계만 전달한다. 히든 줍기의 숨기는 동작은 모두에게 보이되 손 표시·월드 Actor·복제·로그에 내용이나 가치의 상세가 노출되지 않도록 하며 시체 복구액을 운반자에게 전달하지 않는다. 시각적으로 감추는 것과 데이터 수신을 차단하는 것을 구분한다.

몬스터 음성 감지는 호스트가 참가자의 음성 활동을 신뢰 가능한 방식으로 받을 수 있는지에 의존한다. 제공자에 따라 오디오 경로가 호스트를 통과하지 않을 수 있고 클라이언트 단독 보고는 위조될 수 있다. 서비스의 활동 신호·서버 접근·개인정보 및 지연을 비교하는 ADR/검증이 필요하며 지원을 가정하지 않는다. 전체 R01~R14와 테스트 빌드 동기화 계약은 [전체 시스템 설계](../SYSTEM_DESIGN.md)를 따른다.

### 착수 근거와 완료 조건

현재 게임 프로젝트는 Third Person 및 변형 템플릿과 두 Editor 워크벤치가 존재한다. 템플릿 전투, 의존 선언, 에디터 도구는 DIGETHER의 S 기능이 구현됐다는 증거가 아니다. 실제 확인과 검사 범위는 [프로필](../project/PROJECT_PROFILE.md), [개발 도구 안내](../tools/DEVELOPER_TOOLS.md)를 따른다.

각 구현 브리프에 S ID·승인 개정·입출력·소유 경계·수명·미결 항목·작업 경로와 정상/실패/경합 검사·담당 상태를 남긴다. 공유 맵·에셋의 담당과 잠금을 확인한다. 후보 ADR은 호스트 세션·ID/재접속, 복제 방식과 예산, 지형·충돌, 월드/장부 인계, 음성 및 몬스터 음성 감지, 저장 기준점·복구, 데이터/튜닝 원본이다. 구현 전 실험·의사결정 근거와 영향을 기록하며 이름만으로 채택으로 취급하지 않는다. 문서 완료와 L1~L3/M2·M3 실행 완료를 구분한다.
