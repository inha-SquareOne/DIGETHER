# 문서 지도와 프로젝트 문서 구성

이 문서는 프로젝트 기준과 작성 양식을 안내한다. 현재 확정값과 미결 항목은 [프로필](../project/PROJECT_PROFILE.md) 및 [프로젝트 문서](../project/README.md)에서 확인한다. 양식은 새 결정을 부여하지 않는다. 아래 '필수'는 필요한 정보의 최소 범위이며 파일 개수를 강제하는 뜻이 아니다. 작은 프로젝트는 여러 항목을 프로젝트 안내 문서 한 파일의 절로 합쳐도 된다.

## 프로젝트에 필요한 최소 정보

처음에는 아래 다섯 묶음만 갖춘다. 각 묶음에 연결된 양식 중 필요한 절만 가져와 기존 프로젝트 문서에 합칠 수 있다. 템플릿을 복사했다는 사실은 정책 채택이나 구현 완료가 아니다.

### 1. 목적·범위·요구사항

- 독자/목적: 기획·개발·검수자가 무엇을 만들고 무엇을 제외하는지 같은 기준으로 판단한다.
- 필수 항목: 사용자 목표, 사용 대상·플랫폼, 핵심 사용 흐름, 포함/제외 범위, 요구 ID·수용 관찰, 확정/제안/미결 구분.
- 작성/갱신: 착수 시 작성하고 범위·게임 규칙·수용 기준이 바뀐 작업에서 갱신한다.
- 책임: 프로젝트가 지정한 기획/요구사항 책임 역할. 실제 담당자는 미정이다.
- 관계/완료: [개요 양식](../templates/PROJECT_OVERVIEW_TEMPLATE.md) → 구조·검증·진행 기록으로 요구 ID를 연결한다. 검수자가 추정 없이 수용 여부를 판단할 수 있고 미결이 표시되면 작성 완료다.

### 2. 환경·온보딩

- 독자/목적: 처음 참여하는 사람이 동일한 프로젝트와 지원 환경을 열고 기준 실행을 재현한다.
- 필수 항목: 프로젝트 루트·.uproject, 엔진 패치/배포 방식·SDK·플러그인의 기준 출처, 소스 컨트롤·에셋 복원, 실행 순서·첫 맵/타깃, 정상 결과와 흔한 실패의 확인 위치.
- 작성/갱신: 첫 참여 전 작성하고 엔진·빌드 도구·의존성·시작 경로가 바뀔 때 갱신한다.
- 책임: 빌드/환경 담당 역할. 계정·키·개인 PC 경로는 공용 문서에 넣지 않는다.
- 관계/완료: [프로필 양식](../templates/PROJECT_PROFILE_TEMPLATE.md)은 설정 결정의 단일 출처, [온보딩 양식](../templates/ONBOARDING_TEMPLATE.md)은 그 설정을 사용하는 절차다. 실제 첫 실행의 환경·결과·한계를 기록해야 재현 확인 완료다.

### 3. 구조·공통 계약·소유권

- 독자/목적: 구현·콘텐츠 담당자가 상태와 변경의 책임 경계를 안다.
- 필수 항목: 진입점/맵·모듈/플러그인 의존, 상태 소유·수명, C++/Blueprint 경계, 공개 요청/결과 계약, 경로별 작성·통합·리뷰 책임과 AI 수정 범위.
- 작성/갱신: 첫 구조와 협업 경계를 잡을 때 작성하고 인터페이스·저장·모듈·소유권이 바뀔 때 갱신한다. 단순 프로젝트는 간단한 경로 표로 시작한다.
- 책임: 구조/통합 담당과 각 영역 담당 역할이 내용별로 책임지고, 프로젝트가 공유 경로 최종 책임자를 지정한다.
- 관계/완료: [구조 양식](../templates/ARCHITECTURE_TEMPLATE.md), [경계 양식](../templates/PROJECT_BOUNDARIES_TEMPLATE.md)을 연결한다. 공개 계약과 실제 코드 위치가 추적되고 미구현·미검증이 구분되어야 한다. CODEOWNERS 리뷰 소유권은 쓰기 권한·잠금을 대신하지 않는다.

### 4. 개발 흐름·테스트·완료 기준

- 독자/목적: 작성자·리뷰어·검수자가 같은 작업 종료 기준을 쓴다.
- 필수 항목: 브리프→담당 경계→구현→검사→리뷰→문서 갱신 순서, 코드/에셋 변경 안전성, 실제 검사 명령과 기대 테스트 수, 증거 위치·실패/skip/미실행 판정, 필요한 L/M등급.
- 작성/갱신: 첫 작업·검사 실행 전 작성하고 명령·CI·대상 플랫폼·검증 요구가 바뀌면 갱신한다.
- 책임: 개발 흐름/검증 담당 역할. 테스트 소스 작성과 읽기 전용 실행 검증 역할을 구분한다.
- 관계/완료: [개발 흐름 양식](../templates/DEVELOPMENT_WORKFLOW_TEMPLATE.md), [검증 계획 양식](../templates/VERIFICATION_PLAN_TEMPLATE.md)에서 [AI 실행 기준](../ai/EXECUTION_POLICY.md)과 [검증 기준](../ai/VERIFICATION.md)을 채택한다. 필요한 검사가 재현 가능하고 실제 증거로 완료를 판정할 수 있어야 한다.

### 5. 현재 진행·차단·재개 지점

- 독자/목적: 팀과 다음 작업자가 현재 진행과 다음 행동을 찾는다.
- 필수 항목: 작업 ID·요구 ID·선행 조건·현재 상태·수용 기준·실제 증거·담당 역할·차단 사유·다음 행동. 일정은 확정된 경우만 기록한다.
- 작성/갱신: 작업을 시작할 때 만들고 상태 변화·통합·중단·인계 때 갱신한다. 과거 실행 기록은 현재 통과 주장과 구분한다.
- 책임: 각 작업 담당이 결과를 쓰고 통합 담당이 전체 상태를 확인한다.
- 관계/완료: [진행·인계 양식](../templates/STATUS_HANDOFF_TEMPLATE.md)에서 요구·검증·결정 기록을 연결한다. 다음 사람이 개인 대화를 읽지 않고 재개할 수 있으면 인계 작성 완료다. 게임 기능 완료와 문서 작성 완료는 다르다.

## 필요할 때 확장

### 상세 게임/콘텐츠 설계

여러 시스템·규칙·수치·콘텐츠 제작물이 생겨 개요로 부족할 때 분리한다. 독자는 기획·아트·구현·검수자이며 목적은 구현 가능한 설계 계약이다. 요구 ID, 규칙·입출력·상태/실패/복귀, 값의 단위와 설계/실행 출처, 자산 의존·수용 관찰이 필수다. [개요 양식](../templates/PROJECT_OVERVIEW_TEMPLATE.md)의 상세 기능 양식을 반복 사용한다. 관련 기능 착수 전에 작성하고 설계 변경과 함께 갱신한다. 기획/영역 담당이 책임지며 구조·데이터·검증으로 추적되어야 작성 완료다. 게임별 전용 장르나 수치를 공통 문서에서 정하지 않는다.

### 설계 결정 기록

되돌리기 어렵거나 대안·제약을 나중에 설명해야 할 때 [결정 양식](../templates/DECISION_RECORD_TEMPLATE.md)을 사용한다. 독자는 현재/미래 유지보수자다. 문제·대안·상태·결정 근거·영향·재검토·대체 관계가 필수다. 결정 시 작성하고 채택/대체 때 갱신하며 결정권자와 기록 담당 역할을 구분한다. [ADR 스킬](../../.agents/skills/architecture-decision-records/SKILL.md)과 연결한다. 미승인 제안이 accepted로 표시되지 않고 기존 결정과 연결되면 작성 완료다.

### 릴리스·운영

외부 배포·지속 운영·세이브/서버 이관이 있을 때 [릴리스·운영 양식](../templates/RELEASE_OPERATIONS_TEMPLATE.md)을 사용한다. 독자는 배포·운영·검수 역할이다. 버전/아티팩트 추적, 승격 조건, 설정·라이선스, 저장 호환·백업·복구/되돌리기, 관측·장애 대응·인계가 필수다. 첫 배포 전에 작성하고 배포마다 실제 결과로 갱신한다. 릴리스 책임 역할이 통합하며 검증 계획과 결정 기록을 연결한다. 실행·복구 확인과 미검증 한계, 실제 승인 근거가 있어야 배포 완료로 판단한다.

### 외부 에셋·의존성 대장

외부/유료/생성 에셋이나 플러그인을 도입할 때 [자산 대장 양식](../templates/ASSET_REGISTER_TEMPLATE.md)을 사용한다. 독자는 콘텐츠·빌드·배포 담당이다. 원본 출처·버전·권리/고지·보관/도입 경로·변경·재현/검증·갱신 책임이 필수다. 도입 전에 작성하고 교체·수정·라이선스 변화 시 갱신한다. 온보딩·아트 기준·릴리스에 연결하고 필요한 사용권·고지·실제 도입 상태가 확인되면 해당 항목 완료다. 계정 잔액이나 비밀키는 기록하지 않는다.

### 규모가 커지는 경우

멀티플레이 계약·데이터 마이그레이션·성능 예산·운영 절차는 위 구조/검증/릴리스 문서에서 시작하고, 여러 팀이 따로 갱신할 만큼 커질 때만 별도 사람용 문서로 분리한다. 독자·책임·갱신 계기·완료 기준과 단일 출처를 이 지도에 추가한다. [Unreal 기준](../unreal/README.md)은 공통 기술 제약이며 프로젝트가 채택한 실제 설정을 대신하지 않는다.

## 읽는 순서와 정합성

사람은 목적·범위 → 온보딩 → 담당 경계/구조 → 현재 작업/검증 순으로 필요한 절을 읽는다. AI는 루트 진입 지침 → 해당 프로젝트 문서 → 작업에 필요한 [AI 기준](../ai/README.md)·[Unreal 기준](../unreal/README.md) 순으로 읽는다. 모든 문서를 매번 전부 읽을 필요는 없다.

요구사항은 사용자 결정과 승인된 설계, 현재 구현은 코드·에셋, 실행 성공은 해당 환경의 검사 증거가 각각 근거다. 서로 다르면 차이를 기록하며 코드가 있다는 이유로 요구사항을 조용히 바꾸지 않는다. 문서 갱신과 이동은 [문서 관리](DOCUMENTATION_POLICY.md)를 따른다.
